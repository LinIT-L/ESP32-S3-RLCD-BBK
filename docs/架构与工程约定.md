# LinTOS 架构与工程约定

> 处理对象：系统架构分层、模块契约、事件调度、内存策略、编码规范、编译/烧录/提交。
> 新功能怎么做 → 见《开发指南》；UI 细节 → 见《UI规范》。

## 1. 架构分层（五层，物理落在目录上）

> V1.2 起分层**不再只是约定，而是目录结构 + 构建守卫**：`components/<层>/<组件>`。
> 完整盘点与实施记录见《模块化重构方案》。

```
rank 5  apps/       L4 应用层   应用页（每个 .c 一页）+ theme/主题引擎 + 装配 apps_register_all()
rank 4  engines/    L3 引擎层   模拟器核心 + 引擎支撑件(board_shim/cheater/color_convert/shared_memory)
rank 3  system/     L2 系统层   os 内核(kernel/services) + input + engine_manager + app_board + bbk_boot
rank 2  services/   L1 服务层   svc_nvs/cfg/log/time · wifi · bt · usb_* · audio · tone · vibrator · keyvault · favorites · web_gamepad
rank 1  ui/         L1 UI 层    ui_common · fonts · kbd_lib · virtual_keys · wallpapers
rank 0  drivers/    L0 驱动层   st7305 · touch_panel · sd_scan · board_battery
rank 0  libs/       L0 库       calc · lua
rank 9  tools/      开发工具     self_test（不受分层约束）
```

## 2. 依赖规则

- **R1 只允许 高层 → 低层**（rank 大 → rank 小）。**同层互调允许**（如 services 内 A 用 B），
  **跨层反向禁止**（system 不得依赖 engines/apps；ui 不得依赖 services）。
- **R2 唯一 API 面**：引擎只经 `engine_api.h`、应用只经 `os_app_api.h` 访问底层能力；
  不得直接 `#include` 驱动/服务头。
- **R3 禁止循环依赖**（CMake 目标图必须无环）。跨层"回调需要"用**注入式回调**解决，
  不要反向 include —— 例：`gam4980_set_exit_confirm_cb()` 由 os 侧注入。
- R4 能力经接口契约暴露（`os_module_t` / `os_service_t` / facade），面向抽象编程。
- R5 新增 = 注册表加一行 + 实现模块（开闭原则）；C 应用用 `tools/new_app.py` 一键接线。
- R6 依赖必须**显式声明**：`REQUIRES`（对外，参与链接）/ `PRIV_REQUIRES`（仅内部）。
- R7 一个模块一个职责；R8 `.c/.h` 结伴自包含，私有 static state 留本文件。
- **R9 守卫强制**：`tools/check_deps.py` 静态校验 R1/R2/R3，**已接入构建**（违例即构建失败）。
  已知历史欠债登记在脚本的 `ALLOW_INVERSIONS` 表（当前 5 条，全是 `wallpapers → services`，
  正解是把电源/屏保部分拆出 `services/power`）。
  > ⚠ ESP-IDF 的 `REQUIRES` **只管链接顺序、不管 include 可见性**（public 头全局可见），
  > 所以"分层"必须有静态脚本兜底，光靠 CMake 管不住。

## 3. 组件规范

- 一目录一职责=静态库；`include/` 公共头；命名小写下划线、类型 `_t`。
- 尽量自包含（字体/图标随模块私有）；驱动组件不混业务资源。
- 跨模块相同代码抽共享组件单源。
- **外设单一所有权**：一个外设（I2C 口、UART、I2S、SPI 设备）只有一个组件负责初始化与持有句柄，别人用它的 API。
- **API 只增不改**：已发布函数签名/字段不改，要改就新增并保留旧符号（改了就是 ABI 事故）。
- 条件编译走 `LINTOS_ENABLE_*`：未完成功能默认 `=0`，不注册就不占 RAM。
- **新模块必须能独立验证**：给一条 `remcon` 命令或最小烧录示例，不能只靠"进某页点几下"。

## 4. 模块契约

- 页面实现 `os_module_t`(on_enter/on_exit/render/action/touch/poll)。
- 懒加载 `os_hw_request/store`；退出必须释放自己申请的资源（任务/堆/外设），不遗留后台线程。
- 全局服务 `os_register_service`（tick/render/touch 热区），不占页面栈。

### 4.1 资源生命周期（合入门槛）

- **`init/start` 必须配对 `deinit/stop`**；无配对不得合入。
- deinit 顺序：**注销回调 → 停任务/定时器 → 关外设/射频 → 释放堆 → 归还总线/引脚**，最后指针置 NULL。
- 共享资源（I2C 总线、USB、PSRAM 池）用**引用计数**，最后一个用户释放。
- ⛔ 启动时全量初始化；高耗能模块（WiFi / BT / USB / 音频 / GPS）必须有明确开关时机。
- `esp_pm_lock` 必须配对 `release`，最小持有，⛔ 在 ISR 里操作。
- **交付必须给**：改动前后 heap / 栈高水位 / 组件 size；deinit 后 heap 应回到基线。

## 5. 事件调度

单主循环（Reactor）：统一轮询输入 → 分发 action/touch → 服务 tick+模块 poll → 统一渲染。
长时间阻塞操作（TLS/HTTP/扫描）放独立高栈 task 并保证退出回收。

## 6. 内存（ESP32-S3：IRAM 与 DRAM 共享同一块 SRAM）

**核心事实**：S3 上 IRAM（代码）与 DRAM（数据）**共享物理 SRAM**，且链接脚本用 `.dram0.dummy`
占位 IRAM 已用空间 —— 所以 **IRAM 常驻代码少 1KB，内部堆就多 1KB**；反之亦然。

- 内部 SRAM：热路径 / 性能关键（引擎热循环放 IRAM 是**有意的取舍**，别一刀切下沉）。
- PSRAM：大缓冲 / 表 / 帧缓冲 —— 用 `EXT_RAM_BSS_ATTR`（单变量）
  或**组件级** `linker.lf` + `LDFRAGMENTS`（整组件 `.bss`，见下）。
- **禁 cache 期间不可访问 PSRAM**：flash/分区写入、NVS commit、`esp_*_sleep_start`、
  `esp_bt_controller_init` 等会关 Flash+PSRAM cache。**含此类路径的静态数据必须留内部**
  （典型：`bt_ctl` 里的 bt_init 任务静态栈 → 故 `bt_ctl` 的 `.bss` **不迁 PSRAM**）。

**已实测的内部 RAM 收益（V1.2）**：

| 项 | 数值 |
|---|---|
| `apps` 组件 `.bss` 整体迁 PSRAM（`components/apps/linker.lf` + `extram_bss`） | `.dram0.bss` 58,416 → **21,544 B（−36.9 KB）** |
| 对应内部堆 | main_free ≈10.3 KB → **≈47 KB（预期，待上机复核）** |

> ⚠ 组件级迁移的**唯一坑**：`linker.lf` 不会自动发现 —— 必须在
> `idf_component_register()` 里写 `LDFRAGMENTS "linker.lf"`，否则**静默失效**（不报错、不生效）。
> 验证必须用 `readelf -SW build/LinTOS.elf | grep -E "dram0.bss|ext_ram.bss"` 看节大小是否真的转移。

---

#### 6.1 强制规范（所有新代码/新应用必须遵守）

> 2026-10-05 由独立文档 `内存使用强制规范.md` 并入 —— 它和 §6 讲的是同一件事（东西放哪、怎么验收），分两处看容易漏。

> 一句话：**内部 RAM 只留给"物理上不能放 PSRAM 的东西"，其余一律放 8MB PSRAM。**
> 立规依据（2026-10-02 实机事故）：蓝牙(手柄)+WiFi 同开时内部堆只剩
> `free=15171 largest=7680`，导致 **TLS 上下文（需一块连续 16KB）分配失败**，
> `esp_http_client_open` 242µs 就返回 `ESP_ERR_HTTP_CONNECT`（28674）——
> 航班雷达"取数一直失败"就是这么来的。

#### 一、为什么不能"全部丢 PSRAM"（4 条硬约束）

| # | 约束 | 后果 | 谁受影响 |
|---|---|---|---|
| 1 | **禁 cache 窗口**：写 flash / NVS commit、`esp_bt_controller_init`、进深睡(`esp_deep_sleep_start`) 期间 **PSRAM 不可访问** | 该期间只要碰到 PSRAM → `LoadProhibited`/cache 错误 | 这些路径上的**任务栈**与**数据**必须内部 RAM |
| 2 | **中断处理 / `IRAM_ATTR` 代码**不能从 PSRAM 执行 | 中断里跳 PSRAM 直接崩 | ISR、`IRAM_ATTR` 函数 |
| 3 | **部分外设 DMA 要求内部 RAM**（本项目 LCD flush 缓冲等） | DMA 数据错/不触发 | 驱动层缓冲 |
| 4 | **启动早期 PSRAM 未初始化**（`app_main` 早期、二级引导） | 访问即崩 | 启动路径代码/数据 |
| 5 | 性能：PSRAM 走 cache 且与 flash 争带宽（内部 RAM 快约 3~5×） | 每帧热路径会掉帧 | 逐帧重绘的大块数据 |

> 结论：不是"内部 RAM 不该用"，而是"**内部 RAM 必须省着用**"。

#### 二、怎么做（本仓库的具体写法）

| 场景 | 写法 |
|---|---|
| **大块静态缓冲**（≥1KB，长驻） | `EXT_RAM_BSS_ATTR static uint8_t buf[N];` —— 放 PSRAM 的 .bss |
| **大块动态分配** | `heap_caps_malloc(n, MALLOC_CAP_SPIRAM)`；失败再退回 `MALLOC_CAP_INTERNAL` 兜底 |
| **小对象 / 每帧热路径** | 普通 `malloc`（`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`，≥2KB 才会去 PSRAM） |
| **任务栈** | **默认内部 RAM**；只有"该任务绝不触碰禁 cache 路径"时才可 PSRAM 栈，**必须写注释说明为什么安全** |
| **Lua 应用的缓冲** | 桥里已经有 `EXT_RAM_BSS_ATTR` 的范例（`luat_lib_net.c` 的 16KB 响应体、`os_pane`、`AM_COL` 141KB、`s_pkg[]`），照抄 |

现成设施（不要造轮子）：
- 宏：`EXT_RAM_BSS_ATTR`（`esp_attr.h`，把 .bss 段放进 PSRAM）
- API：`heap_caps_malloc/get_free_size/get_largest_free_block(MALLOC_CAP_SPIRAM|MALLOC_CAP_INTERNAL)`
- 已开配置：`CONFIG_SPIRAM_USE_MALLOC=y` / `SPIRAM_MALLOC_ALWAYSINTERNAL=2048` /
  `SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` / `SPIRAM_MALLOC_RESERVE_INTERNAL=8192` /
  `FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`（⚠ 能开不代表该开，栈默认仍用内部）

#### 三、验收标准（新功能合入前必须过）

1. `remcon audit` → 看 `internal free / largest`：
   - **`largest` 不得低于 8KB**（低于 8KB 就没法做 TLS/HTTPS，凡是联网应用都会挂）
   - 加完新功能后 `free` 不应比加之前下降超过 8KB（大块必须去 PSRAM）
2. 同开关状态对比（蓝牙开/关、WiFi 开/关各测一次）—— **不同状态下的数字没有可比性**。
3. 联网功能必须在"**蓝牙 + WiFi 同时开**"的最坏情况下测通（这是内部 RAM 最紧的场景）。

#### 四、已犯过 / 已修的典型

| 现象 | 根因 | 修法 |
|---|---|---|
| 联网取数一直失败，错误码 **28674** (`ESP_ERR_HTTP_CONNECT`)，且 200µs 内就失败 | mbedtls 的 TLS 收发缓冲默认 `IN_CONTENT_LEN=16384` **放在上下文里一次性 calloc**，要求一整块连续内部 RAM；BT+WiFi 同开时最大连续块只剩 7.6KB → 分配失败 | ① `CONFIG_MBEDTLS_DYNAMIC_BUFFER=y`（缓冲改为按需单独分配）② `IN_CONTENT_LEN 16384→4096`、`OUT 4096→2048` ③ `esp_http_client` 的 `buffer_size` 2048→1024 |
| 页面/应用一多就"莫名卡"或分配失败 | 大块缓冲写了 `static`（落在内部 BSS） | 改 `EXT_RAM_BSS_ATTR` |

#### 五、代码审查自查 3 问（提交前问自己）

1. 我新加的**静态数组**超过 1KB 了吗？→ 超过就必须 `EXT_RAM_BSS_ATTR`。
2. 我新加的**动态分配**会不会是 ≥2KB 的大块且长驻？→ 是就用 `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`。
3. 我的新任务会不会调用 **flash 写 / NVS commit / `esp_bt_controller_init` / 深睡**？
   → 会就必须用内部 RAM 栈；不会才可以考虑 PSRAM 栈（并写注释）。

## 7. 编码规范

函数 `xxx_yyy`、常量 `#define XXX_Y`、类型 `typedef ..._t`；
头文件顶部说明用途/依赖、`#pragma once`；
校验输入/指针/边界、状态机带超时、ISR 尽量短；中文资源为 UTF-8。

**日志纪律（V1.2 起）**：**高频上下文一律 `ESP_LOGD`**，不得用 `ESP_LOGI`。
高频上下文包括：ISR、HID 输入报告回调（手柄连着时 100+ Hz）、PCM 回调、
每帧调用的 `poll/tick/render`、`recvfrom`/`accept` 循环、2 秒级诊断心跳。
原因：一条日志经阻塞式控制台写出 ≈5 ms @115200，出现在 100 Hz 路径上就是 500 ms/s 的净损耗。
排查时用 `esp_log_level_set("TAG", ESP_LOG_DEBUG)` 临时打开。

## 9. 音频任务与 CPU 分核（2026-10-25 定案）

> 起因：仙剑接 RIX 音乐后整机死机。日志证据 `task_wdt: CPU 0: sdl_aud` / `- IDLE0 (CPU 0)`，
> 反解栈 `audio_task → AUDIO_FillBuffer → RIX_FillBuffer → CEmuopl::update → DBOPL2::adlib_getsample`。
> 结论：**音频合成不是"能算就行"，它和模拟任务抢同一个核时会把 IDLE 饿死，进而触发 TWDT 重启。**

### 9.1 现状（全部引擎逐一核对过）

| 模块 | 执行体 | 核 | 音频在哪产生 | 结论 |
|---|---|---|---|---|
| GB / GBC (`gbc_emu`) | `gbc_emu` | **CPU1** prio 4 | **同一任务内**（`gbc_emu_feed_audio`）| ✅ 合规 |
| NES (`nes_emu`+`video_audio`) | `nes_emu` | CPU1 prio 4 | 同一任务内 | ✅ |
| SMS (`sms_emu`) | `sms_emu` | CPU1 prio 4 | 同一任务内 | ✅ |
| MD (`md_emu`+`genesis_snd`) | `md_emu` CPU1 prio 4；`genesis_snd` CPU1 prio **20** | CPU1 | 单独任务，但**按帧信号量同步**（不自由跑）| ⚠ 见 R3 |
| ArduBoy / 宠物机 | 各自单任务 | CPU1 prio 3 | 同一任务内 | ✅ |
| GAM4980 | `gam4980` | CPU1 | 同一任务内 | ✅ |
| SDLPal | `sdlpal` CPU0 prio 5；`sdl_aud` CPU1 prio 5 | 分开 | **独立任务**（SDL 回调模型决定）| ⚠ 见 R2 |
| 音频后端 | `audio_out` CPU1 prio 8；`audio_play`（MP3）CPU1 prio 1 | CPU1 | 只负责 PCM→I2S | 固定，勿改 |

### 9.2 规则

- **R1 引擎音频合成必须在模拟任务内完成**，只把 PCM 塞进 `audio_player_feed_pcm()` 的环形缓冲。
  单独起一个"音频任务"在 ESP32-S3 上等于把同一个核切成两半，双输。
- **R2 必须独立音频任务时（SDL 回调模型）**：钉 **CPU1**、优先级 **≤ 8**（不得高于 `audio_out`），
  并且**必须带超时自保**：单次回调 > 120 ms 连续 2 次 → 关掉该模块（如音乐），保留系统。
  `sdl_audio.c` 的 `s_music_on` / `slow_hits` 就是这套兜底的样板。
- **R3 高优先级放"被信号量驱动"的任务**：`genesis_snd` prio 20 只在收到帧信号后短暂运行，
  属可接受；**但严禁**把自由跑（`while(1)` 里持续算）的任务设到 > 8，否则会饿死 `audio_out`。
- **R4 贵合成先降级再考虑移植**：OPL/MIDI 软合成在本机实测单核实时因子 < 1
  （44.1 kHz 双芯片、22.05 kHz 单芯片两种配置都跑不到实时），**不是调参能救的**。
  正解是**预渲染**（RIX→MP3/ADPCM，交给 `audio_player` 的 minimp3 解码）。

### 9.3 怎么验证（不要靠听，靠日志）

```
remcon tasks        # 看任务名/优先级
# 死机后看串口：task_wdt 会打印 "CPU x: <taskname>"
# 音频丢帧: remcon audio -> "PCM ring: ... underruns=N ... play=xxxxHz"
```
`underruns` 持续增长 + `play` 远低于 `want` ⇒ 生产端供不上，先查是不是合成太重。

### 9.4 桩函数红线（2026-10-25 血案）

SDLPal 的音频回调链是"先填、后调桩"：

```
AUDIO_FillBuffer(): memset(stream,0) → 音乐 FillBuffer(stream) → 调音量
                  → 音效混音 → AVI_FillAudioBuffer(stream)   ← 最后一步
```

因此**任何写在末端的桩都不许碰 stream**。`pal_stub.c` 里 `AVI_FillAudioBuffer` 曾写成
`memset(stream,0,len)`，结果把音乐和音效整块清零 ⇒ 表现是"合成正常、音量正常、播放器探针满幅，
但一帧声音都没有"，换了两个 OPL 核、三种采样率都查不出来。

规则：
- 空实现的桩只允许 `(void)参数;`，**禁止 memset/写缓冲区**。
- 替换/关闭某子系统时，先确认它在调用链里的**位置**（末端 vs 中段），再看它是否持有输出缓冲。
- 排查"没声音"的顺序：播放器探针（直接问）→ 完整回调探针（走链路）→ 两者不一致就去看链路里谁动了 buffer。
