## 三、🔴 F2：Lua 崩溃排查（未定论）

**现场证据**
- `page_lua.c:69` 探针注释：*"首次打开 Lua 应用整机重启, 串口在复位瞬间丢字抓不到 panic → 用阶段号反推死在哪一步"*（09-28）
- `ss_crash.py`（仓库根）：串口 `usbmodem101` 抓 90s，命中 `Backtrace/Guru/abort/panic` 打 `### CRASH DETECTED ###`
- `backup_lua_apps_20260928/`（10 个 **packed** 版）+ `apps/` 清空 + C 版回归 ⇒ **用下架来规避崩溃**
- 探针阶段 1–13 全在用：1-2 启动链路、3-4 进页、5-11 加载执行、**12-13 = `on_enter` 前后**

**我做的 3 项静态排除**（都能给出"不是它"的依据）

| 假设 | 取证 | 结论 |
|---|---|---|
| 脚本死循环（会触发 WDT 复位） | 10 个应用里 4 处 `while true`：`calc` 递归下降解析 ×2、`wb`/`wifiprobe` Bresenham 画线 —— **全部带 break 出口** | ❌ 排除 |
| Lua 管线被摘掉 | 检索核实：注册在 `apps_registry.c:133`、ELF 里有 `lua_pcall/lua_newstate`、`am_lua.c`+`am_store.c`+`page_main.c` 都走 `OS_PAGE_LUA` | ❌ 排除 |
| 首次写 NVS 落在禁-cache 窗口（项目著名坑） | `app.nvs.*` → `svc_nvs_*` 确实是 flash 写，但**当前任务栈在内部 RAM**（main 12 KB），不是 PSRAM 栈 → `esp_task_stack_is_sane_cache_disabled()` 断言不成立 | ❌ 排除 |

**剩下第一嫌疑：主任务栈被吃光**（硬证据）
- 09-15 抓的日志里每 1s 一行：`BBK: STACK main_free=10172` → main 任务配置 **12,288 B**、稳态只剩 **10.1 KB** 可借
- 而 `luaL_openlibs` + 解析 30–45 KB 脚本是**C 栈大户**，Lua 解析器又是**递归下降** → 脚本一大就极易吃掉 >10 KB
- 这也解释了"**首次**"：首个运行的脚本往往最大（netdect 45.9 KB / wb 30.9 KB）

**我做的增强（让下次一定抓到根因）**
探针从"只记阶段号"升级为**同时记资源快照**（RTC 保留内存，多 4 个字）：

| 下次读到的组合 | 直接指向 |
|---|---|
| `栈余`≈0 词 | **① 栈溢出**（第一嫌疑） |
| `内部堆`/`PSRAM`≈0 | ② 分配失败路径 |
| 都够 + `复位原因=panic/4` | ③ 禁 cache 窗口摸了 PSRAM（`lua_State` 在 PSRAM） |
| `任务=` 不是 main | 换方向（不在主任务上跑） |

打印样例：`上次复位前: 阶段=10 'loadbuffer 完成' 任务=main 栈余=41词(≈164B) 内部堆=188631 PSRAM=6962928 | 复位原因=4`

**复现步骤（需要接设备）**
```bash
python3 ss_crash.py          # 抓 90s
# 期间：应用管家 → 打开任意 Lua 应用（或从 TF 放一个 .lua）
# 复位后看 UART 里 LUAPROBE 两行（开机立即 + 10s 后再复读一次，避开 CDC 重枚举丢字）
```

**若确认是栈**：把 `lua_load_run()` 放到**内部 RAM 栈的专用任务**里跑（项目现成范式就是 `bt_init` 为禁-cache 调用专门开任务），或先把 `CONFIG_ESP_MAIN_TASK_STACK_SIZE` 从 12288 提到 16384 做 A/B 验证。

## 四、🟡 F3：apps 分区 4 MB 空置（决策表）

| 分区 | 大小 | 实际占用 |
|---|---|---|
| factory | 5 MB | 4.42 MB（余 16%，824 KB） |
| appdata | 6.625 MB | ≈5.17 MB（8.BIN 2M + E.BIN 2M + 字库 1.18M）→ 余 ~1.45 MB |
| **apps** | **4 MB** | **0**（全 0xFF） |

三个选项（**我不擅自改分区表**，改分区 = 必须整片烧 + 清数据）：

| 方案 | 操作 | 收益 | 代价 |
|---|---|---|---|
| **A. 缩到 512 KB**（推荐） | apps 4MB→512KB，余 3.5MB 给 appdata | appdata 从余 1.45MB → 近 5MB，够放更多 ROM/字库/词典 | 需整片烧一次；以后再想放 Lua 应用仍有 512KB（10 个应用实测仅 210KB） |
| B. 缩到 512 KB 且余量给 factory | 同上但给 factory | 固件头寸 16%→75% | 同上；factory 5MB 对当前 4.42MB 已够 |
| C. 先不动 | 保留 4MB | 零风险 | 4MB 就是空的（若近期要回归 Lua 应用，反而省事） |

> 我的建议：**若近期不回归 Lua 应用就选 A**；准备回归就先 C，别白烧两次。

## 五、🟡 F4：merge_flash 静默复用旧 apps 镜像 —— 已修

**原逻辑**：`apps/lua` 存在才重新生成 `apps_l.bin`；否则**直接沿用** `build/apps_l.bin`（无提示）。
**风险**：某次忘了删旧镜像，就会把已下架的应用/旧脚本烧回设备 → 应用管家出现"C 版 + Lua 版"重复条目。
**已改**：源目录不在时 → 明确打印提示并**生成空镜像**（临时空目录喂 spiffsgen，实测空目录能正常出 4MB 全 0xFF 镜像）。`bash -n` 语法校验通过。

## 八、方法自查（本轮我纠正过的 2 个假结论）

1. **bash `grep "a\|b"` 的 BRE 假阴性**：一度得出"`page_lua` 没注册、Lua 管线被摘掉"——**错**。macOS BSD grep 对 `\|` 交替不可靠，换检索工具后确认接线完整。（这条本项目早就记过，我又踩了一次；已按纪律回到"交替匹配一律用检索工具"。）
2. **grep 假阳性**：搜 `pmic` 命中 AVR 模拟器的 `iox*.h`（AVR XMEGA 的 PMIC = 可编程中断控制器），并非电源芯片代码 → 避免误报"已有 PMIC 驱动"。
