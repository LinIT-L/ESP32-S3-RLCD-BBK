## 2. 接口总览

两者都是 **WP REST**，`POST`，`Content-Type: application/x-www-form-urlencoded`（也可以 JSON）。

```
注册  POST https://bbk.linit.cn/?rest_route=/lp/v1/register
心跳  POST https://bbk.linit.cn/?rest_route=/lp/v1/heartbeat
```

用 `?rest_route=` 形式而不是 `/wp-json/`：不依赖站点的固定链接配置，换环境也不会 404。

**与管理后台完全分离**：设备端只碰这两个 route；后台页面走 WP 账号 + `manage_options`。
设备端**不持有**任何后台凭据。

## 3. 身份与防伪

### 3.1 设备 ID 由 MAC 派生（服务端强校验）

```
dev_id = "LNT" + MAC 去掉分隔符并转大写
3C:71:BF:11:22:33  ->  LNT3C71BF112233
```

服务端**重新计算** `dev_id` 并与请求里的比对，不一致直接 `400 BAD_DEV_ID`。
所以「只改 dev_id 冒充别的设备」不成立——那必须同时改 MAC，而 MAC 在库里唯一。
（MAC 本身来自 eFuse，固件不允许伪造；见 §7。）

### 3.2 两把密钥

| 密钥 | 用途 | 存放 | 强度 |
|---|---|---|---|
| **产品级 key** | 注册请求签名 | 烧进固件（编译期常量或 NVS 预置） | 32 字节随机串，后台可改 |
| **设备密钥 secret** | 心跳签名 | 注册应答下发，设备存 NVS | 24 字节随机（48 hex），每次注册轮换 |

产品级 key **不是**管理员密码，泄露只能伪造注册（污染统计），拿不到任何后台权限。

### 3.3 签名串（必须逐字节一致）

```
register:  "register\n{dev_id}\n{mac}\n{board}\n{chip}\n{fw}\n{proto}\n{ts}\n{nonce}"
heartbeat: "heartbeat\n{dev_id}\n{ts}\n{nonce}"
sig = lowercase( hex( HMAC_SHA256( key, 上面的串 ) ) )
```

⚠ **签名针对设备发来的原始字符串**（不裁剪、不改大小写）。
服务端只在校验通过之后才做长度裁剪与白名单过滤入库 —— 否则诚实设备会因为
"board 太长被截断"而永远验签失败（实测踩过）。

⚠ MAC 必须**大写 + 冒号分隔**（服务端正则 `^([0-9A-F]{2}:){5}[0-9A-F]{2}$`）。

### 3.4 防重放

- `ts` 为 Unix 秒，服务端容忍 **±300 秒**（设备时钟不准也能过，但不能差太多）。
- `nonce`：16 hex 随机，**同一个 nonce 只能用一次**（`wp_lp_nonces` 主键去重）。
- 两者任一不过 → `400 BAD_TS` / `409 REPLAY`。

### 3.5 频率限制

| 接口 | 限制 |
|---|---|
| register | 同 IP 每分钟 30 次 |
| heartbeat | 同 IP 每分钟 240 次（≈ 4 台设备 × 10 分钟一次仍很宽松） |

超限 → `429 RATE_LIMIT`。

## 4. 注册

### 请求

| 字段 | 说明 |
|---|---|
| `dev_id` | `LNT` + 12 hex |
| `mac` | `AA:BB:CC:DD:EE:FF`（大写） |
| `board` | 硬件型号，≤32，`[A-Za-z0-9._-]` |
| `chip` | 芯片型号，≤32 |
| `fw` | 固件版本，≤32 |
| `proto` | 协议版本，当前 `1` |
| `ts` / `nonce` / `sig` | 见 §3 |

### 应答 200

```json
{"ok":true,"secret":"<48 hex>","hb":600,"proto":1,"server_ts":1761880000}
```

设备要做的事：**把 `secret` 写进 NVS**，按 `hb` 秒定时心跳。

### 语义

- 首次注册：建行，`first_seen = last_seen = last_hb = now`，记 `register` 事件。
- 重复注册（同 MAC）：**不新建**、**不覆盖 `first_seen`**、**轮换 secret**，
  记一条 `register`（detail=`repeat`）。→ 设备重刷固件丢了 NVS 也能自愈，但旧 secret 立即失效。

### 错误码

| code | err | 含义 |
|---|---|---|
| 400 | BAD_MAC | MAC 格式不对 |
| 400 | BAD_DEV_ID | dev_id 与 MAC 不匹配（伪造） |
| 400 | BAD_PROTO | 协议版本越界 |
| 400 | BAD_TS | 时间戳超窗 |
| 400 | BAD_NONCE | nonce 太短/非法 |
| 403 | REGISTER_CLOSED | 后台关闭了注册 |
| 403 | NO_KEY_CONFIGURED | 后台没配产品密钥 |
| 403 | BAD_SIG | 签名不对 |
| 409 | REPLAY | nonce 重复 |
| 429 | RATE_LIMIT | 太频繁 |

## 5. 心跳

### 请求

`dev_id`、`fw`（可带，变了才更新）、`ts`、`nonce`、`sig`（用**设备密钥**签）。

### 应答 200

```json
{"ok":true,"hb":600,"server_ts":1761880600}
```

### 服务器行为

- 更新 `last_seen` / `last_hb` / `last_ip`，`hits + 1`。
- `fw` 变化 → 更新并写一条 `fw` 事件（detail 记旧版本）→ 详情页的"固件变更记录"。
- 从离线恢复 → 写一条 `online` 事件（详情页能区分"重新联网"）。
- **普通心跳不逐条入库**（一次 10 分钟 × N 台 × 365 天 = 天文数字），
  只在「注册 / 固件变更 / 恢复在线 / 异常」写事件。

### 错误码

| code | err | 含义 |
|---|---|---|
| 400 | BAD_DEV_ID / BAD_TS / BAD_NONCE | 同上 |
| 403 | BAD_SIG | 设备密钥不对 |
| 403 | DISABLED | 后台禁用该设备 |
| 403 | RESET_REQUIRED | 库里没密钥（需重新注册） |
| 404 | UNKNOWN_DEVICE | 没注册过，或已被删除 |
| 409 | REPLAY | nonce 重复 |
| 429 | RATE_LIMIT | 太频繁 |

### 离线判定

**不用设备发离线消息**。服务器只看 `last_hb`：
`last_hb >= now - online_timeout` 即在线（阈值后台可配，默认 900 秒）。
设备关机、断网、掉电都会自然变离线。

## 7. 固件端：需要做什么（本轮未实现）

### 为什么没做

1. 现有固件**零设备身份代码**，要新增 MAC 读取、NVS 存密钥、签名、上报节流、
   Wi-Fi 就绪触发 —— 属于新功能，必须真机验证（断网/换 Wi-Fi/时钟不准/重刷）。
2. 本轮约束是"不发布固件、不烧录真机"，写进去也证明不了能用。
3. 后台在 0 设备状态下的表现已按"尚未接入"处理，不阻塞网站上线。

### 实现要点（照这个做就能通）

| 项 | 做法 |
|---|---|
| MAC | `esp_wifi_get_mac(WIFI_IF_STA, mac)`；开机 Wi-Fi 初始化后取一次，缓存。**不要**用 `esp_random()` 之类生成 ID |
| dev_id | `snprintf(id,"LNT%02X%02X...", mac[0..5])`，与 §3.1 完全一致 |
| 密钥存放 | NVS：`lp_dev` 命名空间存 `secret`(string)、`proto`(u8)；产品 key 编译期常量 |
| 时钟 | 签名用 Unix 秒。**无 RTC 时先用 SNTP 对时**；对不上时 ts 会超窗 → 注册失败。兜底：失败后每小时重试一次，别死循环 |
| 上报 | 复用 `net_client`（`netc_start` 单请求槽），**不要**新建常驻任务：用已有的低频定时（或主循环里 10 分钟一次的软定时）触发，一次请求 1~3 KB |
| 时机 | Wi-Fi 拿到 IP 后 3 秒发注册（无 secret 时）或心跳（有 secret 时）；之后按应答里的 `hb` 秒 |
| 失败处理 | 429/5xx：退避（×2，上限 1 小时）；409 REPLAY：换 nonce 重发一次；403 RESET_REQUIRED：清 NVS secret 重新注册 |
| 断电 | secret 在 NVS，重启后直接用；丢了就重新注册（服务端会轮换 secret，不影响统计） |
| 功耗 | 一次上报 ~1-3 KB，10 分钟一次；不要为了心跳保持 Wi-Fi 常开（沿用现有 Wi-Fi 策略） |

### 需要改的文件（预估）

- 新增 `components/services/device_report/device_report.c/.h`（约 300 行）
- `main/main.c` 或 `wifi_manager` 的连接成功回调里挂一次触发（**不改引脚、不改任务优先级**）
- `CMakeLists.txt` / 分区表：不动

## 8. 安全说明

- 设备端**没有**后台凭据；注册用产品 key、心跳用每设备 secret。
- 签名失败不累加 `hits`（实测断言），不会被"错误请求"刷高活跃度。
- 后台页面全部 `manage_options` + nonce，普通用户 `wp_die` 拦下（实测）。
- MAC/IP 只给管理员看；后台页脚与本文档都写明采集目的与保留期。
- 删除是**逻辑删除**（`deleted_at`），历史事件保留；超过保留期才物理清除。
- 不存在"用公开设备 ID 查别人隐私"的接口：没有任何公开查询接口。
- SQL 全部 `$wpdb->prepare`；注入串实测 0 命中。

## 9. 已知限制

1. **在线趋势不是真快照**：没有历史快照表，折线是"按最后心跳日聚合的去重设备数"，
   页面上已写明口径。真要精确曲线，需要每天定时落一次快照（下一轮可加）。
2. `secret` 以明文存库（HMAC 校验必须拿到原值）。库被读走即可伪造心跳；
   缓解：只给 DB 用户最小权限、定期轮换产品 key、后台可禁用设备。
3. 心跳走 WP 引导（约 50-100 ms + 一条 DB 写），对 ESP32 无感，但服务器端成本比裸 PHP 高。
4. 固件未实现 ⇒ 现在后台一定是 0 台设备。
