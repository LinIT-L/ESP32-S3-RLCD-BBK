# LPK 单文件资源包：制作与接入指南

> **一句话**：一个 `.lpk` 装下程序（可选）+ 全部资源，设备**不解压、不散落**，按偏移直接读。
> 卡上只占 1 个文件；存档/配置照旧写真实 FAT。
>
> **本文替换并合并了**原先的《LPK 自包含资源包格式》与《仙剑 LPK 卡顿情况说明》两份文档。
> 目标读者：下一个要给某个引擎/应用做单文件资源包的人（包括 AI 助手）。
> **先读 §4（性能）**——那是唯一会让你做完发现"能跑但慢 6 倍"的章节。

| 关注点 | 结论 |
|---|---|
| 卡上文件数 | 1 个 `.lpk`（替代原 109 个散落文件） |
| 设备端解压 | **完全没有**，也不进 miniz |
| 随机读 | 支持 `fopen/fseek/fread/fclose` 全套（走 ESP-IDF VFS） |
| 存档 | 写真实 FAT，与 ZIP 模式**同一目录**，老存档零迁移 |
| 性能 | 见 §4；**不做预读窗会慢 6 倍** |
| 真机实测（仙剑 109 条 41.7 MB） | STAGE2→3 6.8 s、首帧 13.8 s（目录模式 11.8 s） |

---

## 0. 什么时候用，什么时候别用

| 场景 | 建议 |
|---|---|
| 纯 Lua 应用、无资源 | 不需要，单个 `.lua` 已经是单文件 |
| Lua 应用 + 资源（图/字/数据） | ✅ 用 LPK（**Lua 侧加载器尚未接入**，见 §11） |
| **C 引擎游戏**（仙剑 = `sdlpal_port`） | ✅ 用 LPK，引擎走 `/lpk` 的 VFS + 标准 `FILE*` |
| 资源 > 100 MB（如本地维基） | ❌ 不用。单文件随机读在 FAT 上代价过高 |
| 本身单文件（字体包、单 lua） | ❌ 不用，原本就是 1 个文件 |

## 1. 二进制格式（v1）

### 1.1 布局

```
┌──────────────────────────────┐ 0
│ HEADER (64 B)                │
├──────────────────────────────┤ 64
│ LUA ENTRY（原始字节，可空）    │  lua_off / lua_size
├──────────────────────────────┤ man_off
│ MANIFEST                     │  man_size
│   count × 32 B 记录           │
│   + 文件名池（UTF-8，无 NUL）  │
├──────────────────────────────┤ data_off（512 对齐）
│ RESOURCE DATA（原始字节）      │  每条 [off, off+size)
│   …每条 512 字节对齐…          │
└──────────────────────────────┘ total_size
```

- 全部**小端**；**无压缩、无 DEFLATE、不依赖 miniz**。
- 资源按 **512 B 对齐**：单次读不会跨扇区起头；109 条最多浪费 ~55 KB（0.13%）。
- 索引前置：打开只读头 + 索引（109 条约 22 KB），之后每个资源一次 `fseek` 就能读。
- **整个包从不被整体加载**。

### 1.2 HEADER（64 B）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | char[4] | magic | `"LPK1"` |
| 4 | u16 | version | `1` |
| 6 | u16 | hdr_size | `64` |
| 8 | u32 | flags | 保留，0 |
| 12 | u32 | lua_off | Lua 入口偏移，无则 0 |
| 16 | u32 | lua_size | Lua 入口长度，无则 0 |
| 20 | u32 | man_off | 索引偏移（= 64 或 64+lua_size） |
| 24 | u32 | man_size | 索引总长度 |
| 28 | u32 | data_off | 资源数据起始（512 对齐） |
| 32 | u32 | count | 资源条数 |
| 36 | u32 | total_size | 整包字节数 |
| 40 | u32 | pkg_crc | **整包 CRC32，计算时把 [40,44) 视为 0** |
| 44 | u8[20] | reserved | 0 |

### 1.3 ENTRY（32 B，位于 man_off）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u32 | off（**相对 data_off**） |
| 4 | u32 | size |
| 8 | u32 | crc32 |
| 12 | u16 | name_off（相对文件名池） |
| 14 | u16 | name_len |
| 16 | u8[16] | reserved |

### 1.4 路径规则（两端同一套：`lpk_path_ok`）

- 只允许 `/` 分隔，禁止 `\`。
- 禁止绝对路径（首字符 `/`）、禁止 `..` 与 `.` 段、禁止 `//`。
- 禁止以 `/` 结尾（那是目录，包里只有文件）。
- 长度 ≤ `LPK_MAX_NAME`。
- **大小写**：查找先精确匹配，未命中再做 ASCII 折叠匹配；折叠后命中多条 → `LPK_E_AMBIG`（歧义即拒绝，不猜）。

### 1.5 打开时的校验（任一不过 → 安全拒绝并关句柄）

`magic` / `version` / `hdr_size` / `total_size == 实际文件大小` / 索引与文件名池边界 /
每条 `[off, off+size)` 落在 `data_off..total_size` 内 / `off` 512 对齐 /
偏移单调不减 / 无重复路径 / 无大小写冲突。

> 重复路径与大小写冲突在 `lpk_open` 就整体拒绝（O(n log n) 折叠名排序扫描），
> 不是"用到才懒判"——坏包必须在挂载时就死掉。

## 2. 打包（`tools/pack_lpk.py`）

```bash
# 纯资源包（C 引擎游戏，最常见）
python3 tools/pack_lpk.py --zip pal_stored.zip -o dist/lpk/pal.lpk --name pal

# Lua 应用 + 资源（主程序作为入口）
python3 tools/pack_lpk.py --lua app.lua --assets ./res -o dist/app.lpk --name demo

# 从目录打包
python3 tools/pack_lpk.py --assets ./gametree -o out.lpk --name game

# 检查 / 逐条 CRC 校验 / 解包到主机（仅调试，设备端永不解包）
python3 tools/pack_lpk.py --inspect out.lpk
python3 tools/pack_lpk.py --verify  out.lpk
python3 tools/pack_lpk.py --extract out.lpk --to /tmp/x
```

### 打包纪律（这几条被真实事故验证过）

| 规则 | 原因 |
|---|---|
| `--zip` 只接受 **stored**（method=0）条目；遇到 deflate **直接拒绝** | 设备端不引入 miniz，进了压缩包等于坏了 |
| 默认排除表丢弃 `manifest.json / Thumbs.db / .DS_Store / *.tmp / *.part / *.bak` | 这些是下载器/系统残留，进包会污染资源清单 |
| 同名、大小写冲突、非法路径 → **直接报错退出** | 生成不出来好过生成一个打不开的包 |
| 文件名里的 `\` 被转成 `/` 时**必须打印告警** | 在 macOS/Linux 上 `\` 是合法字符，静默改名等于偷偷换了资源名 |
| 不修改源 ZIP | 源包是可复现的基准 |

仙剑正式包（可复现）：

```
109 条 / 43,750,912 B / pkg_crc = 40973b8f
源 zip = 商店 pkgs/pal.zip（43,729,607 B / crc deec847b）
```

## 3. 设备端接入

### 3.1 组件结构

```
components/services/lpk/
├── lpk1.c          格式读取器（纯 C，宿主机同源单测，零 ESP 依赖）
├── lpk_mount.c     读写分流挂载层（纯 C，句柄表 + 预读窗）
├── lpk_vfs.c       ESP-IDF VFS 适配 + 真机自检（lpkv/lpkstat）
├── lpk_mode.c      安装模式判定（lpk / zip / none）
└── include/        对应头文件
```

`lpk1.c` / `lpk_mount.c` **不依赖 ESP-IDF**，所以分流规则和格式校验能在 PC 上完整单测。
`lpk_vfs.c` 才碰 VFS / PSRAM / 日志。

### 3.2 VFS 挂载：两个必须知道的坑

**① 挂载点只能是短路径 `/lpk`**
`is_path_prefix_valid()` 要求 2..15 字符、`/` 开头、不以 `/` 结尾。
`/sdcard/apps/app/pal` 有 20 字符 ⇒ **挂不上去**。所以挂 `/lpk`，真实路径另存。

**② VFS 会先剥掉挂载点，回调收到的是 `/ABC.MKF` 而不是 `/lpk/ABC.MKF`**
`vfs_calls.c` 在调用 FS 前先跑 `translate_path()`。
按后者写：**编译完全正常，运行时每个 open 都 EINVAL**。这个坑无法在编译期发现。

```c
static const char *strip_mnt(const char *path) {   /* 剥完是空串 = 挂载根 */
    if (!path) return NULL;
    size_t n = strlen(LPK_VFS_MNT);                 /* "/lpk" */
    if (strncmp(path, LPK_VFS_MNT, n) != 0) return NULL;
    const char *p = path + n;
    while (*p == '/') p++;
    return p;
}
```

### 3.3 读写分流：三条规则，没有例外

| 类型 | 走哪里 |
|---|---|
| 显式登记的可写路径（`save/`、`sdlpal.cfg`、`screenshot/`） | **只走真实 FAT**（读写都走，否则读不到自己写的东西） |
| 其余（= 游戏资源） | **只从 LPK 读**；任何写意图 → `LPK_E_ROFS` |
| 两边都不命中 | `LPK_E_NOENT`，**不跨类回退到 FAT** |

> 第三条是血泪：如果"包里没有就回退到盘上"，卡上一个残留的同名文件会顶掉包内资源，
> 表现为"资源莫名其妙变了"，极难排查。

### 3.4 引擎侧路径改写：用平台钩子，不动 third_party

SDLPal 提供了 `PAL_HAS_PLATFORM_SPECIFIC_UTILS` 这个上游口子。
在自有 `pal_platform.c` 里实现 `UTIL_Platform_Init()`，**在 `PAL_LoadConfig()` 之后**
把 `pszGamePath` 改成 `/lpk`：

```
时序必须是： SDL_Init → PAL_LoadConfig(TRUE) → UTIL_Platform_Init → PAL_Init
```

**提前改会被配置文件里的 `GamePath=` 覆盖**；只改 LPK 模式，ZIP 模式原样。
配置里残留的 `GamePath=/lpk` 在 ZIP 模式下会被改回来。

**存档/配置/截图两种模式都写同一个真实 FAT 目录** ⇒ 换模式、换包、升级固件都不丢存档。

⚠ 还有一个隐藏点：**包里没有目录条目**。引擎会 `stat("<GamePath>/music")` 判断有没有音乐。
必须补"有子文件即目录"的推断，否则判成"没有音乐" ⇒ 切音效模式 ⇒ **画面正常但音乐没了**。

### 3.5 生命周期：卸载必须在 `sd_remount()` 之后

真机实测：强杀游戏任务后 `fclose()` 会去拿 FatFs 卷锁，而锁被刚删除的任务带走
⇒ **卸载卡 10 秒**。正确顺序：

```
停音频 → 停游戏任务 → sd_remount()（重置卷与锁）→ lpk_vfs_unmount() → 释放
```

❌ 不要把 `lpk_vfs_unmount()` 放在 `sd_remount()` 之前，也不要在还有活跃读取句柄时卸载。

## 4. ⚡ 性能：单文件为什么慢，怎么治（最重要）

### 4.1 真机现象与对照（同一台机器、同一张卡、同一批资源）

| 模式 | STAGE 2→3（载入资源主体） | 首帧 |
|---|---|---|
| 目录模式（109 个小文件） | 6.5 s | **11.8 s** |
| LPK 单文件，无预读 | **37.5 s** | 40 s 内 0 帧 |
| LPK + 4 × 64 KB 预读窗 | **6.8 s** | **13.8 s** |
| LPK + 4 × 128 KB 预读窗 | 6.9 s | ≈13.8 s |

SD 裸读基准：4 KB / 16 KB / 64 KB / 256 KB 分块**都是 ~430 KB/s**（与块大小无关）。

### 4.2 根因：引擎的读法 × FAT 簇链

引擎（`palcommon.c`）每读一个 chunk 的序列是：

```c
fseek(fp, 4 * chunkNum, SEEK_SET);   // ① 跳回索引区（文件头附近）
fread(&offset, 4, 1, fp);            //   读 8 字节
fseek(fp, offset, SEEK_SET);         // ② 跳去数据区（可能几 MB 远）
fread(buffer, 1, chunkLen, fp);      //   读一个 chunk（几 KB）
```

**每读一个 chunk 就在「索引区 ↔ 数据区」跨整个文件来回跳两次。**

- 目录模式：每个 MKF 只有几十~几百簇，跳一次走几步就到。
- 单文件：41.7 MB ÷ 4 KB 扇区 ≈ **1300+ 簇**，每次跳都要沿 FAT 簇链走一遍。

⇒ 同样的数据量（实测载入只读 **1697 KB**），耗时差 **5.7 倍**。**这不是数据量问题，是寻道开销。**

> `CONFIG_FATFS_SECTOR_4096=y`、`CONFIG_FATFS_USE_FASTSEEK` 未开。
> 开 FASTSEEK 需要应用层构造 clmt，而 ESP-IDF 的 FATFS VFS 不暴露该 API——所以走应用层缓存。

### 4.3 两个**错误**方案（都真机验证过，别重蹈）

| 方案 | 为什么错 |
|---|---|
| **整资源预载**：open 时把整个 MKF 读进 PSRAM | ① 一次读 1.5 MB 要 3.5 s；② 当时全程持全局锁 ⇒ 游戏和音频一起堵死，**40 秒 0 帧、全程没声音** |
| **单窗口预读**（每句柄 1 个 256 KB 窗） | 引擎在索引区/数据区来回跳，**每次跳都重建窗** ⇒ 每个 chunk 多读 512 KB，比不预读还慢 |

### 4.4 正确方案：每句柄 4 个 64 KB 预读窗 + LRU

```
命中任一窗：   直接 memcpy，一次都不碰 SD
未命中且请求 < 一窗：  从当前位置顺序读一整窗（64 KB），淘汰最久未用的那个
请求 ≥ 一窗 / 无窗：  逐次直读（兜底）
```

- **4 个窗**正好容纳「索引窗常驻 + 数据窗跟着 chunk 走」，来回跳都能命中。
- 窗口大小依据：索引项 4 B/条 ⇒ 64 KB 覆盖 16384 个 chunk；数据 chunk 平均几 KB ⇒ 一窗覆盖多个连续 chunk。
- **内存全部来自 PSRAM**：256 KB/句柄，总预算 4 MB；PSRAM 分配失败 **就退化为直读**，
  **绝不回落内部 RAM**（内部只剩 ~100 KB，吃光会直接把系统打死）。
- 实测：读卡次数 13584 → **7030**（128 KB 窗），载入期实际读取量仅 **1697 KB**，无带宽浪费。

### 4.5 剩余 2 秒差在哪（诚实交代）

LPK 13.8 s vs 目录 11.8 s，差约 2 s，分布在：

1. **STAGE 1 前**：挂载 + 读 22 KB 索引表 + `esp_vfs_register`（约 1 s）
2. **STAGE 5 → 首帧**：音乐预渲染路径（约 1 s）

都可以再压，但收益递减；先保证正确性。

### 4.6 对照开关（现场随时可切）

```bash
lpkstat          # 看挂载状态 / 读卡次数 / 字节 / 毫秒 / 实际吞吐 / 预读窗占用
lpkstat 0        # 关预读窗（回到逐次直读，用于 A/B 对照）；0 会立刻归还 PSRAM
lpkstat 1        # 重新开启
lpkstat r        # 计数清零
sdb 4            # SD 裸读基准（内部 DMA 缓冲 / PSRAM 缓冲两种都测）
```

> ⚠ `sdb` 必须两种缓冲都测：IDF 的 `sdmmc_read_sectors()` 只在缓冲**可直接 DMA** 时走单次 DMA，
> 否则每次都要临时分配 DMA 缓冲再拷贝。**用 PSRAM 缓冲测出来的 430 KB/s 是低估的。**

## 5. 三种安装模式共存

### 5.1 唯一权威：`.install_mode`

目录 `<target>/.install_mode`，内容 `lpk` 或 `zip`。
商店安装器写入（`lpkmode <dir> lpk|zip` 是同一条路径）。

### 5.2 判定表（`lpk_mode.c`，判定失败**不删任何东西**）

| 记录 | 包 | 目录 | 结果 |
|---|---|---|---|
| lpk | 有效 | — | LPK |
| lpk | 坏 | 完整 | 回落 ZIP（不删包、不删存档） |
| lpk | 坏 | 不完整 | NONE（明确报错，不误启动） |
| zip | — | 完整 | ZIP |
| zip | 有效 | 不完整 | 允许回落 LPK（按既定规则） |
| 无 | — | 完整 | ZIP（旧安装兼容，目录优先） |
| 无 | 有效 | 无 | 按兼容策略 |
| 无 | 坏 | 不完整 | NONE |

⛔ 判定**不看**「目录里有没有某个临时文件」「有没有残留子目录」。
判定失败只回落 + 打日志。

### 5.3 商店 `type=lpk`

- `index.json` 里 `type` 取 `asset`（ZIP 解包）或 `lpk`（单文件）。
- 固件用 `am_pkg_is_res()` / `am_pkg_is_lpk()` 统一判定，**上层不要各写一遍 `strcmp`**。
- LPK 下载 = **下载即安装**：落盘到 `<target>/<stem>.lpk` → 验包（头/索引/必备资源）→
  写 `.installed` / `.pkg.lst` / `.install_mode=lpk`。**没有解压阶段**，进度条 0–96% 下载、末尾验包到 100%。
- 验包不过 → **删掉刚下的文件并报"安装失败"**，不留"看起来装好了"的状态。
- 卸载时**必须清 `.install_mode`**，否则下次启动仍按 lpk 找包 → 判定 NONE。

## 6. 串口自检

```bash
lpkmode                          # 当前模式 / 包内条数 / 判定原因
lpkmode /sdcard/apps/app/pal lpk # 写安装记录（= 商店安装器调的那一条）
lpkv                             # 挂载 + VFS 全通路 PASS/FAIL
lpkv /sdcard/apps/app/pal/pal.lpk /sdcard/apps/app/pal c   # c = 逐条 CRC
lpkstat [0|1|r]                  # I/O 与预读窗状态（见 §4.6）
```

`lpkv` 覆盖：挂载状态 / ABC·GOP·FBP 的索引与随机块 / 资源写打开必须失败 /
`save/` 写入回读并核对真实 FAT / 16 句柄全开且第 17 个安全失败 / `../` 与 `//` 被拒。
所有缓冲动态申请、及时释放；失败不会重启、不碰真实存档。

## 7. 内存账（2026-11-01 构建实测）

### 7.1 运行期（只有 LPK 模式才分配，退出全还）

| 项 | 大小 | 位置 | 何时释放 |
|---|---|---|---|
| 条目表（109 × 200 B） | ~21 KB | **PSRAM**（失败降级内部） | unmount |
| 挂载体 `lpk_mnt_t`（16 句柄槽） | ~4.9 KB | **PSRAM** | unmount |
| **预读窗** | 64 KB × 4 × 句柄数（≤4 MB） | **PSRAM，失败即退化直读，不占内部** | close / unmount |
| 模式判定临时表 | ~21 KB | PSRAM，判完立即 free | — |
| 索引读取临时块 | ~4.7 KB | 内部 RAM（函数内即放） | `lpk_open` 返回前 |
| LPK 整体 | **从不加载** | — | — |

每句柄另外还有一个 newlib `FILE`（约 1 KB 内部 RAM）+ 一个 FatFs 句柄；16 句柄峰值约 16 KB。

### 7.2 静态（`xtensa-esp-elf-size` 各 .o）

| 目标 | text | data | bss |
|---|---|---|---|
| `lpk1.o` | ~9 KB | — | — |
| `lpk_mount.o` | ~5 KB | — | ~0.5 KB |
| `lpk_vfs.o` | ~7 KB | — | ~0.5 KB |
| `lpk_mode.o` | ~3 KB | — | — |

### 7.3 整机（`idf.py size`）

```
Flash Code 2,796,912 B / Flash Data 1,219,964 B
DIRAM 178,600 / 341,760 = 52.3%（余 163,160）
```

## 9. 踩过的坑（逐条，别再踩）

1. **接入点不是 `SDL_RWFromFile`**。仙剑的资源主通道是 `FILE*`（`palcommon.c`），
   `SDL_RWFromFile` 只给图标和已关的 midi 用。接入点必须是 **ESP-IDF VFS**。
2. **VFS 会剥掉挂载点**，回调收到 `/ABC.MKF`。按 `/lpk/ABC.MKF` 写：编译正常，运行时全 EINVAL。
3. **挂载点 ≤15 字符**，应用目录路径太长 ⇒ 只能挂 `/lpk`。
4. **包里没有目录条目**：`stat("<GamePath>/music")` 必须靠"有子文件即目录"推断，
   否则判成没音乐 ⇒ 切音效模式 ⇒ 画面正常但音乐没了。
5. **整资源预载 + 持全局锁 = 40 秒 0 帧、全程没声音**（把游戏和音频一起堵死）。
6. **单窗口预读比不预读更慢**（引擎索引区/数据区来回跳，每次都重建窗）。
7. **卸载放在 `sd_remount()` 之前 = 卡 10 秒**（强杀任务的 FatFs 卷锁）。
8. **`lpk_open` 里重复路径/大小写冲突要在打开时整体拒绝**，不能"用到才懒判"。
9. **原子 CAS 分配句柄槽后，失败路径必须先 return 再占槽**，否则 16 个槽会慢慢漏完，
   之后所有 open 都报 NOMEM。
10. **打包器把文件名里的 `\` 改成 `/` 必须告警**，不能静默改资源名。
11. **`sdb` 基准要用内部 DMA 缓冲测**，用 PSRAM 缓冲会落进 IDF 的"临时 DMA 缓冲+拷贝"慢分支。
12. **全量烧 16 MB 镜像会清 NVS** ⇒ WiFi 凭据和音量（可能被存成 0）一起没。
    只更新固件时烧 `0x60000` app 分区即可。

## 10. 给新引擎/新应用接 LPK 的 checklist

- [ ] 确认它读文件的真实接口：`FILE*` / `open` / `SDL_RW` / 自己的封装？
      **看实际调用点，不要按名字猜。** 只有 `FILE*`/`open` 这条能直接吃 VFS。
- [ ] 确认它需要哪些目录操作：`stat` / `access` / `opendir` / `mkdir` / `rename`。
      VFS 只实现到用到的程度，**目录遍历要单独确认**（LPK 现在不实现 `readdir`）。
- [ ] 列出**必须写入**的路径（存档 / 配置 / 截图 / 缓存），登记成可写路径。
      只登记真正需要的，别扩大范围。
- [ ] 找上游的"平台钩子"改资源根目录（不要改 third_party）。确认时序：
      在配置文件加载**之后**、资源初始化**之前**。
- [ ] 打包：`--inspect` 看条数和路径；`--verify` 逐条 CRC；有真实 zip 就跑 `verify_pack.py` 对照。
- [ ] 主机测试接入 `tests/lpk/run_all.sh`（至少加一段"真实资源访问顺序"）。
- [ ] 真机：`lpkv` 全通路 → `lpkv ... c` 逐条 CRC → 进游戏掐表 → `lpkstat` 看读卡次数与吞吐。
- [ ] **性能不达标先看 §4**：是不是没开预读窗 / 窗口太小 / 引擎读法不是顺序的。
