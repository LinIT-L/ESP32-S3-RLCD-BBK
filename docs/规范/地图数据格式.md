# 地图数据格式（.ltm v3）

设备端只读 TF 卡 `/sdcard/Map/`，索引从 `https://bbk.linit.cn/bbk/maps.json` 拉。  
`.ltm` 是矢量折线容器，**小端**，与 Lua `string.unpack` 逐字节对齐。

读写实现：`tools/mapgen/ltm_read.py` / `ltm_write.py`（往返自测通过）。

## 头（64 B）

| 偏移 | 类型     | 字段                                                       |
| -- | ------ | -------------------------------------------------------- |
| 0  | `4s`   | magic `LTM1`                                             |
| 4  | `B`    | ver（当前 3）                                                |
| 5  | `B`    | layer（1=道路 / 2=等高 / 3=POI）                               |
| 6  | `H`    | nlod                                                     |
| 8  | `4×i4` | minlat, minlon, maxlat, maxlon（1e-6°）                    |
| 24 | `8×I`  | off_lod, off_feat, off_pt, off_str, npt, nfeat, crc, rsv |
| 56 | `I`    | off_idx                                                  |
| 60 | `I`    | 保留                                                       |

## LOD 表（每条 20 B）

`cmax(B) w(B) zmin(H) f0(I) f1(I)`，后 2 字节保留。

- `zmin` 是这条 LOD 生效的最小 zoom，档位 0 / 13 / 14 / 15 / 17
- `f0..f1` 指定该档使用要素表里的哪一段

## 要素表（每条 24 B，按 `cls` 升序）

`cls(B) npts(B) noff(H) poff(I)` + `bbox(4×i4)`

- `bbox` 是相对文件 `min` 的偏移，单位 1e-6°
- `poff` 指向点段起点（相对 `off_pt`）

## 点段

每条折线：

1. 首点 `i4 lat` + `i4 lon`（相对文件 min，1e-6°）
2. 后续点用 **i2 增量**，按 8 / 4 / 2 / 1 分批：剩余 ≥8 就一次读 8 对，否则 4/2/1

增量累计可还原绝对坐标，单点最大跳变需控制在 ±0.0327°（i2 × 1e-6）。

## 参考量级（示例区域 15×15.6 km 实测）

| 内容               | 体积     |
| ---------------- | ------ |
| 道路               | 161 KB |
| 等高线              | 120 KB |
| 同一份数据覆盖全部 zoom 档 | —      |

对比预渲染位图瓦片：z15 单档就要 52 MB。

## 省级包：1 个 `.bin` + 1 个 `.json`（不是一瓦片一文件）

| 方案 | 为什么不行 |
|---|---|
| 一个 `.ltm` 装整省 | 18 MB，而 `app.fs.read` 上限 **512 KB** ⇒ 根本读不进来 |
| 一瓦片一个 `.ltm` | 福建 = 607 路块 + 564 标块 = **1171 个 HTTP 请求**，每个都要重来一遍 TLS 握手 |
| ✅ 块平铺进一个 `.bin` + 索引 | 一次请求下完整个省；设备端 `app.fs.read_at(bin, off, size)` 只读当前视口那几块 |

产物（`tools/map_prov.py`）：

```
fj.json   索引: 顶层标量 + tiles:[{x,y,o,s,po,ps}]   (一行一块, 道路与地标共用网格键)
fj.bin    [省级概览][地标块...][道路块...]  —— 顺序平铺, 偏移写在 json 里
```

设备端策略：`z <= ztile-1`（默认 10）用概览；`z >= ztile`（11）按视口读块（±1 块边距）。

福建实测（源 46.5 MB `.osm.pbf`，671 万 node / 45 万 way）：解析 13 s → 产出 18.0 MB
（概览 605 KB + 610 路块 + 564 地标块），索引 46.7 KB，**下载 1 次请求**。

### 三个把体积压下来的优化（都是必须，不是可选）

1. **同名 way 溶解**：体积大头是要素表 24 B/条，而 OSM 把一条国道打成几百段。
   先按同名同级串接；**无名路走 strict**（只在"共享端点恰好连 2 条"时接）——
   只做同名时 46 065 → 24 172，加 strict 才降到 13 110（多数干道压根没名字）。
2. **概览层降级**：`--ovcls 0`（只高速/国道）384 KB，`--ovcls 1`（含省道）605 KB。
   选 1 —— 384 KB 那版在福州一带只看得见 3 条高速。
3. **块缩到 0.15°**：最大块 555 KB → 364 KB（全部落进单次读上限），中位 26 → 13.8 KB。

## 空间索引段（`off_idx` 指向）

v3 = v2 + 尾部追加索引段，用头的 `off_idx`（偏移 56）定位：

```
u8  iver | u8 pad | u16 nx | u16 ny      6 B   ← 注意是 6 字节不是 4
i4  ox, oy, cw, ch                      16 B   网格原点(微度, = 文件 min) 与格尺寸
u32 nsid | u32 gcount                    8 B
u32 cell_start[nx*ny+1]                        前缀和 → 第 c 格的条目区间
u16 fid[nsid]                                  要素下标
u16 gid[gcount]                                "跨格太多"的长要素，每帧都扫
```

**关键设计：要素只登记在 bbox 的「最小格」里，查询时把格区间向外扩 2 格。**
数学上等价于"每格都登记"，但天然不会取到重复要素 —— 否则要在 Lua 里维护一张
`nfeat` 大小的去重表（几千要素就是几百 KB）。跨格 > 3 格的（溶解后的整条国道）
进 `gid`，每帧扫一遍（它们本来就几乎总在视口里）。

格数 `nx=ny=⌈√(nfeat/3)⌉`，上限 64。**格数别小**：16×16 时 z16 只能过滤 81%，
50×50 能过滤 93%（"外扩 2 格"的开销在小格数下被放大）。

效果（每帧解表的要素数）：z16 9307 → 662（14.1×）、z10 13110 → 1035（12.7×）、
z15 11.6×、z14 4.6×、z12 2.8×、z11 2.2×（视口几乎覆盖整块，本来就没多少可过滤）。
每次解表 ≈ 0.5~1 µs ⇒ **z16 省约 6 ms/帧、z10 省约 8.5 ms/帧**。代价：文件 +5%。

### 两个坑

- **索引段偏移是 6 字节不是 4**（`<BBHH`）⇒ `ox` 在 off 6、`nsid` 在 off 22、
  `cell_start` 在 off 30。算错 2 字节 ⇒ `string.unpack` 报 `data string too short`。
- **`table.sort` 不是稳定排序**：加索引后要素遍历顺序变了，"同优先级"的标注并列名次换人，
  画面像素跟着变 —— 看起来像索引画错了，其实只是排序没定序。修法：`place_labels` 的排序键
  补成 `(p, y, x, s)` **全序**，`collect_road_labels` 先 `table.sort(names)`。
  **这条对任何"改变遍历顺序"的优化都成立。**

### 等价性必须逐像素验

加 `LTM_NOIDX` 开关强制退回线性扫，同数据同视口跑两遍比对帧缓冲 ——
z16/z15/z14/z12/z11/z10 六档全部逐像素一致才算过。只比"看起来一样"不算。

## 还没做的（按价值排序）

1. **几何变长编码**（单/双 delta + zigzag varint）：点表 4.37 B/点 → 估 1.5~2 B/点，全省再省约 6 MB（−30%）。解码要放 **C 侧**（`app.poly` 加"变长点串"入参变体），放 Lua 会吃掉收益。
2. **块内 bbox 用 i2**：省 4.0 MB，代价是格式多一个变体。
3. 跨块共享名字字典：全省字符串表仅 0.19 MB，**收益太小，不做**。
4. 搜索索引（POI/地址）：现在没有"找最近的加油站"这类需求，要做需单独一层。
