# 文档规范

> 目标：任何人（或 AI）拿到任务，**一屏内能看懂「是什么 / 怎么用 / 怎么验」**，不用翻代码猜。

## 1. 写法

- **只写可验证事实**。没实测的标「待确认」，⛔ 把推测写成结论。
- **结论先行**，一段一句；⛔ 讲历史与心路 —— 项目不保留过程记录，只留结论。
- 命令、路径、引脚号一律给**原文**，不写"大概/应该是"。
- 同一事实**只写一处**，其它地方引用它（`见《硬件与IO §1》`），⛔ 复制粘贴。

## 2. 每份文档必须有

| 项 | 要求 |
|---|---|
| 开头 | 一句话说清"这份文档解决什么问题" + 真相源在哪 |
| 正文 | 按任务顺序组织，不按代码结构 |
| 结尾 | 踩坑 / 已知限制 / 回滚办法 |

## 3. 交付物（发给 linit 的东西）一屏内

1. **是什么** —— 改了什么
2. **怎么用** —— 触发路径 / 命令
3. **验证命令** —— 现场能跑的自检（`remcon heap` 等）
4. **已知限制** —— 没做到的、待确认的
5. **回滚** —— 出问题怎么退

## 4. 什么时候更新

- 功能变更 **同一次改动**里更新对应文档，⛔ 攒着。
- 新增 Lua API **必须**跑 `tools/lua_api_doc.py`（自动生成 `docs/手册/API完整参考手册.md`），否则构建失败。
- 删除/合并文档时，**同一次改掉所有引用**，不留指针文件（旧指针已全部清理）。

## 5. 重大决策 → 极简 ADR

超过一天工作量、或推翻过既有方案的改动，追加一段：

```
## ADR-<日期> <标题>
背景 / 选项 / 选择 / 后果
```

## 6. 文档分层（放哪里）

```
docs/
├── README.md      唯一入口（索引 + 按任务查）
├── 手册/          六本，成体系、可通读
├── 规范/          短规范：随时对照，不通读
├── 专题/
│   ├── 应用资料/  一个应用一份
│   ├── 功能专题/  跨应用的机制
│   └── 第三方组件与许可证.md
├── 游戏优化计划/  各游戏还差什么
└── diagnostics/   临时诊断代码登记处
```

| 目录 | 放什么 | 规则 |
|---|---|---|
| `手册/` | 成体系的技术说明 | 一个主题一份主文档，别在别处复制正文 |
| `规范/` | 短规范、硬规则、格式规格 | 写代码时对照；内容长到能成体系就升格进 `手册/` |
| `专题/应用资料/` | 单个应用的实现说明 | 一个应用一份 |
| `专题/功能专题/` | 跨应用的系统机制 | 只拆真有独立机制的，不硬拆 |

判断标准：**这条结论半年后还有效吗？** 有效 → 写进手册或专题；只是"当时怎么查的" → 不落盘。

新增正式文档必须同时做两件事：在 `docs/README.md` 的索引表登记一行；本文件 §7 清单同步。

## 8. 生成文档的规则

- `API完整参考手册.md` 由 `tools/lua_api_doc.py` 从源码生成，**⛔ 手改**（下次生成会被覆盖）。
- 要改它的表述（说明文字、约定段），去改 `luat_lib_*.c` 的注释或脚本里的 `MODULE_DESC`。
- 生成器只认**代码**里的 `lua_newtable` / `lua_setfield`，注释里的示例不算数
  （2026-10-30 修过一次：注释中的 `lua_newtable(L)` 曾把 11 个顶层 API 误标成 `app.sys.*`）。
