# 下载性能与射频省电（应用商店 / 资源包）

> 适用范围：`components/services/net_client/`（唯一 HTTP 客户端）、`components/apps/pages/am_store_net.c`（商店下载编排）、
> `components/services/wifi_manager/`（射频省电策略）。
> 结论来自 ESP32-S3 真机 + 串口计时实测，不是桌面推算。

## 1. 铁律：任何下载/取数期间不许进 DTIM 省电

**规则（linit 2026-10-31 定）**：只要在下载或取数，射频必须全醒（`WIFI_PS_NONE`）；
取数结束、失败、取消、超时，都要把 hold 放掉，由系统在延迟后恢复省电。

原因（同一台设备、同一个 AP、同一个 530 KB 包，只差一个省电开关）：

| 省电状态 | 局域网 ping | 530 KB 下载 |
|---|---|---|
| `MIN_MODEM`（默认） | 丢包 12.5~37.5%，RTT 21~276 ms | 33.2 s（16 KB/s） |
| `NONE`（全醒） | 丢包 0%，RTT 7~44 ms | 12.2~14.2 s（37~43 KB/s） |

MIN_MODEM 下射频只在 DTIM 窗口醒，首包与 ACK 大量落在睡眠窗口里 → 重传 → 用户看到
「点下载一直 0%，等一会才动，还很慢」。41.7 MB 的资源包在省电状态下传到第 8 个文件就断流。

## 2. `wifi_manager_ps_hold()` 生命周期

```
netc_task 开始 ── hold(true)  ──┐  计数 0→1：立刻 esp_wifi_set_ps(NONE)
                                │
            （请求体，可能几十秒）│  期间不管有几个请求，都不会回省电
                                │
netc_task 结束 ── hold(false) ──┘  计数 1→0：启动 8 s 单次定时器
                                   8 s 内又有新请求 → hold(true) 会停表，不回省电
                                   8 s 内没有新请求 → ps_restore_cb 恢复 MIN_MODEM
```

要点：

- **引用计数**，不是布尔。多请求并发/嵌套不会算错；`hold(false)` 在计数为 0 时直接返回（幂等）。
- **延迟 8 秒**恢复：109 个文件连续下载时不会每个文件都切一次 DTIM（切模式要重新协商，
  频繁切比不切更差）；单次取数结束后也能及时省电。
- **连接事件里的兜底**：`WIFI_EVENT_STA_CONNECTED` 分支里若 `s_ps_hold > 0` 或诊断开关为真，
  **不会**把省电打开 —— 否则一次重连就把「下载期间全醒」的规则破坏掉。
- **异常退出一定释放**：`netc_task` 只有一个出口，`wifi_manager_ps_hold(false)` 放在
  `vTaskDelete(NULL)` 之前，正常/失败/取消（`s_cancel`）/超时都走同一条路。
- **防永久 hold**：计数只在 `netc_task` 里增减，且该任务必然退出（单请求槽，没有常驻循环）；
  恢复靠 esp_timer 单次定时器，回调里再判一次 `s_ps_hold > 0` 才跳过，不会误恢复。

诊断开关：串口 `wifi ps 0` 强制全醒（`s_ps_diag_off=true`，不自动恢复），`wifi ps 1` 复原。
仅用于测量/排查，**不要**在业务代码里用它代替 hold。

## 3. 吞吐天花板：TCP 接收窗口 / RTT

ESP-IDF 默认 `CONFIG_LWIP_TCP_WND_DEFAULT=5760`。单条 TCP 连接的吞吐上限是

```
吞吐 ≈ 接收窗口 / RTT
```

- RTT 22 ms：5760 / 0.022 ≈ **262 KB/s** ← 这就是「原来约 300 KB/s」的由来
- RTT 100 ms：≈ 57 KB/s
- RTT 216 ms（省电抖动的实测最大值）：≈ 27 KB/s

也就是说：**窗口 5.7 KB 时，速度完全由 RTT 抖动决定**，网络稍差就掉到 10~40 KB/s。
2026-10-31 实测到 8.5 KB/s 就是这个机制的极端表现，不是"改造把代码写慢了"。

调整（`sdkconfig` + `sdkconfig.defaults`）：

| 项 | 旧 | 新 | 作用 |
|---|---|---|---|
| `CONFIG_LWIP_TCP_WND_DEFAULT` | 5760 | **20480** | 把吞吐从"跟 RTT 走"变成"跟链路走"；20 KB 在 RTT 54 ms 下约 380 KB/s |
| `CONFIG_LWIP_TCP_RECVMBOX_SIZE` | 6 | **24** | 已收到的段能排队，不会因为应用正在写卡就立刻关窗 |
| `CONFIG_ESP_WIFI_RX_BA_WIN` | 8 | **16** | 802.11 接收块确认窗口，AP 可以连发更多帧再等确认 |

⚠ 窗口不是越大越好：`TCP_WND` 的内存来自内部 RAM 的 pbuf，按到达数据动态占用。
设备实测内部 RAM 空闲约 105 KB、最大连续块 31 KB，20 KB 窗口 + 8 KB 落盘缓冲 + mbedtls ≈ 70 KB，
留有余量；再往上加要先压别的模块。

## 4. 接收/落盘路径上的三处纯开销

1. **`esp_http_client` 的 `buffer_size`（1024 → 4096）**
   `esp_http_client_read()` 内部把单次 transport 读限制在 `buffer_size_rx`：
   `byte_to_read = min(need_read, client->buffer_size_rx)`。1024 时每 1 KB 就是一次
   select + 一次 `mbedtls_ssl_read` + 一次 memcpy —— 41.7 MB 要 4 万轮。
2. **stdio 缓冲（改为 `_IONBF`）**
   newlib 给 FATFS 流默认 1 KB 缓冲，`fwrite` 8 KB 会被拆成 8 次 `f_write`（每次 2 个扇区）。
   关掉缓冲后一次 8 KB 直接下发。
   ⛔ 不要用 `setvbuf(fp, chunk, _IOFBF, n)` 复用落盘缓冲 —— `fwrite` 的源正是 `chunk`，重叠会写坏数据。
3. **CRC32（16 项半字节表 → 256 项整字节表）**
   半字节表每字节 2 查表 + 2 移位；整字节表 1 查表 + 1 异或。41.7 MB 约 3.3 s → 1.1 s。
   这段是**边收边算**、和网络读串行，直接影响吞吐。
   等价性已验证：新旧实现在 0~300000 字节全长度 + 分段累加下逐位相同，
   且与 Python `binascii.crc32` 一致（`60946e91`）。

## 5. 保持不变的完整性设计

提速**没有**动这些：

- `.part` 临时文件 → 状态码 200 + 长度 + CRC32 三道闸门 → 才替换正式文件（旧文件全程保留，失败可回滚）
- 增量 CRC32（不重复扫全文件），校验失败一律拒绝安装
- 断点续传（已存在且 CRC 正确的文件跳过）
- 进度回调（`s_got` 每块更新，UI 侧节流到 ~0.5 s）

## 6. 怎么回归测试

```bash
# 1) Mac 侧基线（排除服务器问题）
curl -s -o /dev/null -w "%{speed_download} B/s\n" https://bbk.linit.cn/bbk/pkgs/font_fusion8.zip

# 2) 设备侧（串口）：同一文件跑 3 次取均值
#    串口命令: storedl <包名>
#    看 NETC: 请求 … 与 NETC: 成功 len=…
#    速度 = len / (成功时刻 - 请求时刻)

# 3) 并行 ping 看链路（下载中）
ping -c 20 -i 0.3 <设备IP>
```

判定标准：

- 设备侧 ≥ 150 KB/s 视为达标；≥ 300 KB/s 视为恢复原水平
- 若设备侧远低于「窗口/RTT」推算值，先查 TF 卡写入（`cp` 同一文件测）与 RSSI，再查代码
- 每次只改一个变量：先窗口，再 buffer_size，再 stdio/CRC

## 7. 踩坑记录

| 现象 | 真因 | 处置 |
|---|---|---|
| 点下载后进度 0% 停十几秒 | 省电 DTIM 睡射频，首包反复丢 | hold 在**建连之前**就切 NONE |
| 530 KB 花 33 s（16 KB/s） | 同上 + 窗口 5.7 KB | 见 §1、§3 |
| 41.7 MB 传到第 8 个文件断流 | 省电掉线重连 + 窗口过小 | 同上 |
| 同一固件测出 12 s / 62 s 巨大波动 | 窗口小 ⇒ 吞吐对 RTT 抖动极敏感 | 提高窗口，使速度与抖动解耦 |
