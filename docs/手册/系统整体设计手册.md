### 1. 架构分层（五层，物理落在目录上）

> V1.2 起分层**不再只是约定，而是目录结构 + 构建守卫**：`components/<层>/<组件>`。
> 实施记录见 `CHANGELOG.md` 的 v1.2 一节。

```
rank 5  apps/       L4 应用层   应用页（每个 .c 一页）+ theme/主题引擎 + 装配 apps_register_all()
rank 4  engines/    L3 引擎层   模拟器核心 + 引擎支撑件(board_shim/cheater/color_convert/shared_memory)
rank 3  system/     L2 系统层   os 内核(kernel/services) + input + engine_manager + app_board + bbk_boot
rank 2  services/   L1 服务层   svc_nvs/cfg/log/time · wifi · bt · usb_* · audio · tone · vibrator · keyvault · favorites · web_gamepad
rank 1  ui/         L1 UI 层    ui_common · fonts · kbd_lib · virtual_keys · wallpapers
rank 0  drivers/    L0 驱动层   st7305 · touch_panel · sd_scan · board_battery
rank 0  libs/       L0 库       calc · lua
rank 9  tools/      开发工具     self_test（不受分层约束）
```

### 2. 依赖规则

- **R1 只允许 高层 → 低层**（rank 大 → rank 小）。**同层互调允许**（如 services 内 A 用 B），
  **跨层反向禁止**（system 不得依赖 engines/apps；ui 不得依赖 services）。
- **R2 唯一 API 面**：引擎只经 `engine_api.h`、应用只经 `os_app_api.h` 访问底层能力；
  不得直接 `#include` 驱动/服务头。
- **R3 禁止循环依赖**（CMake 目标图必须无环）。跨层"回调需要"用**注入式回调**解决，
  不要反向 include —— 例：`gam4980_set_exit_confirm_cb()` 由 os 侧注入。
- R4 能力经接口契约暴露（`os_module_t` / `os_service_t` / facade），面向抽象编程。
- R5 新增 = 注册表加一行 + 实现模块（开闭原则）；C 应用用 `tools/new_app.py` 一键接线。
- R6 依赖必须**显式声明**：`REQUIRES`（对外，参与链接）/ `PRIV_REQUIRES`（仅内部）。
- R7 一个模块一个职责；R8 `.c/.h` 结伴自包含，私有 static state 留本文件。
- **R9 守卫强制**：`tools/check_deps.py` 静态校验 R1/R2/R3，**已接入构建**（违例即构建失败）。
  已知历史欠债登记在脚本的 `ALLOW_INVERSIONS` 表（当前 5 条，全是 `wallpapers → services`，
  正解是把电源/屏保部分拆出 `services/power`）。
  > ⚠ ESP-IDF 的 `REQUIRES` **只管链接顺序、不管 include 可见性**（public 头全局可见），
  > 所以"分层"必须有静态脚本兜底，光靠 CMake 管不住。

### 3. 组件规范

- 一目录一职责=静态库；`include/` 公共头；命名小写下划线、类型 `_t`。
- 尽量自包含（字体/图标随模块私有）；驱动组件不混业务资源。
- 跨模块相同代码抽共享组件单源。
- **外设单一所有权**：一个外设（I2C 口、UART、I2S、SPI 设备）只有一个组件负责初始化与持有句柄，别人用它的 API。
- **API 只增不改**：已发布函数签名/字段不改，要改就新增并保留旧符号（改了就是 ABI 事故）。
- 条件编译走 `LINTOS_ENABLE_*`：未完成功能默认 `=0`，不注册就不占 RAM。
- **新模块必须能独立验证**：给一条 `remcon` 命令或最小烧录示例，不能只靠"进某页点几下"。

### 4. 模块契约

- 页面实现 `os_module_t`(on_enter/on_exit/render/action/touch/poll)。
- 懒加载 `os_hw_request/store`；退出必须释放自己申请的资源（任务/堆/外设），不遗留后台线程。
- 全局服务 `os_register_service`（tick/render/touch 热区），不占页面栈。

#### 4.1 资源生命周期（合入门槛）

- **`init/start` 必须配对 `deinit/stop`**；无配对不得合入。
- deinit 顺序：**注销回调 → 停任务/定时器 → 关外设/射频 → 释放堆 → 归还总线/引脚**，最后指针置 NULL。
- 共享资源（I2C 总线、USB、PSRAM 池）用**引用计数**，最后一个用户释放。
- ⛔ 启动时全量初始化；高耗能模块（WiFi / BT / USB / 音频 / GPS）必须有明确开关时机。
- `esp_pm_lock` 必须配对 `release`，最小持有，⛔ 在 ISR 里操作。
- **交付必须给**：改动前后 heap / 栈高水位 / 组件 size；deinit 后 heap 应回到基线。

### 5. 事件调度

单主循环（Reactor）：统一轮询输入 → 分发 action/touch → 服务 tick+模块 poll → 统一渲染。
长时间阻塞操作（TLS/HTTP/扫描）放独立高栈 task 并保证退出回收。

### 6. 内存（ESP32-S3：IRAM 与 DRAM 共享同一块 SRAM）

**核心事实**：S3 上 IRAM（代码）与 DRAM（数据）**共享物理 SRAM**，且链接脚本用 `.dram0.dummy`
占位 IRAM 已用空间 —— 所以 **IRAM 常驻代码少 1KB，内部堆就多 1KB**；反之亦然。

- 内部 SRAM：热路径 / 性能关键（引擎热循环放 IRAM 是**有意的取舍**，别一刀切下沉）。
- PSRAM：大缓冲 / 表 / 帧缓冲 —— 用 `EXT_RAM_BSS_ATTR`（单变量）
  或**组件级** `linker.lf` + `LDFRAGMENTS`（整组件 `.bss`，见下）。
- **禁 cache 期间不可访问 PSRAM**：flash/分区写入、NVS commit、`esp_*_sleep_start`、
  `esp_bt_controller_init` 等会关 Flash+PSRAM cache。**含此类路径的静态数据必须留内部**
  （典型：`bt_ctl` 里的 bt_init 任务静态栈 → 故 `bt_ctl` 的 `.bss` **不迁 PSRAM**）。

**已实测的内部 RAM 收益（V1.2）**：

| 项 | 数值 |
|---|---|
| `apps` 组件 `.bss` 整体迁 PSRAM（`components/apps/linker.lf` + `extram_bss`） | `.dram0.bss` 58,416 → **21,544 B（−36.9 KB）** |
| 对应内部堆 | main_free ≈10.3 KB → **≈47 KB（预期，待上机复核）** |

> ⚠ 组件级迁移的**唯一坑**：`linker.lf` 不会自动发现 —— 必须在
> `idf_component_register()` 里写 `LDFRAGMENTS "linker.lf"`，否则**静默失效**（不报错、不生效）。
> 验证必须用 `readelf -SW build/LinTOS.elf | grep -E "dram0.bss|ext_ram.bss"` 看节大小是否真的转移。

##### 6.1 强制规范（所有新代码/新应用必须遵守）

> 2026-10-05 由独立文档 `内存使用强制规范.md` 并入 —— 它和 §6 讲的是同一件事（东西放哪、怎么验收），分两处看容易漏。

> 一句话：**内部 RAM 只留给"物理上不能放 PSRAM 的东西"，其余一律放 8MB PSRAM。**
> 立规依据（2026-10-02 实机事故）：蓝牙(手柄)+WiFi 同开时内部堆只剩
> `free=15171 largest=7680`，导致 **TLS 上下文（需一块连续 16KB）分配失败**，
> `esp_http_client_open` 242µs 就返回 `ESP_ERR_HTTP_CONNECT`（28674）——
> 航班雷达"取数一直失败"就是这么来的。

##### 一、为什么不能"全部丢 PSRAM"（4 条硬约束）

| # | 约束 | 后果 | 谁受影响 |
|---|---|---|---|
| 1 | **禁 cache 窗口**：写 flash / NVS commit、`esp_bt_controller_init`、进深睡(`esp_deep_sleep_start`) 期间 **PSRAM 不可访问** | 该期间只要碰到 PSRAM → `LoadProhibited`/cache 错误 | 这些路径上的**任务栈**与**数据**必须内部 RAM |
| 2 | **中断处理 / `IRAM_ATTR` 代码**不能从 PSRAM 执行 | 中断里跳 PSRAM 直接崩 | ISR、`IRAM_ATTR` 函数 |
| 3 | **部分外设 DMA 要求内部 RAM**（本项目 LCD flush 缓冲等） | DMA 数据错/不触发 | 驱动层缓冲 |
| 4 | **启动早期 PSRAM 未初始化**（`app_main` 早期、二级引导） | 访问即崩 | 启动路径代码/数据 |
| 5 | 性能：PSRAM 走 cache 且与 flash 争带宽（内部 RAM 快约 3~5×） | 每帧热路径会掉帧 | 逐帧重绘的大块数据 |

> 结论：不是"内部 RAM 不该用"，而是"**内部 RAM 必须省着用**"。

##### 二、怎么做（本仓库的具体写法）

| 场景 | 写法 |
|---|---|
| **大块静态缓冲**（≥1KB，长驻） | `EXT_RAM_BSS_ATTR static uint8_t buf[N];` —— 放 PSRAM 的 .bss |
| **大块动态分配** | `heap_caps_malloc(n, MALLOC_CAP_SPIRAM)`；失败再退回 `MALLOC_CAP_INTERNAL` 兜底 |
| **小对象 / 每帧热路径** | 普通 `malloc`（`CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=2048`，≥2KB 才会去 PSRAM） |
| **任务栈** | **默认内部 RAM**；只有"该任务绝不触碰禁 cache 路径"时才可 PSRAM 栈，**必须写注释说明为什么安全** |
| **Lua 应用的缓冲** | 桥里已经有 `EXT_RAM_BSS_ATTR` 的范例（`luat_lib_net.c` 的 16KB 响应体、`os_pane`、`AM_COL` 141KB、`s_pkg[]`），照抄 |

现成设施（不要造轮子）：
- 宏：`EXT_RAM_BSS_ATTR`（`esp_attr.h`，把 .bss 段放进 PSRAM）
- API：`heap_caps_malloc/get_free_size/get_largest_free_block(MALLOC_CAP_SPIRAM|MALLOC_CAP_INTERNAL)`
- 已开配置：`CONFIG_SPIRAM_USE_MALLOC=y` / `SPIRAM_MALLOC_ALWAYSINTERNAL=2048` /
  `SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` / `SPIRAM_MALLOC_RESERVE_INTERNAL=8192` /
  `FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y`（⚠ 能开不代表该开，栈默认仍用内部）

##### 三、验收标准（新功能合入前必须过）

1. `remcon audit` → 看 `internal free / largest`：
   - **`largest` 不得低于 8KB**（低于 8KB 就没法做 TLS/HTTPS，凡是联网应用都会挂）
   - 加完新功能后 `free` 不应比加之前下降超过 8KB（大块必须去 PSRAM）
2. 同开关状态对比（蓝牙开/关、WiFi 开/关各测一次）—— **不同状态下的数字没有可比性**。
3. 联网功能必须在"**蓝牙 + WiFi 同时开**"的最坏情况下测通（这是内部 RAM 最紧的场景）。

##### 四、已犯过 / 已修的典型

| 现象 | 根因 | 修法 |
|---|---|---|
| 联网取数一直失败，错误码 **28674** (`ESP_ERR_HTTP_CONNECT`)，且 200µs 内就失败 | mbedtls 的 TLS 收发缓冲默认 `IN_CONTENT_LEN=16384` **放在上下文里一次性 calloc**，要求一整块连续内部 RAM；BT+WiFi 同开时最大连续块只剩 7.6KB → 分配失败 | ① `CONFIG_MBEDTLS_DYNAMIC_BUFFER=y`（缓冲改为按需单独分配）② `IN_CONTENT_LEN 16384→4096`、`OUT 4096→2048` ③ `esp_http_client` 的 `buffer_size` 2048→1024 |
| 页面/应用一多就"莫名卡"或分配失败 | 大块缓冲写了 `static`（落在内部 BSS） | 改 `EXT_RAM_BSS_ATTR` |

##### 五、代码审查自查 3 问（提交前问自己）

1. 我新加的**静态数组**超过 1KB 了吗？→ 超过就必须 `EXT_RAM_BSS_ATTR`。
2. 我新加的**动态分配**会不会是 ≥2KB 的大块且长驻？→ 是就用 `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`。
3. 我的新任务会不会调用 **flash 写 / NVS commit / `esp_bt_controller_init` / 深睡**？
   → 会就必须用内部 RAM 栈；不会才可以考虑 PSRAM 栈（并写注释）。

### 7. 编码规范

函数 `xxx_yyy`、常量 `#define XXX_Y`、类型 `typedef ..._t`；
头文件顶部说明用途/依赖、`#pragma once`；
校验输入/指针/边界、状态机带超时、ISR 尽量短；中文资源为 UTF-8。

**日志纪律（V1.2 起）**：**高频上下文一律 `ESP_LOGD`**，不得用 `ESP_LOGI`。
高频上下文包括：ISR、HID 输入报告回调（手柄连着时 100+ Hz）、PCM 回调、
每帧调用的 `poll/tick/render`、`recvfrom`/`accept` 循环、2 秒级诊断心跳。
原因：一条日志经阻塞式控制台写出 ≈5 ms @115200，出现在 100 Hz 路径上就是 500 ms/s 的净损耗。
排查时用 `esp_log_level_set("TAG", ESP_LOG_DEBUG)` 临时打开。

### 9. 音频任务与 CPU 分核（2026-10-25 定案）

> 起因：仙剑接 RIX 音乐后整机死机。日志证据 `task_wdt: CPU 0: sdl_aud` / `- IDLE0 (CPU 0)`，
> 反解栈 `audio_task → AUDIO_FillBuffer → RIX_FillBuffer → CEmuopl::update → DBOPL2::adlib_getsample`。
> 结论：**音频合成不是"能算就行"，它和模拟任务抢同一个核时会把 IDLE 饿死，进而触发 TWDT 重启。**

#### 9.1 现状（全部引擎逐一核对过）

| 模块 | 执行体 | 核 | 音频在哪产生 | 结论 |
|---|---|---|---|---|
| GB / GBC (`gbc_emu`) | `gbc_emu` | **CPU1** prio 4 | **同一任务内**（`gbc_emu_feed_audio`）| ✅ 合规 |
| NES (`nes_emu`+`video_audio`) | `nes_emu` | CPU1 prio 4 | 同一任务内 | ✅ |
| SMS (`sms_emu`) | `sms_emu` | CPU1 prio 4 | 同一任务内 | ✅ |
| MD (`md_emu`+`genesis_snd`) | `md_emu` CPU1 prio 4；`genesis_snd` CPU1 prio **20** | CPU1 | 单独任务，但**按帧信号量同步**（不自由跑）| ⚠ 见 R3 |
| ArduBoy / 宠物机 | 各自单任务 | CPU1 prio 3 | 同一任务内 | ✅ |
| GAM4980 | `gam4980` | CPU1 | 同一任务内 | ✅ |
| SDLPal | `sdlpal` CPU0 prio 5；`sdl_aud` CPU1 prio 5 | 分开 | **独立任务**（SDL 回调模型决定）| ⚠ 见 R2 |
| 音频后端 | `audio_out` CPU1 prio 8；`audio_play`（MP3）CPU1 prio 1 | CPU1 | 只负责 PCM→I2S | 固定，勿改 |

#### 9.2 规则

- **R1 引擎音频合成必须在模拟任务内完成**，只把 PCM 塞进 `audio_player_feed_pcm()` 的环形缓冲。
  单独起一个"音频任务"在 ESP32-S3 上等于把同一个核切成两半，双输。
- **R2 必须独立音频任务时（SDL 回调模型）**：钉 **CPU1**、优先级 **≤ 8**（不得高于 `audio_out`），
  并且**必须带超时自保**：单次回调 > 120 ms 连续 2 次 → 关掉该模块（如音乐），保留系统。
  `sdl_audio.c` 的 `s_music_on` / `slow_hits` 就是这套兜底的样板。
- **R3 高优先级放"被信号量驱动"的任务**：`genesis_snd` prio 20 只在收到帧信号后短暂运行，
  属可接受；**但严禁**把自由跑（`while(1)` 里持续算）的任务设到 > 8，否则会饿死 `audio_out`。
- **R4 贵合成先降级再考虑移植**：OPL/MIDI 软合成在本机实测单核实时因子 < 1
  （44.1 kHz 双芯片、22.05 kHz 单芯片两种配置都跑不到实时），**不是调参能救的**。
  正解是**预渲染**（RIX→MP3/ADPCM，交给 `audio_player` 的 minimp3 解码）。

#### 9.3 怎么验证（不要靠听，靠日志）

```
remcon tasks        # 看任务名/优先级
```
`underruns` 持续增长 + `play` 远低于 `want` ⇒ 生产端供不上，先查是不是合成太重。

#### 9.4 桩函数红线（2026-10-25 血案）

SDLPal 的音频回调链是"先填、后调桩"：

```
AUDIO_FillBuffer(): memset(stream,0) → 音乐 FillBuffer(stream) → 调音量
                  → 音效混音 → AVI_FillAudioBuffer(stream)   ← 最后一步
```

因此**任何写在末端的桩都不许碰 stream**。`pal_stub.c` 里 `AVI_FillAudioBuffer` 曾写成
`memset(stream,0,len)`，结果把音乐和音效整块清零 ⇒ 表现是"合成正常、音量正常、播放器探针满幅，
但一帧声音都没有"，换了两个 OPL 核、三种采样率都查不出来。

规则：
- 空实现的桩只允许 `(void)参数;`，**禁止 memset/写缓冲区**。
- 替换/关闭某子系统时，先确认它在调用链里的**位置**（末端 vs 中段），再看它是否持有输出缓冲。
- 排查"没声音"的顺序：播放器探针（直接问）→ 完整回调探针（走链路）→ 两者不一致就去看链路里谁动了 buffer。

## 第二部分 系统架构与启动流程

> 本部分讲：启动三层结构、主循环帧预算、页面与任务、渲染送屏。

> 讲**运行时**：上电后按什么顺序初始化、主循环每圈做什么、页面和任务怎么组织。
> 分层规则、依赖约束、内存策略不在这里重复 —— 见第一部分。
> 真相源：`main/main.c`、`components/system/os/`、`components/system/app_board/`、
> `components/drivers/board_pins/board_pins.c`。

### 1 一句话架构

单个 FreeRTOS 主任务跑一个 **Reactor 主循环**：轮询输入 → 分发到当前页 → 服务 tick →
统一渲染 → 按脏状态决定下一圈等多久。重活（模拟器内核、音频合成、网络、下载）各自起任务，
用脏标记和消息回主循环，不直接画屏。

### 2 启动顺序

`app_main()`（`main/main.c:795`）严格按下面的顺序执行，**顺序本身是契约**，改动要重新评估。

**启动分三层**：`app_main()` 做完阶段 1–15 后，把剩下的全交给 `os_boot_shell()`；
`os_boot_shell()` 初始化完 OS 再进 `os_shell_loop()` 死循环。
代码位置：`app_main()` 在 `main/main.c:795`，`os_boot_shell()` 在 `:634`，`os_shell_loop()` 在 `:271`。

#### 2.1 第一层：`app_main()`

| # | 阶段 | 做什么 | 为什么必须在这个位置 |
|---|---|---|---|
| 1 | `power_mgr_wake_gate()` | 判断本次唤醒是否合法 | 手动关机唤醒要求 PWR 按住 ≥0.5s，误触直接回深睡（不返回）|
| 2 | `power_stat_init()` | 结算上次深睡时长 | 晚了会把初始化耗时算进睡眠段 |
| 3 | `svc_log_init()` | 日志缓冲 + 可选落盘 | 后面所有日志依赖它 |
| 4 | 版本横幅 | 打印对外/内部版本、构建时刻、git 描述 | 烧录后靠这一行确认设备里跑的是哪一版 |
| 5 | `svc_time_init()` | 时区 + 默认时间兜底 | 各页显示时间的前提 |
| 6 | `store_fs_mount()` | 挂 SPIFFS 到 `/store`（分区名 `apps`）| 没挂上 ⇒ 应用中心里 Lua 应用全部不可见 |
| 7 | 释放经典蓝牙内存池 | `esp_bt_controller_mem_release(CLASSIC_BT)` | S3 没有经典蓝牙，先回收再初始化，白拿内存 |
| 8 | `nvs_flash_init()` | NVS 起底（失败则 erase + 重试）| `hw_cfg` 要读写 NVS，顺序不能反 |
| 9 | `hw_cfg_init()` | 探 I2C 指纹定板型 | 决定后面所有引脚从哪张表取 |
| 10 | `espsdr_reclaim_boot()` | 决定频谱仪 64KB 采集区是否回收进堆 | 必须在堆分配铺开之前一次性决定 |
| 11 | `app_board_init()` | LCD / 触摸 / SD 启动 | 硬件就绪 |
| 12 | `settings_apply_dark()` | 面板反色 | 必须在画 Logo **之前**，否则 Logo 会被反成黑底 |
| 13 | 画 Logo 并送屏 | 先上屏，不等后续初始化 | 把黑屏从 ~656ms 压到 ~520ms |
| 14 | 触摸兜底 + `sd_wait_ready(1500)` | 等 TF 卡收尾 | 不等就会出现「存储信息全空 / 引擎读不到卡」|
| 15 | `hw_adapt_loop()`（仅未识别时）| 屏上提示、每 10s 换目标重探 | 板型没定就进系统会黑屏 |
| 16 | **`os_boot_shell(&g_lcd, &board)`** | 交给第二层，**这是 `app_main()` 的最后一句** | 全部 OS 级初始化都在里面（`main.c:966`）|

#### 2.2 第二层：`os_boot_shell()`（`main.c:634`）

按实际调用顺序，**这 8 步都在一个函数里**：

| 顺序 | 调用 | 作用 | 行号 |
|---|---|---|---|
| ① | Logo 兜底 | 仅当 `s_logo_t0_ms == 0` 时补画一次（正常路径已在阶段 13 画过）| `:639-647` |
| ② | `os_init(&ctx, lcd)` | 内核、服务、页面栈 | `:648` |
| ③ | `apps_register_all()` | 注册全部内置应用页 + 应用表（V1.2 起从 `os_init` 内部移出）| `:649` |
| ④ | `power_mgr_boot_diag()` | 复位/唤醒诊断。**放这里**是因为 USB 已重新枚举，早期日志不会丢 | `:651` |
| ⑤ | `remcon_init()` | 串口远程控制台（USB Serial/JTAG 收命令）| `:652` |
| ⑥ | `board_shim_set_lcd(lcd)` | 把主屏绑到 `board_shim`，NES/GBC/文曲星/ArduBoy 引擎的前置条件 | `:653` |
| ⑦ | `os_platform_set(&s_os_platform)` | 把音量/蓝牙/WiFi/USB 等平台能力注入 OS | `:654` |
| ⑧ | 音频 + 电池初始化 | `hw_cfg_enabled()` 门控后调 `app_board_init_audio()` / `app_board_init_battery()` | `:662-670` |

**⑧ 与 Logo 停留窗口重叠**：这两个初始化约 300ms，被特意安排进 `LOGO_HOLD_MS`（300ms）
的等待循环里（`:675`），所以用户看到的是 Logo 而不是黑屏。
早期顺序是「画完桌面 → 音频+电池 → 才进主循环」，代价是桌面已显示但按键约 300ms 无响应。

#### 2.3 第三层：`os_shell_loop()`（`main.c:271`）

`os_boot_shell()` 的最后一句 `os_shell_loop(&ctx)`（`main.c:769`）进入死循环，
`while (1)` 在 `main.c:278`，结构见 §3。**此后不再返回 `app_main()`。**

> 调试提示：每个阶段都有 `boot_ts()` 打点，串口能看到各段耗时。
> 排查「开机卡住」先看最后一个打点停在哪。

### 3 主循环

`os_shell_loop()`（`main/main.c:271`）里的 `while (1)`（`:278`），一圈做这些事（**顺序固定**）：

```
① 记圈首时刻 t0
② 屏保到点？        → do_auto_shutdown()（不返回）
③ PWR 长按 2s ？    → 先退屏保（解除 LCD 独占 + 开刷屏门禁 + 恢复触屏）再弹「关机?」
④ 屏保态？          → 只轮询物理键 → vTaskDelay(32ms) → continue（跳过一切渲染与 tick）
⑤ 刚从屏保回来？    → 作废送屏指纹 + 置脏 + 1 秒强制重绘
⑥ os_tick(ctx)      → 服务 tick + 当前模块 poll
⑦ input_get_action()→ 有按键就分发给当前页
⑧ 触摸 → 命中就交给当前页 touch()
⑨ os_render(ctx)    → 脏了才画；画完按需送屏
⑩ st7305_idle_tick()→ 有绘制回 HPM(≈32Hz)，500ms 没画掉 LPM(≈1Hz)
⑪ 周期预算：圈尾只补足到目标周期，且至少让出 2ms
```

**帧节拍是"周期预算"不是"固定延时"**：

| 状态 | 周期 |
|---|---|
| 有脏帧（拖动 / 动画 / 游戏）| **8 ms**（125 Hz，跟手）|
| 静止 | **16 ms**（上限 62 fps，与老工程一致）|
| 屏保 | 32 ms（壁纸由独立监督任务画）|

> 为什么这条重要：老写法「渲染 6~10ms 后再 delay(16ms)」实际周期 22~26ms，只有 38~45fps，
> 表现就是「左右滑动不如老版本流畅」。`remcon pace N` 可覆盖，语义是**周期**不是延时。

### 4 页面与应用

#### 4.1 一个页面 = 一个 `os_module_t`

| 字段 / 回调 | 作用 |
|---|---|
| `on_enter` / `on_exit` | 进页加载、退页全释放（任务/堆/外设都要还）|
| `render` | 只画，⛔ 不做 IO / NVS / 网络 |
| `poll` | 每帧调用，触摸轮询、动画、计时 |
| `action(a)` | 物理键 |
| `touch(ctx,x,y)` | 触摸，命中返回 true；旋转页用 `ctx->map_touch` |
| `.fullscreen` | 隐藏状态栏 |
| `.exit_confirm` | 返回键先弹「退出程序?」 |
| `.keep_on_idle` | 空闲不自动回主菜单（工具页用）|

#### 4.2 页面栈

`os_push` / `os_pop` 维护页面栈，栈顶页面独占输入与渲染。弹窗是**旁路层**，
不占页面栈（`os_dialog_depth()` 单独计数）——所以「回调里 pop」会把上层页面一起关掉，
正确做法是 `os_dialog_mark_handled(ctx)`。

#### 4.3 应用注册

内置应用分两条路：

- **上主菜单**：`s_builtin_apps[]` 加一条（名字 / 图标索引 / page_id），图标顺序即 ABI，
  新图标只能追加末尾。
- **只进应用管家**：默认 `hidden=true`。商店装的 Lua 应用走这条路，装完**永不自动启动**。

`apps_registry.c` 负责把页面注册进内核；调用点是 `os_boot_shell()` 里的 `apps_register_all()`
（`main.c:649`），全程只调一次。

#### 4.4 后台服务

`os_register_service()` 注册的服务有 `tick` / `render` / `touch` 热区，不占页面栈、没有图标。
状态栏、通知这类常驻逻辑用它；重活仍应起独立任务。

### 5 任务模型

主循环只占一个任务。其余任务按「谁需要谁起、退出就停」组织，关键约束：

| 任务类别 | 约束 | 详见 |
|---|---|---|
| 模拟器内核 | CPU1，prio 3~4，**音频合成在同一任务内** | 第一部分 §9 |
| 音频输出 `audio_out` | CPU1，prio 8，固定 | 同上 |
| 网络 / 下载 | 独立高栈任务，必须可退出回收 | 第四部分 |
| 屏保监督 | 独立任务，屏保期间独占送屏 | 本文 §3 ④ |
| TF 卡挂载 | `app_board` 内的异步任务，进桌面前由 `sd_wait_ready` 收口 | `main.c:929` |

⛔ 不要在 `render` / `poll` 里阻塞；慢操作放后台，完成后置脏标记。

### 6 事件分发

```
物理键 ──┐
触摸   ──┼→ input 层（去抖 / 长按 / 手势 / 旋转映射）→ 主循环 → 当前页 action/touch
手柄   ──┤                                              ↘ 弹窗层优先消费
USB HID ─┘
```

- 按键动作码 `1=UP 2=DOWN 3=LEFT 4=RIGHT 5=CONFIRM 6=BACK 7=HOME`，与 `os_action_t` 用
  `_Static_assert` 钉死。Lua 侧 `app.UP..app.HOME` 一一对应。
- 手势返回（底部上滑）由 `gesture_back` 模块统一管控，开关随 `os_push/os_pop` 联动。

### 7 渲染与送屏

- 绘制进 framebuffer（1bpp，400×300 = 15000 字节），脏区合并后整帧送屏。
- 面板有空闲降档：有绘制回 HPM（≈32Hz），连续 500ms 无绘制掉 LPM（≈1Hz）。
- 送屏是**异步**的（与绘制重叠），整帧 15000B 在 40MHz 下约 3ms。
- 屏保期间所有 flush 被门禁丢弃（`st7305_set_flush_blocked`），壁纸走旁路 `flush_override`。

## 第三部分 文件系统与分区

> 本部分讲：Flash 布局、挂载点、路径约定、空间限制、恢复。

> 讲清 Flash 怎么切、哪个路径落在哪块介质、空间有多少、坏了怎么恢复。
> 真相源：`partitions.csv`、`main/lua_launch.c`、`components/drivers/sd_scan/`、
> `components/ui/fonts/font_part.h`、`merge_flash.sh`。

### 1 Flash 布局（16 MB）

| 分区 | 类型 | 偏移 | 大小 | 用途 |
|---|---|---|---|---|
| （bootloader）| — | `0x0` | 32 KB | 二级引导 |
| `nvs` | data/nvs | `0x10000` | 256 KB | 设置 / 凭据 / 板型 / 玩家档案 / 应用隐藏标记 |
| `phy_init` | data/phy | `0x50000` | 4 KB | RF 校准，**保留不动** |
| `factory` | app/factory | `0x60000` | 5 MB | 系统固件（内核 / 驱动 / 模拟器 / 页面）|
| `appdata` | data/0x40（raw）| `0x560000` | 6.625 MB | 统一数据区，**永不擦写**；字库从 `+0x400000` 起按槽 mmap |
| `apps` | data/spiffs | `0xC00000` | 4 MB | 应用安装区（SPIFFS）。固定开销约 360 KB，**可用约 3.65 MB** |

- 整片镜像 `dist/merged_16mb.bin` 从 `0x0` 写；只改固件写 `0x60000`；只改 Lua 写 `0xC00000`。
- 改 `partitions.csv` 后不需要改 `merge_flash.sh` / `tools/sync_apps.py` —— 两者按表自动解析偏移。

**`appdata` 内部布局**（`font_part.h`）：

| 槽 | 偏移 | 内容 |
|---|---|---|
| — | `appdata + 0x000000` | 保留 |
| 槽 1 | `appdata + 0x400000` | `font_zh.bin`（粗体 24px，槽 512 KB）|
| 其余槽 | 依次 | 其它字库，见 `font_part.h` |

> 字库用 `esp_partition_mmap` 只读映射（XIP），所以**不占 RAM**；
> base 平移是安全的，按 label 相对定位，不要写死绝对地址。

### 2 两个挂载点

| 挂载点 | 介质 | 文件系统 | 何时挂 | 代码 |
|---|---|---|---|---|
| `/store` | Flash `apps` 分区 | SPIFFS | 开机 `store_fs_mount()`（约 40ms）| `main/lua_launch.c:54-59` |
| `/sdcard` | microSD（SDMMC 1-bit）| FAT | `app_board` 异步任务，进桌面前由 `sd_wait_ready(1500)` 收口 | `sd_scan.c:109,739` |

⚠ **`/store` 挂载失败 = 应用中心里所有内置 Lua 应用不可见**（不是"没装"，是没挂上）。
历史上就是因为挂载藏在被注释掉的冒烟测试里，导致 `/store` 从未挂载。排查先看开机日志有没有
`SPIFFS /store 挂载` 这一行。

### 3 路径约定

| 路径 | 内容 | 谁写 |
|---|---|---|
| `/store/apps/{cat}/x.lua` | 从商店装到内置存储的 Lua 应用 | `am_store.c:680-686` |
| `/sdcard/apps/{cat}/x.lua` | 装到 TF 卡的应用 | 同上（`pref=1` 分支）|

`cat → 目录` 映射：游戏 → `app`，运维 / 工具 → `ops`，其余 → `app`。

### 4 NVS

NVS 的命名空间与"谁拥有"见独立文档 **第五部分**，本文不重复。
三条硬规则复述：

1. 一个命名空间只有一个主人，别人要读走主人的 API。
2. 写 NVS 会关 flash cache，**禁止在 `render` / `poll` / 循环里写**。
3. Lua 侧 `app.nvs` / `app.db` 有 1 秒节流，窗口内断电会丢最后一次写。

### 5 空间限制

| 介质 | 容量 | 约束 |
|---|---|---|
| `factory` | 5 MB | 实测固件约 3.7~3.9 MB，余量约 25%。超了构建直接失败 |
| `apps`（SPIFFS）| 4 MB | 可用约 3.65 MB；SPIFFS 固定开销 360 KB 不可用于文件 |
| `appdata` | 6.625 MB | 字库占前 4 MB 之后的部分，其余可扩 |
| TF 卡 | 取决于卡 | FAT，单文件受 FAT32 4 GB 限制 |

> ⚠ 下载前**没有剩余空间预检**（见 第四部分 §9）。
> 装大资源包（pal.zip 约 32 MB）前先确认识别到 TF 卡且空间足够。

### 6 数据清理与恢复

| 症状 | 做法 | 影响 |
|---|---|---|
| 设置错乱 / 想恢复出厂设置 | 整片重烧 `0x0`（`merged_16mb.bin`）| 清 `nvs` + `apps`，**`appdata` 也会被覆盖** |
| 只清设置，保留应用 | `esptool erase_region 0x10000 0x40000` | 板型/凭据/隐藏标记全丢，下次开机会重新识别板型 |
| 应用装乱了 | 应用中心逐个卸载，或 `erase_region 0xC00000 0x400000` | SPIFFS 全清，`/store` 变空 |
| 换板后黑屏 | 设置 → 硬件管理 → 重新自检（清 NVS 里的板型）| 会重新探 I2C 指纹 |

⛔ **不要 erase `appdata`**（`0x560000`，6.6 MB）：字库在那，擦了要重新 `merge_flash.sh` 才有。

### 7 常见陷阱

- **深睡 hold SD 引脚**：进深睡前 hold 了 CLK/CMD/D0，开机必须 `gpio_hold_dis`，否则认不到卡
  （只能断电恢复）。
- **挂载前扫目录会"记住没卡"**：`opendir("/sdcard")` 拿到空列表后不再重扫，
  所以消费者必须等 `sd_wait_ready()`。
- **`app.fs.exists("/sdcard")` 对挂载点本身会失败**：VFS 把挂载点解析成空路径，
  判断卡在不在要用别的办法（`luat_lib_fs.c:15-16`）。
- **`opendir("/store")` 会同时吐出 `apps`、`apps/app`、`apps/app/x.lua`**：
  扫应用列表时要自己过滤层级（`am_store.c:187`）。

## 第四部分 应用中心与安装

> 本部分讲：索引格式、下载、校验、安装、更新、卸载、打包。

> 这份文档讲清「商店列表从哪来 → 怎么下载 → 怎么校验 → 装到哪 → 怎么更新/卸载」。
> 真相源：`components/apps/pages/am_store.c`、`am_store_net.c`、`am_store_json.c`、`am_asset.c`、
> `components/services/net_client/net_client.c`、`tools/pack_app.py`、`tools/sync_apps.py`。
> 本文所有结论都标注了源码位置；标「待核实」的表示源码不足以证明，需要真机或服务端确认。
> **引用约定**：定位以函数名 / 变量名 / 宏名为准，行号只是辅助 —— 源码在持续修改，行号会漂移。

### 1 三个概念先分清

| 概念 | 是什么 | 存放位置 |
|---|---|---|
| **Lua 应用包** | 单个 `.lua` 文件，头部带 `--@app` 元信息 | 设备 SPIFFS `/store/apps/{cat}/`；商店源在 `/store/` 或 `/sdcard/store_pkg/` |
| **资源包**（`type=asset`） | 一个 ZIP，只有数据没有程序（如仙剑） | TF 卡 `target` 目录，如 `/sdcard/apps/app/pal` |
| **商店索引** | `index.json`，列出所有可下载包 | 云端 `/bbk/index.json`；另有一份**编进固件**的内置索引（离线可用） |

**"安装"= 复制文件，永不自动启动**。装完只让应用列表失效重扫，不写应用注册表，也不需要重启。

### 2 索引格式 `index.json`

顶层是**对象**，不是数组：

| key | 类型 | 必需 | 说明 |
|---|---|---|---|
| `mirrors` | `string[]` | **是** | 镜像前缀，设备最多取 **4** 个；一个都没有直接判失败（`am_store_json.c:156`）|
| `pkgs` | `object[]` | **是** | 包列表，设备最多收 **40** 条（`AM_RPKG_MAX`）|
| `ver` | number | 否 | 索引代次。**设备端从不读取**，纯服务端用 |
| `site` / `updated` | string | 否 | 仅供人看，设备不读 |

`pkgs[]` 每一条：

| key | 类型 | 必需 | 说明 |
|---|---|---|---|
| `name` | string | **是** | 包名，也是落盘文件名。空则整条丢弃 |
| `label` | string | **是** | 显示名。空串回退成 `name` |
| `cat` | string | **是** | 分类，只能 游戏 / 软件 / 标准 / 运维 / 学习 |
| `path` | string | **是** | 相对路径，如 `pkgs/xxx.lua` |
| `size` | **裸数字** | **是** | 字节数。写成字符串会解析失败并丢弃整条 |
| `crc32` | **十六进制字符串** | **是** | 无前缀，校验用。为 `0` 视为非法 |
| `desc` | string | 否 | 一句话说明 |
| `type` | string | 否 | `app`（默认）/ `asset` |
| `target` | string | asset 必需 | 解包目标目录 |
| `ver` | number | 否 | 缺省 = 0 = 未知 |
| `build` | string | 否 | 12 位 `YYYYMMDDHHMM`，**商店判断有无新版只看它** |
| `author` / `date` | string | 否 | 展示用 |

⚠ **单条记录上限 512 字节**（`am_store_json.c:170-174` 的栈缓冲）。超长记录会被静默截断，
被切掉的字段等于不存在 —— 写 `desc` 时不要过长。

### 3 列表从哪来

1. 优先拉云端 `index.json`（镜像列表逐个试），成功则缓存到 `/store/index.json`。
2. 拉取失败时**降级用编进固件的内置索引**（`store/index.json` 被 `build*.sh` 自动嵌入），
   离线也能看到列表，不报错。
3. 内置索引也没有 → 状态进 `ARS_FAIL`，UI 提示「无法获取应用列表」。

索引请求超时 10 秒，外层再等 15 秒（`am_store_net.c:142,148`）。

### 4 下载

| 项 | 值 | 位置 |
|---|---|---|
| 客户端 | `net_client`（`esp_http_client`，挂 `crt_bundle`）| `net_client.c:69-77` |
| 分块 | 8 KB 读缓冲 | `NETC_CHUNK`，`net_client.c:58` |
| 单包超时 | 15 秒 | `am_store_net.c:414` |
| 总时长 | `.lua` 180 秒 / `asset` 600 秒 | `am_store_net.c:423` |
| 断点续传 | **没有**。失败换镜像从 0 重下 | `am_store_net.c:404-408` |

落盘路径（`am_store_net.c:382-393`）：

- 普通包：有 TF 卡 → `/sdcard/store_pkg/<name>.lua`；无卡 → `/store/<name>.lua`
- `asset`：`/sdcard/<path 的文件名>`（当前即 `/sdcard/pal.zip`）

落盘流程（`net_client.c` + `netc_fs_replace.c`）：

1. 先写 `<目标>.part`，**永不直接写目标文件名**；
2. HTTP 200 + `Content-Length` 相符 + 期望 size/CRC 全部通过，才进入替换阶段；
3. 替换：目标已存在 → 先改名成 `<目标>.bak` → `.part` 改名为目标 → 删 `.bak`。
   任何一步失败 → 立即回滚，**旧版本全程只被改名，从不删除**；
4. 下载/校验失败 → 只删 `.part`，目标位置原样保留。

⚠ **FatFs 不支持"目标存在时覆盖改名"**：`f_rename()` 返回 `FR_EXIST`（`ff.c:5244`），
IDF 6.0.3 也**没有** `CONFIG_FATFS_VFS_RENAME_REPLACES_DESTINATION` 这个选项
（`vfs_fat.c` 直接调 `f_rename()`，没有补救）。所以必须先腾位。
这**不是** POSIX 原子替换，而是"**可恢复的非原子替换**"：掉电最坏结果是目标短暂缺失、
`.bak` 里是完整旧版，由"下一次同名下载"或"商店扫描"复位。

**掉电残留的自愈**：商店每次扫描前先跑 `am_store_recover_baks()`（`am_store.c`），
只扫 `/sdcard/store_pkg`：遇到 `*.lua.bak` 就复位成正式名；正式文件已存在则删陈旧 `.bak`；
`.part` **一律不碰**（可能正在下载，删了会毁掉别人的传输；扫描的 `.lua` 后缀过滤也不会把它当包）。
下载进行中（`netc_busy()`）整段跳过，避免与替换中的 `rename` 抢同一个文件。

### 5 校验：size + CRC32

边收边算 CRC（半字节表实现，与 `binascii.crc32` 对齐，`net_client.c:36-52,111`），结束后双重比对：

```c
if (rc == 0 && ((pk->size > 0 && total != (int)pk->size) ||
                (pk->crc != 0 && crc != pk->crc))) { rc = 4; }   /* am_store_net.c:467-472 */
```

失败只删 `.part`（**不再 `remove(dst)`** —— 那会把上一版好文件一起删掉），状态 `ARS_DLFAIL`。

三道关卡，顺序不能换：

| # | 位置 | 比什么 | 不通过时 |
|---|---|---|---|
| ① | `net_client.c`（替换**之前**）| 期望 size / CRC | 只删 `.part`，目标位置一个字节不动 |
| ② | `am_store_net.c`（下载结束后）| size + CRC 再比一次 | `rc=4`，UI 报失败 |
| ③ | `am_store.c`（安装阶段）| 源文件与 `.new` 的 `stat` 大小 | 删 `.new`（多为空间不足）|

> ① 是"保护旧文件"的硬闸门，② 是验收，③ 是复制完整性。①缺了会退化成"先替换再校验"，
> 旧版本可能被坏数据顶掉 —— 2026-10-30 之前一直是这个状态（字段传了但没人用）。

### 6 安装

#### 6.1 Lua 包

- 目标：`/store/apps/{cat}/`（cat → 目录映射：游戏→`app`，运维/工具→`ops`，其余→`app`），
  源码 `am_store_install_cb()` 里的 `to_tf` / `base`（`am_store.c:686-687`）。
- 动作：512 字节缓冲逐块 `fopen/fwrite` 复制（`am_copy_file`，`am_store.c:137-147`）。
- 完成后：`am_lua_invalidate()` + `am_store_invalidate()` 让列表重扫（`am_store.c` 内紧随复制之后）。

> ⚠ `am_store.c:290` 把「装 TF 卡」的偏好**写死为 0**，所以手动安装永远进 SPIFFS。
> 源码注释（`:97-100`）写「默认装 TF 卡」已经过时。

#### 6.2 资源包 `type=asset`

- 下载完成后**自动解压**到 `target`，然后删掉 zip（`am_store_net.c:489-499`）。
- 解压器：miniz 流式（`mz_zip_reader_extract_to_callback`），内存不随包体增长，
  支持 **stored(0) 和 deflate(8)**；拒绝绝对路径与含 `..` 的条目（防 zip slip），
  见 `am_asset.c:99-140`。
- 「已安装」的判据是 **`target/.installed` 标记文件**，不是目录存在（写入处在 `am_store.c:867-869`）。
- 应用条目靠 `.requires="<target>"` 与目录绑定：目录不在就整条不显示。

> ⚠ **解包任务栈必须 ≥ 20 KB**（`am_dl_task`，`am_store_net.c` 的 `xTaskCreatePinnedToCore`）。
> 反汇编实测各层栈帧：`am_dl_task` 1136 + `am_asset_install_cb` 2624 +
> `mz_zip_reader_extract_to_callback` **9664** ≈ **13424 B**；再加上 miniz 深层调用余量。
> 曾按 8 KB 建任务 ⇒ 下载**成功后**解包那一刻栈溢出，`***ERROR*** A stack overflow in task am_dl`，
> 连同 FAT 目录缓存一起被复位清掉（现象：SD 根目录留着完整 zip，`target` 目录却没建出来）。
> 改动这一处前先跑一遍 `xtensa-esp32s3-elf-objdump -d` 核 `entry a1, N`。

> ⚠ `am_asset.c` 与 `am_asset.h` 的头注释仍写「只支持 stored」——那是 2026-10-27 改 miniz 前的旧说明，
> 属**代码注释过期**，不是行为约束。`tools/pack_asset.py:50` 仍固定写 ZIP_STORED。

### 7 更新判定

`am_pkg_has_update()`（`am_store.c:544`，三分支的说明写在它上面 538-543 的注释里）三条分支：

| 情况 | 判定 |
|---|---|
| 云端有 `build` + 本地有 `build` | `strcmp(云端, 本地) > 0` 才算有新版 |
| 云端有 `build`，本地没有（2026-10-30 前发布的包）| **一律提示一次更新**，把设备迁到新体系 |
| 云端没有 `build`（老索引）| 退回 `云端 ver > 本地 ver` |

因为 `build` 是定长 12 位数字，字典序等于时间序，直接字符串比较，不转数值。

> ⚠ 第二分支的副作用：只要云端那包带 `build`，本地旧包就会**每次进商店都显示「更新」**，
> 直到用户更新到带 `build` 的新包为止。这是设计取舍，不是 bug。

### 8 进度显示

- 单一全局进度 `s_permille`（0..1000），`am_rstore_dl_permille()` 对外（`am_store_net.c:62`）。
- `.lua` 包占 0..1000；`asset` 下载占 0..700，解包占 700..1000。
- UI：列表行第二行被进度条顶掉，右侧画 `NN%`，按钮文案锁定「下载中」；
  下载中该行冒泡到第一位并每帧重绘（`page_app_manager.c:1011-1040,1688-1710,1749`）。
- 老的中心浮动进度框 `am_draw_dl_overlay()` 是**死代码**（函数体直接 return，调用处已注释）。

### 9 错误处理

错误码（`am_internal.h:87`）：`1`=HTTP 非 200，`2`=连接/超时/截断，`3`=写盘，`4`=校验失败。

| 场景 | 真实行为 |
|---|---|
| 索引拉取失败 | 有内置索引 → 静默降级离线；无 → 「无法获取应用列表」 |
| 下载失败 | 逐个镜像重试，全失败删残文件 → 「下载失败」 |
| 校验失败 | 删文件 → 「下载失败」 |
| 空间不足 | **下载前不检查剩余空间**；写失败落到 `rc=2`，UI 只会说「下载失败」 |
| 自动安装失败 | 只打 `ESP_LOGW`，状态仍置 OK → UI 会弹「已安装」|

> ⚠ 最后一条是**已知缺陷**：自动安装失败时界面显示成功。见 `am_store_net.c:506-511`。
> 另外 `3`（写盘）这个错误码**从未被赋值**，`AM_DL_MAX`（2MB）是**未使用的死宏**
> （pal.zip 有 31.9MB，正说明它没生效）。

### 10 卸载

- Lua 包：删 4 条路径（`/store/apps/{cat}/x.lua`、`/sdcard/apps/{cat}/x.lua`、
  `/sdcard/store_pkg/x.lua`、`/store/x.lua`），再清主菜单/隐藏标记（写 NVS），
  见 `am_store.c:932-961`。
- 资源包：递归删 `target` 目录（深度上限 8，`am_asset.c:189-197`），**不动 NVS**。
- ⚠ 不清理应用自身的数据目录（源码中未找到实现）。

### 11 打自己的包

```bash
python3 tools/sync_apps.py          # 收 apps/lua → build/apps_l.bin + 商店索引
esptool ... write_flash 0xC00000 build/apps_l.bin
python3 tools/pack_asset.py make pal --src <目录> --target <目录> --label 名称 --write-index
```

- 改 Lua 不需要重编固件；只有改 C 才 `build.sh`（且必须先 build 再 sync）。
- 手工改服务器上的 `bbk/index.json` 后**必须 `nginx -s reload`**：open_file_cache 会持有旧句柄，
  设备端会拉到空内容。

### 12 待核实

- 服务端 `store_publish` 每次发布把 `ver` +1，而 `tools/store_build.py` 写死 `"ver": 1`，
  两边口径不一致（不影响设备，因为设备不读 `ver`）。
- 仓库内 `store/pkgs/` 没有 `pal.zip`（只存在于服务器），无法在本地复核其压缩方式。
- 写盘失败归到 `rc=2`（连接失败），真机上空间不足的实际提示文案待实测确认。

## 第五部分 设置与存储归属（NVS）

> 本部分讲：命名空间与 key 的主人。

> 目的：**同一份配置只有一个"主人"**。新增/修改设置前先查这张表，别在第二个模块里另开一个键。
> 生成依据：全仓源码扫描（`nvs_open` / `svc_cfg_set_*` / `svc_nvs_*` 与 `#define *_NS / *_KEY`），2026-10-26。

### 规则（三条）

1. **一个命名空间一个主人（owner）**：只有主人能新增 key；别人要读，走主人的 API，不要自己去 `nvs_open`。
2. **跨模块共用命名空间必须在本表登记**（下面标 ⚠ 的）。
3. **写 NVS 会关 flash cache**，正在跑的代码会停顿十几~几十 ms ⇒ **禁止在渲染/轮询/循环里写**；交互触发才写，连续调节要防抖（参考音量 1500ms 防抖）。

### Lua 侧写 NVS 的约束（2026-10-26 加）

`app.nvs.set_int/set_str`、`app.db.set/seti` 现在走**1 秒节流**：同一 (命名空间, key) 1 秒内只落盘一次，
窗口内的后续写入只更新内存最新值，由一次性定时器统一落盘；**读之前会先刷待写值**，读到的一定是自己刚写的。
⇒ Lua 应用即使在循环里写，也不会每帧卡 flash。唯一风险窗口：写完后 **1 秒内** 直接断电/进深睡会丢最后一次写。

## 第六部分 显示与灰阶（ST7305 400×300 1bpp）

### 1 帧缓冲格式（唯一真相：`st7305.c` 的 `st7305_draw_pixel`）

不是"逐行 1bpp"，而是面板原生的 **2 列 × 4 行 / 字节**：

```
字节索引 = (x >> 1) * 75 + (y >> 2)        /* 75 = 300 / 4 */
位号     = 7 - ((y & 3) << 1 | (x & 1))
```

- 一字节 = 2 个相邻列 × 4 个相邻行 ⇒ **改一个像素必须用掩码写，不能整字节赋值**（会连带改掉邻行邻列）。
- 颜色常量：`ST7305_COLOR_BLACK = 0`、`ST7305_COLOR_WHITE = 1`（**0 才是黑**，容易记反）。
- 整帧 15,000 B。写 fb 一律走 `st7305_draw_pixel` / `write_masked_pixel`，不要自己拼位。

### 2 引擎灰阶：4 档 + 2×2 图案

源只有 4 级（GBC 的 palette / NES 的 2bit），一个源像素映射成 **2×2 物理点**，图案里画几个黑点由 `vid_tune` 的用户曲线（dots 0..4）决定。
**2×2 最多 5 级密度**，这是硬上限——想要更多级只能换更大的物理块（= 更大缩放），不是算法能绕过的。

两个引擎的图案**必须来自同一处**：

| 引擎 | 消费方式 | 位置 |
|---|---|---|
| GB/GBC 2× | 每源像素查 1 次图案，写 4 个位 | `board_shim_pat_get()` |
| NES 1×/缩放 | 预先把"2 个源像素 → 2 个位"编成字节表，热循环只查表 | `s_rowbits[4][2][16][2]` |

> 2026-10-30 之前这两条路径各写一遍取表逻辑；现在统一到 `board_shim_pat_get()`，
> `s_rowbits` 多一维 **x 相位**（`[pair][cp&1]`），因为位置相关的算法需要它。
> ⚠ 改这两处**必须同时改**，否则 NES 与 GBC 的灰阶会不一致。

### 3 两种算法与切换

| 算法 | 说明 | 默认 |
|---|---|---|
| `CLUSTER_2X2` | 黑点按固定顺序聚成块/散开（`ord_cluster` / `ord_scatter`），与屏幕位置无关 | ✅ |
| `BAYER_4X4` | 4×4 有序 Bayer 阈值，按**绝对屏幕坐标**取阈值，黑点分散 | 实验，关闭 |

- 串口：`gray` 查询、`gray 0|1` 切换。切换会重建 GB/GBC/NES 三张表并 `st7305_invalidate_frame()` 强制整屏重画。
- 两者**填充率相同**（`dots*4/16` = `dots/4`）⇒ 整体亮度不变，可直接肉眼 A/B。
- 实现：`components/engines/board_shim/gray_quant.c`（纯 C，主机测试 `tests/gray_quant` 直接编译它）。

**已实测的结论（重要）**：默认曲线 `dots{0,1,3,4}` 对应的填充率只有 `d∈{0,4,12,16}` 四档，
而 4×4 Bayer 的阈值 0..3 落在"偶/偶"格点、12..15 落在"偶/奇"格点 ⇒ 这四档下**每块的点数与哪一格是白都与块位置无关**，
与 `CLUSTER_2X2` **同构（只是排列不同）**。只有 `d=8`（dots=2，50%）这类中间档才会呈现棋盘分布。
⇒ **在这条默认曲线下开 Bayer 几乎看不出差别**；要它有意义，必须先让曲线给出中间密度（例如 2 点档）。

### 4 局部刷新（脏矩形）：结论是**不做**

`st7305_set_partial()` / `st7305_get_partial()` 现在是空壳，`remcon partial` 永远回 0。
不是"还没做"，是 **2026-10-25 做完又按 linit 要求整块删掉的**（见 `st7305.c` 的注释）：

1. 脏行带局刷依赖 `CASET` 镜像换算，**旋转方向无法用仪器验证**，算错的表现是"某几行横移/花屏/局部永不刷新"，
   与"卡死"无法区分；
2. 整帧 SPI 只有 ~3–4.5 ms，而面板自刷新只有 16–24 Hz（帧周期 41–62 ms）⇒ **SPI 占帧时间 7–11%**，省字节换不来帧率；
3. **静止画面本来就已经不传**：`st7305_flush()` 用整帧校验和 `s_last_sum` / 竖屏缓冲校验和 `s_last_psum` 判定"内容没变"直接返回，
   0 字节。（模拟器实测：跑 18 s 与 40 s 的 SPI 字节数完全相同 = 75,132 B。）

⇒ 再引入脏矩形，唯一能省的是"局部变化帧"的 SPI 时间（最多 ~4 ms），却要额外一份 15 KB 上一帧缓冲 + 每帧比较，
并且把已经踩过的方向换算风险重新引回来。**除非将来出现"SPI2 与 SD 抢总线导致卡顿"的实测证据，否则不做。**

## 附：内存实测与蓝牙按需加载（2026-10-30）

> 补充第一部分的"为什么要省内部 RAM"。数字来自真机实测（**旧固件**），
> 改动后的验收**未烧录执行**，所以"预期收益"未验证。

### 1 根因：关了蓝牙也不还内存

蓝牙控制器初始化后会**常驻约 71 KB**（控制块 + 缓冲），`esp_bt_controller_disable()`
只停射频，**不释放内存**。原来的实现是"开机即初始化"，等于永久占着这 71 KB —— 即使从没用过手柄。

**改法**：改成**按需加载** —— 首次真正需要 BLE 时才初始化控制器，退出后保持（不反复 init/deinit，
因为反复初始化有失败风险）。

### 2 真机实测基线（旧固件，同外设状态）

| 状态 | 内部 free / largest |
|---|---|
| 启动后空闲 | 见历史报告实测值（未在本表固化，避免与当时外设状态不符）|
| 蓝牙已初始化 | 比未初始化低约 71 KB |

> ⚠ 这两行故意不写具体数字：**不同外设状态下的数字不可比**，固化了反而误导。
> 要数字请现场 `remcon audit`，并记录当时的 WiFi/BT/音频开关状态。

### 3 内部内存 TOP 大户（下一批优化候选）

历史审计列出的方向：**BT 常驻块 → 字库/页面缓冲 → 引擎帧缓冲 → 网络 TLS 缓冲**。
优化顺序按"收益 ÷ 风险"排，不要一次动多个（分不清是谁的锅）。

### 4 未解决

- 按需加载的**验收未执行**（当时禁止烧录），首次上机要确认：连续开关蓝牙 5 次不崩、
  连接手柄成功率不降。
- `bt_ctl` 的 `.bss` **不能迁 PSRAM**（`bt_init` 任务静态栈会走禁 cache 路径）。

### 5 任务栈单位陷阱（2026-10-29 血案）

`xTaskCreate()` 的 `usStackDepth` 在 **ESP-IDF 里单位是「字节」**，不是 word。
`main/remcon.c` 原来写 `4096` 并注释"16KB/峰值 12.2KB"，实际只有 **4KB** →
remcon 任务栈溢出，表现为**整机反复重启**。

修复：改成 `#define RC_TASK_STACK 16384`（4 倍余量），代价是内部 RAM 少 12 KB
（桌面基线 205.9 KB → 约 193.6 KB）。

**自查**：新增任务时按"峰值栈 × 3~4"给字节数，别用 word 数乘 4 去估。
栈高水位用 `remcon audit` 看，别猜。
