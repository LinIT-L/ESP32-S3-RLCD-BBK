# LinTOS 软件架构与模块规范（存档 v2）

> 更新：2026-08-27
> 定位：本项目（ESP32-S3 模块化掌机固件）的**目标架构 + 规范规则 + 现状对齐**存档。
> 原则：低性能嵌入式系统仍应分层、模块化、明确依赖方向 —— 分层几乎零运行时开销，收益远超成本。

---

## 一、目标架构：微内核 + 分层（Layered Kernel Shell）

参考成熟且**与本项目形态高度一致**的方案：
- **Flipper Zero / Flipper One 固件**：最小内核 + 独立模块注册表（registry 宏系统）+ 全局服务（service）+ 应用（app）静态表 + Reactor 单事件循环 —— 增删功能只需改一张注册表，符合 OCP（开闭原则）。
- **LK（Little Kernel）**：`Arch / Platform / Target / Kernel / App` 严格五层，上层只依赖下层。
- **ESP-IDF 官方**：组件即静态库（.a），`REQUIRES`/`PRIV_REQUIRES` 显式声明依赖。

**结论**：LinTOS 已自然演进到该形态（`os_module_t` 注册、`os_register`、`os_pages.c` 装配表、`svc_statusbar` 全局服务、页面栈单环）。本文把它明确固化为规范，并纠正越界/重复。

```
┌─────────────────────────────────────────────┐
│ L4 应用/页面层   os/pages/*、引擎运行循环      │
├─────────────────────────────────────────────┤
│ L3 内核/服务层   os/kernel/* + services/*     │
│                 (页面栈/弹窗/主题/管家/状态栏)  │
├─────────────────────────────────────────────┤
│ L2 领域服务层   favorites/引擎管理器/壁纸/      │
│                 文件扫描/音频/网络/蓝牙         │
├─────────────────────────────────────────────┤
│ L1 驱动/兼容层   st7305/触摸/ES!/minimp3/      │
│                 input/board_shim/HAL          │
└─────────────────────────────────────────────┘
```
**上层可以依赖下层；下层永远不知道上层的存在。同层之间尽量不互调，改由 L3 内核调度。**

---

## 二、分层与依赖方向规范

| # | 规则 |
|---|---|
| R1 | 依赖只能单向向下：页面(L4)→内核(L3)→服务(L2)→驱动(L1)。禁止反向依赖、禁止同级页面互调。 |
| R2 | 请求应逐层传递，不跳层调底层（页面不应直接写寄存器；如需底层能力走 L2/L3 提供的 API）。 |
| R3 | 每层职责单一：驱动只管硬件、服务管能力、内核管调度/生命周期、页面管交互/渲染。 |
| R4 | 能力经**接口契约**暴露（`os_module_t`、服务 API、Host API），上层面向抽象/接口编程，不 #include 具体实现细节。 |
| R5 | 新增功能 = 注册表加一行 + 实现模块，**不改已有模块**（开闭原则）。 |
| R6 | 组件依赖用 `REQUIRES`（对外可见）与 `PRIV_REQUIRES`（仅内部）**显式声明**，不得隐式依赖。 |
| R7 | 一个模块只做一个职责（SRP）：可被“多个不同原因”修改的模块必须拆分。 |
| R8 | 高内聚低耦合：`.c/.h` 结伴自包含，私有 static state 留本文件，对外只暴露最小接口。 |

## 三、组件（Component）规范

- **边界**：一个目录 = 一个独立可复用职责，编译为静态库。`include/` 为公共头，`*.c` 为实现。
- **命名**：小写下划线，见名知义（`wifi_manager`、`board_battery`）；类型名/结构体名用 `_t` 后缀。
- **尽量自包含**：字体/图标等静态资源随模块私有（`#include "xxx.inc"` 不动态引用外部），避免跨目录复制。
- **职责归位**：显示驱动只管显示；启动 logo 归启动模块；赞助/收款资源归赞助页面；图标按用途归对应模块。**驱动组件内不得混入业务资源**。
- **公共抽取**：跨模块完全相同的代码（如 `make_color.c`）抽为共享组件，单一来源，勿复制。

## 四、模块契约与生命周期

- 页面/应用统一实现 `os_module_t`：`on_enter / on_exit / render / action / touch / poll`，私有 static state 由模块自持（薄 `ui_ctx`）。
- **懒加载**：按需 `os_hw_request/store` 启动硬件/引擎，`release` 归零即关闭；进入引擎菜单后台预载，返回主菜单即时清理（`os_mgr` / `engine_manager`）。
- **退出清理**：模块退出必须释放自己申请的资源（任务、堆、外设），不遗留后台线程（如下载/扫描 task 退出时结束）。
- 全局服务（状态栏等）由内核统一 `svc_*` 叠加，不占页面栈、每次 flush 前统一绘制覆盖层。

## 五、内存与资源规范（ESP32-S3 双区 RAM）

| 区域 | 放什么 | 禁放 |
|---|---|---|
| 内部 SRAM（DIRAM） | 热路径、性能关键（引擎模拟内存、蓝牙映射、总线镜像） | 大静态缓冲 |
| PSRAM（EXT_RAM_BSS_ATTR / SPIRAM） | 弹窗栈、终端缓冲、页面菜单、字库索引、歌词/LRC 等大块静态缓冲 | 性能关键时刻 |

- 优先静态分配；递归必须有界；生产构建用 `-fstack-protector` 与内存峰值日志（`os_mgr` 已内嵌内存监控）。
- 目标内部 SRAM 余量 ≈ 161.7KB 以上（历史基线）。

## 六、事件调度与解耦

- **单主循环（Reactor）**：`os_shell_loop` 统一轮询输入 → 分发 action/touch → 服务 tick + 模块 poll → 统一渲染。避免各模块自行乱建网格/while 轮询。
- **弹窗统一**走 `os_dialog` 4 层栈（list/confirm/toast/自定义），不手绘业务弹窗。
- **资源请求用回调/注册表**做依赖注入，避免硬编码调用链（参考 registry 宏表风格）。
- 长时间阻塞操作（TLS/HTTP/扫描）放**独立高栈 task**（如 32KB），并保证退出时被回收。

---

## 七、编码规范（嵌入式）

- 命名：函数 `xxx_yyy`；常量 `#define XXX_Y`；类型 `typedef ... _t`。不用晦涩缩写。
- 头文件：文件顶部说明用途/依赖，公共头放 `include/`；`#pragma once`。
- 防御式：校验外部输入、指针、数组边界；循环与状态机带超时；ISR 尽量短。
- 工具类常量注释放 `<escaped>` 或注明编码（本项目中文资源为 UTF-8）。
- 新增组件遵循本篇 R1–R8 与 ESP-IDF 组件规范；无必要不新增抽象。
