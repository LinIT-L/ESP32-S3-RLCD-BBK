# 文档规范

> 目标：任何人（或 AI）拿到任务，**一屏内能看懂「是什么 / 怎么用 / 怎么验」**，不用翻代码猜。

## 1. 写法

- **只写可验证事实**。没实测的标「待确认」，⛔ 把推测写成结论。
- **结论先行**，一段一句；⛔ 讲历史与心路，需要就放 `archive/`。
- 命令、路径、引脚号一律给**原文**，不写"大概/应该是"。
- 同一事实**只写一处**，其它地方引用它（`见《硬件与IO §1》`），⛔ 复制粘贴。

## 2. 每份文档必须有

| 项 | 要求 |
|---|---|
| 开头 | 一句话说清"这份文档解决什么问题" + 真相源在哪 |
| 正文 | 按任务顺序组织，不按代码结构 |
| 结尾 | 踩坑 / 已知限制 / 回滚办法 |

## 3. 交付物（发给 linit 的东西）一屏内

1. **是什么** —— 改了什么
2. **怎么用** —— 触发路径 / 命令
3. **验证命令** —— 现场能跑的自检（`remcon heap` 等）
4. **已知限制** —— 没做到的、待确认的
5. **回滚** —— 出问题怎么退

## 4. 什么时候更新

- 功能变更 **同一次改动**里更新对应文档，⛔ 攒着。
- 新增 Lua API **必须**跑 `tools/lua_api_doc.py`（自动生成 `Lua桥API参考.md`），否则构建失败。
- 删除/合并文档时，**留指针**（如 `板型IO表.md` → 《硬件与IO》），别让旧链接断。

## 5. 重大决策 → 极简 ADR

超过一天工作量、或推翻过既有方案的改动，追加一段：

```
## ADR-<日期> <标题>
背景 / 选项 / 选择 / 后果
```
