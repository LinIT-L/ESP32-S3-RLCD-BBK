# 蓝牙手柄：连接 / 自动回连 / 自动映射 —— 详细重构方案

> 2026-10-02 · linit 反馈三件事：
> ①「能连上，协议没问题，但**自动连接老是出问题**」
> ②「怀疑你**保存历史连接**也有问题」　③「手柄**经常变 MAC 地址**」
> ④「蓝牙连接过后，**它不会进行自动映射**」
> 本方案参照 **Bluepad32**（ESP32 手柄 host 的权威开源实现）重做。

---

# 0. 一句话结论

> **错在把"设备身份"建在 MAC 上；错在把"映射向导"关在手柄页里。**

这两条不改，自动回连和自动映射**永远时好时坏**。

## 0.1.1 C2/C7 实施细节（与 4.1 / 4.5 的差异，以本节为准）

**C2 · 手柄档案表**

- 未新造 `gp_profile_t` 取代历史表，而是**并列新增** `gpm` 键存"名字 → {kmap, supmap, gbmap, mapped}"，最多 `GPM_MAX=6` 只。旧键 `kmap/supmap/gbmap` **保留不动**，作为"尚未连接任何手柄"时的默认值 → **可回滚**。
- 首次升级（`gpm` 为空但有 `lconn`）→ **自动迁移**：把现有那套全局映射认作"上次连接手柄"的档案并标 `mapped=true` → **原有映射不丢、不弹重复引导**。
- `mapped` 只在**用户真的存过映射**时置位。为此把两处"隐式落盘重置"改成**只改内存不落盘**（`bt_manager_reset_pad_clean()`、`on_connected_cb` 的建档分支）——这正是 4.5 那条「除忘记入口，任何路径都不许隐式清映射」的落地。

**C7 · 忘记此手柄**

- 按**名字**（身份）执行 5 件事：①清该名字全部连接记录 ②清这些记录的 BLE 绑定 ③删档案 ④若正连着则清当前绑定并断开 ⑤清掉"上次连接/回连目标"，停回连。
- 手柄页菜单由 6 项变 7 项，`忘记此手柄` 与 `设备信息` 一样**只在已连接时显示**。

# 1. 参考：Bluepad32 到底怎么做的

Bluepad32（`ricardoquesada/bluepad32`，Apache-2.0，底层 BTstack）：ESP32/ESP32-S3/PicoW 上事实标准的手柄 host。

## 1.1 它的设备模型

```
uni_hid_device_t
├─ vendor_id / product_id      ← 设备身份的一部分（HID 描述符里读出来）
├─ name[..]                    ← 设备身份的一部分（广播名）
├─ cod (Class of Device)       ← 设备类别（鼠标/键盘/手柄/摇杆）
├─ hid_descriptor              ← 用它认"是哪款手柄"
├─ address                     ← 只当"一个属性"，不是唯一身份
└─ state (Created/Init/Connecting/Connected/PendingReady/Ready/Disconnecting/Deleted)
```

**关键点：它从来不用"地址相等"来判定"这是不是同一只手柄"。**

## 1.2 它的六条策略（我们逐条对照）

| # | Bluepad32 策略 | 我们现状 | 要不要抄 |
|---|---|---|---|
| 1 | 身份 = **name + VID/PID + CoD**，地址只是属性 | 身份 = **地址**（`is_paired_device(bd_addr)`） | ✅ 必须 |
| 2 | **"没有设备连着时才扫描"**（连上立刻停扫） | 扫描与后台回连可能并行 | ✅ 必须 |
| 3 | **显式状态机 + 每态超时**，靠超时收敛，不"放弃本轮" | 3s 直连 + 60/120/240/300s 退避，匹配不到**直接放弃** | ✅ 必须 |
| 4 | **扫描 / 自动连接是两个显式开关** | 两者共用一条路，互相覆盖 | ✅ 必须 |
| 5 | **FORGET 是用户显式动作**；不隐式清配对钥匙 | 判为"新手柄"时**隐式重置按键映射** | ✅ 必须 |
| 6 | BLE 地址会变 → **配对后靠 IRK 把随机地址解析成身份地址** | 有 bond 存储，但**没利用 IRK 解析结果** | ✅ 先取证再定 |

## 1.3 为什么不直接搬 Bluepad32

它用 **BTstack**（`hci` 层自己写），我们已用 **ESP-IDF Bluedroid + esp_hid_host**。
→ **只抄"策略与状态机"，不抄代码**；改动全部落在我们自己的 `bt_ctl` 组件里。

## 2.1 连接链（用户点选）

```

       ├─ s_last_connect_was_new = s_pending_new      (549-565)
       ├─ bt_map_calibrate_start()                     (606) ← 摇杆中性点采集(自动✓)
       └─ s_connect_cb(true)                           (608) ← 页面用它切"连接成功!"弹窗
```

## 2.2 自动回连链

```
bt_manager_poll_auto_reconnect()   (bt_manager.c:253)
  ├─ 目标地址 = 本次开机连过的 s_last_conn_addr, 否则 NVS 历史 s_history[0].bd_addr
  ├─ s_rc_target_valid / s_auto_reconnect_pending 标志
  └─ bt_reconnect_task  (bt_manager.c:820, 常驻, 低优先级)
       ├─ 开机回连窗口 30s (BT_BOOT_RECONNECT_WINDOW_MS)
       ├─ 窗口内每 3s 直连一次 (BT_BOOT_RECONNECT_POLL_MS)
       ├─ 之后退避: 60s → 120s → 240s → 封顶 300s
       └─ 扫描窗口内匹配 (bt_manager.c:664-703) → 命中地址才连
断连回调 → 退避复位 + bt_manager_wake_reconnect()   (bt_manager.c:623-627)
```

## 2.3 映射链（★ 你说的"不会自动映射"就在这）

| 动作 | 位置 | 何时跑 | 自动吗 |
|---|---|---|---|
| **摇杆中性点采集** `bt_map_calibrate_start()` | `bt_map.c:350`，由 `on_connected_cb` 调用 | 每次连接成功 | ✅ 自动 |
| **按键映射向导** `start_key_mapping()` | **`page_gamepad.c:555`（页面私有 static）** | 只有两个入口：① 手柄页内点选设备连上后（`:228`）② 手柄页菜单点"按键映射"（`:603`） | ❌ **不自动** |
| **清映射回默认** `bt_manager_reset_pad_clean()` | `bt_manager.c:934` | 判为"新手柄"时（`:1022` / `:1039`） | ❌ 而且**隐式** |

> ⚠ **致命组合**：地址一漂 → 判"新手柄" → **清掉你配好的映射**；同时因为不是从手柄页连的，**又不会打开映射向导** → 结果就是"映射没了，也没人来引导你重配"。**这正是你遇到的现象。**

# 4. 目标设计（详细到数据结构 / 状态机 / NVS）

## 4.1 设备档案 `gp_profile_t`（取代"历史 + 三份全局映射"）

```c
/* 一只手柄的全部身份与配置 —— 主键是 (name, vid, pid)，不是地址 */
typedef struct {
    char     name[33];        /* 身份主键 1: 广播名, 空串=无 */
    uint16_t vid, pid;        /* 身份主键 2: 能读到就更稳, 0=未知 */
    uint8_t  addr[6];         /* 缓存: 最近一次见到的地址 (只做"快路径直连") */
    uint8_t  addr_type;       /* 缓存: 上次地址类型 (public/random/resolvable) */
    uint8_t  flags;           /* bit0 = 已做过按键映射; bit1 = 曾成功连接过 */
    uint32_t last_seen_s;     /* 最近连接时刻(相对秒), 用于挑"最近的那只" */
    uint8_t  kmap[FUNC_MAX];  /* 按键映射 —— 每只手柄独立! (现在是一份全局) */
    uint8_t  supmap[SUP_MAX];
    uint8_t  gbmap[GB_MAP_MAX];
    uint8_t  reserved[8];
} gp_profile_t;
```

**身份比较规则（按优先级降级）**
```
1) name 非空 且 两边 name 相同        → 同一只
2) vid&&pid 都非 0 且相同              → 同一只
3) 以上都不成立时, 才退化比较 addr     → 同一只
```
→ **地址漂移不再导致"新手柄"**，映射不再被清（P1/P4/P6 一起解决）。

**NVS 存储**
- 新键：`gprof`（blob，`gp_profile_t[GP_PROFILE_MAX]`，建议 `GP_PROFILE_MAX=6`）+ `gpnum`（条数，uint32 blob —— 注意别重犯之前 `hcnt` 用 u8 读 u32 存的那个坑）。
- **一次性迁移**：首次启动若发现旧键存在（`history`/`hcnt`/`kmap`/`supmap`/`gbmap`），就合成 1 条 profile（名字取 `lconn`，地址取 `history[0].bd_addr`，映射取旧全局映射），写新键、置 `gmig=1`，**旧键保留不删**（可回滚）。

## 4.2 自动回连状态机（取代零散重试）

```c
typedef enum {
    RC_IDLE = 0,     /* 不需要回连(已连上 / 用户关机 / 用户手动断开 / 预算用完已关射频) */
    RC_DIRECT,       /* ① 直连 profile.last_addr: 最多 3 次 × 3s      —— 预算 9s */
    RC_SCAN_NAME,    /* ② 按身份(名字/VID/PID)扫描: 只扫 1 轮 5s      —— 预算 5s */
    RC_STOP,         /* ③ 预算用完 → **关射频省电**, 等下一次"值得试"的时机唤醒 */
} rc_state_t;
```

| 状态 | 做什么 | 预算 | 失败后 |
|---|---|---|---|
| `RC_DIRECT` | `bt_core_connect(profile.last_addr, addr_type)`，间隔 3s 最多 3 次 | 9 s | → `RC_SCAN_NAME` |
| `RC_SCAN_NAME` | 扫 5s，结果里按 **4.1 的身份规则**匹配；命中即连（**地址随便变**） | 5 s | → `RC_STOP` |
| `RC_STOP` | **关射频（停 Controller / 停扫）**，等下一次唤醒条件 | 0（最省电） | 被唤醒 → `RC_DIRECT` |

**进入/退出条件**
```
进 RC_DIRECT:  开机 / 意外断连 / 用户唤醒(按键·进手柄页·开机回连窗口)
退 RC_IDLE  :  连上成功 / 用户关机 / 用户手动断开 / 用户正在扫列表
进 RC_STOP  :  一轮预算用完**没连上** → 关射频, 不再自己重试
唤醒 RC_STOP:  ① 用户进手柄页 ② 用户按任意键唤醒设备 ③ 下次开机
```

## 4.2.1 ★ 省电预算表（linit 2026-10-02 追加："不要盲目的一直连接"）

蓝牙射频常开是这台设备最大的电耗项之一，所以回连**必须有预算、见好就收**：

| 时机 | 尝试预算 | 用完没连上怎么办 |
|---|---|---|
| **开机** | 直连 3 次(3s 间隔) + 扫 1 轮 5s ≈ **≤ 14s** | **关射频**（不再后台循环）—— 原"开机回连窗口 30s + 退避到 300s"取消 |
| **使用中意外断连** | 直连 3 次 + 扫 1 轮 ≈ **≤ 14s** | **关射频** + 只留一个"待回连"标志 |
| **用户唤醒**（进手柄页 / 按任意键） | 再给一轮 ≈ **≤ 14s** | 同上 |
| **息屏 / 屏保即将进** | **立即中止回连 + 关射频** | — |
| **低电量 < 20%** | 预算砍半 ≈ **≤ 7s** | 直接关射频 |

**明令禁止（就是"盲目一直连"的几种形态）**
- ❌ 无限退避循环（原 30→60→120→300s 封顶后**继续**重试）
- ❌ 后台无上限扫描（**扫描是最费电的动作**：每次扫描射频全开、占空比高）
- ❌ 已经连上了还继续扫（原扫描窗口与连接并行）
- ❌ 断连后不受预算约束地立刻重连（原 `bt_manager_wake_reconnect()` 没有次数上限）
- ❌ 手柄不在场时死等（原 `esp_hidh_dev_open` 会阻塞到超时，白耗电）

**省电还体现在**：
- 回连只在**内部 RAM 栈**的低优先级任务里做，不阻塞 UI、不抬 CPU 频率
- 每次尝试之间**必须** `vTaskDelay`，不允许忙等
- 关射频走现有的 `bt_manager_disable()`（`bt_core_deinit()` 会真的把 Controller 关掉，**这是省电的关键**）
- 与 `os_hw` 管家一致：只有 `os_hw_request(OS_HW_BT)` 计数 > 0 时才允许射频开着

## 4.3 自动映射（P5 的解，也是最关键的一条）

把映射**从 UI 页面里搬出来**，变成"连接后由策略层驱动的动作"：

```
on_connected_cb()
  ├─ 认出手柄 → 找到/新建 profile
  ├─ bt_map_calibrate_start()            摇杆中性点 (已有, 保留)
  ├─ 若 profile.flags & 已映射:
  │     → 把 profile.kmap/supmap/gbmap **应用**到 bt_map    ← 用户的配置自动生效
  └─ 否则:
        → s_map_pending = true, s_map_pending_name = profile.name   ← 待用户确认后进向导
```

**UI 侧（任意页面都能收到）**
- 在 OS 主循环每帧 poll `bt_manager_take_map_pending()`（一次性消费）：
  - 命中 → 弹确认框 `「检测到新手柄 Q36，现在设置按键映射？」` → 确认则 `os_push(OS_PAGE_KEYMAP)`
  - **不强制**：用户选"稍后"就保留 `pending`，下次连接再问
- **映射向导抽成独立页面** `page_keymap.c`（`OS_PAGE_KEYMAP`），入参 = profile 指针/名字
  - 现在它整块逻辑在 `page_gamepad.c:555+`（`map_render/map_key/map_poll` + 一堆页面 static）→ 原样搬过去，改"写全局映射"为"写 profile.kmap"
- 映射完成 → 写回 profile + 置 `flags |= 已映射` → **下次连接自动应用，不再问**

## 4.4 扫描纪律（P7）

- 全局一个"蓝牙活动模式"：`BT_ACT_NONE / BT_ACT_RECONNECT / BT_ACT_USER_SCAN / BT_ACT_CONNECTED`
- `RECONNECT` 与 `USER_SCAN` **互斥**：用户点"添加设备" → 暂停回连（`RC_IDLE`），扫完/取消后按需恢复
- `CONNECTED` → 立即 `stop_scan`（对齐 Bluepad32 "连上就停扫"）

## 4.5 显式「忘记此手柄」（P8）

手柄页菜单加一项：**忘记此手柄** =
1. `bt_core_remove_bond(addr)`（清配对钥匙）
2. 删除该 profile 条目
3. 清映射（并**只**在此时允许清）
4. toast：`已忘记 Q36，请手柄重新配对`
> 反向纪律：**除这个入口，任何代码路径都不许隐式清映射**（把 `bt_manager_reset_pad_clean()` 里"重置映射"那几行去掉，只保留清历史/停回连）。

# 5. 分步实施（每步：改什么 / 怎么验收）

## C1 · 取证（先做，1 次构建）
**改**：`on_connected_cb` 与 `sdr_analyze` 类似，在连接/断开/回连各阶段打一行：
```
BT_EVID bda=%02x:.. addr_type=%u name="%s" vid=%04x pid=%04x
        bond=%u profile_hit=%d(stage=direct/scan/backoff) map_flag=%u
```
`addr_type` 取值：0=public 1=random 2=RPA 3=NRPA（Bluedroid `esp_ble_addr_type_t`）。
**怎么判**：
- `addr_type=2(RPA)` 且 **bond 记录数 ≥1** → 栈本应给出稳定身份地址 → 走 4.1 改造即可
- `addr_type=3(NRPA)` 或 **每次连接 bond 数都=0** → 地址天生不可信 → 4.1 的"名字为主键"是唯一解
**验收**：串口能看清"地址到底怎么变、名字稳不稳、bond 有没有"。

## 6.2 历史记录（连接记录）—— 现状与"保留几"的决定

**linit 2026-10-02 问**：「历史记录会不会太多？每次添加希望能顶替掉之前的。保留几个？」
**决定：保留 4 条不变**（仅做下面那处口径修复）。

实测现状（不是推测）：

| 项 | 实测值 |
|---|---|
| 上限 | `BT_HISTORY_MAX = 4`（`bt_manager.h:211`） |
| 单条大小 | **41 B**（`<6sB32sb?` 无填充）→ 4 条共 **164 B** NVS，可忽略 |
| 去重 | 已按**同名 或 同址**去重 → 命中则**替换并移到最前**（`add_to_history()`） |
| 满 4 条 | 挤掉最旧（**已经是"顶替"语义**，不会无限增长） |
| **谁在用** | **只有 `s_history[0]`**：`poll_auto_reconnect()`、`bt_try_reconnect_now()`、地址失败改按名字 |
| 第 1~3 条 | **只喂「连接记录」那个列表**（`open_hist_dialog`，UI 里 `items[4][64]` 写死 4） |

→ 所以"会不会太多"的答案是**不会**；唯一会让列表出现"同一只重复项"的机制是
**名字比较口径不一致**（见下），已修。

**本次修复：统一"设备身份"比较口径**

- 新增 `btm_same_name(a, b)` = **名字非空且相同 → 同一只**；名字缺失才退化比地址。
- 原先口径不一：`add_to_history()` / `reset_pad_clean()` 额外要求 `has_name` 标志为真，
  而 `is_known_device()` 只看名字串 → 这只漂 MAC 且名称有时读不到的手柄会被**判成新手柄并多占一格**。
- 统一改到 `btm_same_name()`；顺手去掉 3 处 `has_name` 造成的"名字已读到却被当无名"的旁路
  （`poll_auto_reconnect` 的回连目标名、`bt_reconnect_task` 的按名字重解析、`connect_device` 的判定）。
- `bt_device_t.has_name` **保留为只写字段**，**不改结构体 = NVS `history` blob 布局不变**（老存档继续可读）。
- 新增取证日志（用它判断历史有没有重复，不必猜）：
  - `[EV] 历史: 复用 'X' (旧位置 1 → 最前, 共 3 条, 按名字命中)` ← 顶替
  - `[EV] 历史: 新增 'X' (2/4)` / `(4/4, 已顶替最旧)` ← 又占一格

## 追加 · C5.1 修"同一只手柄被引导映射两次"（2026-10-02）

**现象**：连接完成后映射一次 → 过一会儿又提示"检测到新手柄，打开按键映射" → 又映射一次。

**根因：两条引导路径同时存在，但只有一个消费"待办"**

| 路径 | 位置 | 触发场景 | 是否消费待办 |
|---|---|---|---|
| A 页内衔接 | `page_gamepad.c` `conn_dlg_poll()` | 在手柄页里点连接 | ❌ **从不消费** ← bug |
| B 桌面 C5 | `page_main.c` `p_main_poll()` | 后台自动回连（人在桌面） | ✅ 取走 |
| 待办来源 | `bt_manager.c` `HIDH_OPEN` 分支 | 连接时该手柄**尚未 `mapped`** → `s_map_pending = true` | — |

于是：路径 A 打完向导后待办还挂着 → 用户退回桌面 → 路径 B 拿同一个（已过期）待办再弹一次。

**决策：两条路径都不能删，删的是"第二次触发"**

- 删 A → 页内连上却不给映射，要退回桌面才弹（更差）
- 删 B → 后台自动回连永远进不了向导 = 退回"连接过后不会自动映射"的老 bug

**改法（让两条路径互斥消费同一个一次性待办）**

1. `conn_dlg_poll()`：`if (bt_manager_take_map_pending(pnm, sizeof pnm)) start_key_mapping(ctx);`
   —— 只在"这手柄还没映射过"时才衔接向导，**并顺手取走**；已映射过的重连不再打扰。
2. `start_key_mapping()` 开头再 `bt_manager_take_map_pending(NULL, 0);`
   —— 覆盖"本页菜单 → 按键映射""桌面 C5""页内连接"全部入口，保证**任何入口都只引导一次**。

**行为基线（回归时照这个验）**

| 场景 | 期望 |
|---|---|
| 新手柄首次连接（页内 / 后台回连） | 提示连接成功 → 自动进向导 → **只进一次** |
| 已映射过的手柄重连 | 只提示"连接成功"，**不弹向导** |
| 用户主动重映射 | 手柄页菜单 → 「按键映射」仍然可用 |

> 教训：**"一次性待办"类标志必须"谁处理谁消费"**。只加一条消费路径（桌面 poll）而漏掉另一条
> （页内直接调用向导）时，多出来的那次引导不会报错，只会在用户退回某个页面时"迟到地"冒出来 ——
> 症状就是"同一个东西被处理两次"。新增触发入口时，先问：**这个入口消费待办吗？**
