# LAPP — 单文件应用资源包格式 v1

> **目标：一个 `.lua` 文件 = 代码 + 图标 + 元信息（名称/分类/简介/版本）。**
> 不需要额外文件、不需要文件夹约定；图标与信息都在同一个文件里，固件通过 API 解析。
>
> 关键设计：**文件头是注释** —— 固件可**静态解析**（不执行任何 Lua 代码）就能拿到
> 名称/分类/简介/图标；Lua 解释器则把头部当注释忽略。**因此普通 `.lua` 依然直接能跑**，
> 打包是"可选增强"，不是新门槛。

---

## 1. 文件结构

```
--@lapp v1                                   ← 格式标记 (存在即视为已打包)
--@app name=电脑诊断                          ← 列表/商店显示名 (UTF-8 中文可用)
--@app cat=系统                               ← 分类: 程序/游戏/系统/运维/网络/学习
--@app desc=按现象追问, 概率排序给出故障配件与排除方案
--@app version=1.0
--@app icon=<base64>                          ← 64×64 1bpp 位图, MSB first, 1=黑 (512B → 684 字符)

-- -- LAPP 图标自绘前奏 (打包器注入) --
local _APPICON = "<同上 base64>"
local function blit_app_icon(x, y, inv) ... end   ← 应用可调它把自己图标画到屏上
-- -- 以上为注入前奏, 以下为应用原始代码 --
<应用原始 Lua 代码, 一字未改>
```

- **头部**：`--@app <key>=<value>`，每行一条，位于文件最前。解析器只看前 ~4 KB。
- **图标**：与固件图标**同一规范**（`gen_main_icons_64.py` 的输出格式），可与 `ICON_*` 互转。
- **前奏**：打包器注入约 20 行 Lua，提供 `blit_app_icon(x, y[, inv])`，**读内嵌数据自绘**，
  不碰文件系统、不需要固件新 API 即可在应用内显示自己的图标。

## 2. 打包工具 `tools/pack_app.py`

```bash
# 用固件已有图标打包 (从 icons_main.inc 取, 与固件图标同源 → 视觉一致)
python3 tools/pack_app.py pack apps/lua/netdect.lua \
        --name "网络扫描" --cat "运维" \
        --desc "局域网主机/端口/弱口令检测" \
        --icon-from-main ICON_NETDECT

# 用自定义 PNG 打包 (64x64, 会按 <128 阈值二值化)
python3 tools/pack_app.py pack apps/lua/foo.lua --name "我的工具" --cat "程序" \
        --desc "..." --icon /Users/linit/Desktop/完美图标/应用管家/应用/我的工具.png

# 校验 / 查看
python3 tools/pack_app.py verify apps/lua/netdect.lua
# 取出图标 (PBM 纯文本, 无依赖, 直接能看)
python3 tools/pack_app.py unpack apps/lua/netdect.lua -o /tmp/icon.pbm
```

**可重复打包**：再次 `pack` 会先剥离旧头部与旧前奏，不会层层堆积。

**实测**（2026-09-22）：`diag.lua` / `morse.lua` / `calc.lua` 三个应用已打包，
打包后仍是合法 Lua（`tools/lua_check.py` 全通过），图标 512 B 可无损取回。

## 3. 固件侧要加的 API（**待实现**，接口已定）

新增组件 `components/services/apppack/`（L1 服务层，只依赖 `sd_scan`/stdio，**不依赖 os**）：

```c
/* apppack.h — LAPP 头部静态解析 (不执行 Lua) */
#define APPPACK_ICON_BYTES 512u          /* 64x64/8 */

typedef struct {
    char     name[48];                   /* 显示名 (UTF-8) */
    char     cat[16];                    /* 分类 */
    char     desc[96];                    /* 简介 */
    char     version[12];
    bool     has_icon;
    uint8_t  icon[APPPACK_ICON_BYTES];   /* 64x64 1bpp, MSB first, 1=黑 */
} apppack_meta_t;

/* 读取文件头若干行解析元信息; 无 LAPP 头部时返回 ESP_ERR_NOT_FOUND (调用方回退老逻辑) */
esp_err_t apppack_parse(const char *path, apppack_meta_t *out);
```

**接入点（各 3~5 行）：**

| 位置 | 改动 |
|---|---|
| `apps/pages/am_lua.c` 扫描 | 每发现一个 `.lua` → `apppack_parse()`；有元信息则用 `name` 作显示名（替代文件名）、带 `desc`、`icon` |
| `apps/pages/am_store.c` 扫描 | 同上（商店列表显示真图标 + 简介，而不是统一 `ICON_MINI_GAMES`） |
| 列表渲染（`page_app_manager.c`） | 若列表项带位图 → `st7305_blit_1bit()` 直画 64×64；否则回退现有 `icon_idx` |
| `os.h` 的 `os_app_t` | 可选加 `const uint8_t *icon_bmp`（非 NULL 时列表优先用位图） |

**成本估计**：新组件 ~150 行 + 三处接入各几行；无 Lua 侧改动、无破坏性（无头部即回退现状）。

## 4. 为什么这样设计（而不是自定义二进制容器）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **注释头部（本方案）** | 纯文本、可直接阅读编辑；普通 `.lua` 兼容；固件静态解析简单；git diff 友好 | 头部 ~700 字节冗余（图标 base64 比二进制大 33%） | ✅ **采用** |
| 自定义二进制容器（`LAPP\0` + 段表） | 体积最省 | 不能直接当脚本跑；不打包就无法用；工具链复杂；调试困难 | ❌ |
| 附随文件夹（`app/` + `icon.png` + `meta.json`） | 结构清晰 | **违背"一个文件"目标**；拷贝/安装要处理多文件；旧扫描逻辑要重写 | ❌ |

**核心权衡**：宁可多 700 字节，也要保住"**就是普通 Lua 文件**"这一性质 ——
写、改、调、diff、丢 TF 卡直接跑，全都不需要额外工具；打包只在你想要图标和商店元信息时做一次。

## 5. 与现有流程的关系

| 环节 | 未打包 `.lua` | 打包后（LAPP） |
|---|---|---|
| TF 卡丢包运行 | ✅ 直接跑 | ✅ 一样 |
| 商店源扫描 | 显示"文件名" | 显示**真名 + 简介 + 真图标** |
| 应用中心列表 | 统一占位图标 | 各自真图标 |
| 应用内自绘图标 | 需自己画 | 调 `blit_app_icon(x, y)` 一行 |
| 固件改动需求 | 无 | 需按 §3 加 `apppack` 服务（可选增强） |
