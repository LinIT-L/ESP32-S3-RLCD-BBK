### 1. 两条路线为什么选矢量

| | 预渲染位图瓦片（被否） | **矢量折线（采用）** |
|---|---|---|
| 存储 | 每个 zoom 档要渲一份 → 体积随档数线性膨胀 | **一份数据覆盖全部 zoom** |
| 清晰度 | 文字/线条放大就糊 | 任意缩放清晰；文字永远是固件 16px 点阵 |
| 设备算力 | 只贴图，最省 | 要实时投影+画线（靠 LOD + 行程合并压住） |
| 莆田市区实测 | z12≈0.9MB / z13≈3.4MB … z15≈52MB | **道路 161KB + 等高 120KB**（15×15.6 km 全域，全档通用） |

### 2. `.ltm` 文件格式（小端，与 Lua `string.unpack` 逐字节对齐）

```
Header            64 B
LOD 目录     20 B × nlod
要素表       16 B × nfeat   ← **按 cls 升序排列**
点表              首点 8 B + 后续 4 B/点
字符串表          UTF-8 路名, \0 分隔
```

#### Header（`<4sBBH` + `iiii` + `IIIIIIII` + `xxxxxxxx`）
`magic("LTM1") ver layer nlod | minlat minlon maxlat maxlon | off_lod off_feat off_pt off_str len_str nfeat npt crc32`

> ⚠⚠ **跨语言陷阱**：4 字节定长串 —— Python 写 `"4s"`，Lua 写 `"c4"`。
> 两边**不是同一个写法**：Python 的 `"c4"` = 4 个独立的 `c`（占 4 项），语义完全不同（踩过一次）。

#### LOD 目录（`<BBHIIII`）
`cls_max w zmin f_start f_end p_start p_end`

#### 要素表（v2: `<BBHIiiii`，**24 B**）
`cls npts name_off point_off | bbox(minx,miny,maxx,maxy)`

⚠ **bbox 单位是 1e-5 度**（不是微度！），相对文件 min。
⚠ v1 是 `<BBHIhhhh>`（bbox 为 i2，表 16 B），**只能装 0.3277°×0.3277°** —— 一个省装不下，
   v2 改成 i4（±21474°）。步长 16 → 24，设备端步长常量 `FEAT_LEN` 必须同步。

#### 点表
- **首点**：`i4` 微度，**相对文件（或块）bbox 的 min**（精度 0.11 m）
- **后续点**：`i2` 微度，**相对前一点**的增量（4 B/点，比全绝对省一半）
- ⛔ 相邻点距 > 32767 微度（3.3 km）会溢出 ⇒ 打包时**自动插共线点**
  （插的都是共线点，Bresenham 走同一条线，渲染结果逐像素一致）
- ⛔ 但插点会让点数变多，而 `npts` 是 **u8（≤255）** ⇒ 必须**先把点数预算算够再插**
  （见 `map_vec.pack_ready()`）；先插后压会顶穿 255

#### crc32
= **头部之后全部载荷**的校验和（不含头部）。无自引用，设备端 `crc32(file:sub(65))` 即可核。

### 3. 核心设计

#### 3.1 LOD = 按缩放分档（回答"根据放大尺寸显示清晰度"）
要素表按 `cls` 升序排 ⇒ 每个 LOD 的要素区间是**连续前缀** ⇒ **零冗余**，
同一条路不会为了多档被存多份。设备端切档只是换个下标区间，**不做任何计算**。

| LOD | zmin | cls≤ | 含义 |
|---|---|---|---|
| 0 | 0 | 1 | z≤12 省市级概览：高速/国道/省道 |
| 1 | 13 | 2 | + 次干道 |
| 2 | 14 | 3 | + 县道 |
| 3 | 15 | 6 | + 居住区路/内部路 |
| 4 | 17 | 7 | + 步道/小径 |

**等高线用自己一套 LOD**（语义相反：缩放越小只画越粗的等值线）：
cls0 = 整百米计曲线 · cls1 = 整四十米 · cls2 = 其余首曲线。文件里存了 LOD 表 ⇒ **自描述**。

> 分档目标是**每屏要画的要素条数大致恒定**。缩得越小可见范围越大，等级门槛必须收得更紧，
> 否则缩略视图反而比近景更慢（实测粗档下 z12 会飙到 14363 次跨界调用）。

#### 3.2 设备端渲染的四个提速点
1. **LOD**：见上。
2. **要素 bbox 预剔除**：bbox 存在要素表里，屏外的**连点都不解**。
3. **Bresenham 合并同主轴连续段**：一条水平路只调 **1 次** `app.hline`，不是 400 次 `app.px`。
   （逐点画 400 px 要 400 次 Lua↔C 跨界调用，这就是"卡"的来源）
4. **屏幕空间抽稀 MINSTEP=3**：相邻点投影后距离 < ~2 px 时跳过不落笔，
   **但画的时候是从"上次落笔点"直连到当前点 ⇒ 线不会断**。
   缩略视图下 OSM 节点间距本就有中位 **34 m**（z12 是 34.5 m/px，≈1 px），
   不抽稀一条路要摊成十几个 hline。抽稀误差 ≤ 2 px ≈ 线宽本身，视觉无损；
   放大后点距远超 2 px，**自动不抽**。

#### 3.2b ★ 整条折线一次调用：固件图元 `app.poly`（2026-10-05）
**先量**：一帧 z14 城市路网 `hline 3138 + vline 3083 = 6221` 次 Lua↔C 跨界，
**只落墨 17465 像素** ⇒ 平均每次调用只画 **2.8 像素**（run 太碎）。
根因是 Lua 侧逐段 Bresenham：一条路抽稀成很多 3 px 小段，每段再按"y 一变就收 run"
切成 1~2 px 的 run，每个 run 一次跨界调用。

**改法**：固件新增 `app.poly(raw[,w[,ct,cb]])` —— 抽稀后的屏幕点打包成 i2 点串一次传入，
Bresenham + 行程合并 + 边界裁剪全在 C 侧跑（`luat_lib_gfx.c`）。
Lua 侧每条折线 = **1 次 `string.pack` + 1 次 `app.poly`**。

| | 优化前 | 优化后 |
|---|---|---|
| Lua→C 跨界调用 | 6221 | **355** |
| 落墨像素 | 17465 | 17465（**逐像素零差异**）|

#### 3.3 坐标一律走整数（LUA_32BITS 的坑）
本项目 Lua 编的是 `LUA_32BITS=1` ⇒ `lua_Number` 是 **float**（只 ~7 位有效数字）。
`lon_e6 = 119011000` 有 9 位，直接进浮点就被截断（float 在 1.19e8 量级的间隔是 **8 微度 ≈ 1 m**）。

做法：**全程微度整数**，先做 `lon_e6 - 中心lon_e6`（精确整数减法，差值很小）再乘缩放系数。
点表的相对 min 也必须在设备端**加回 minlat/minlon**（`string.unpack "i"` 与 HDR 的 `"i"` 都是整数子类型，加减精确）。

#### 3.4 投影 = 墨卡托局部线性化
每度经度占多少像素在墨卡托里**与纬度无关**（共形投影性质）：
```
kx = 0.711105 × 2^z        （156543.034 / 111320 的倒数）
ky = kx / cos(lat)
```

### 4. PC 侧编译器 `tools/map_vec.py`

```
roads   : Overpass `way["highway"](bbox); out geom;`  → 裁剪 → DP 抽稀 → 按 cls 排序 → 打包
contour : terrarium DEM(z13) → marching squares → 断线串接 → 裁剪/抽稀/去碎 → 打包
preview : 反向解析 + **与设备端同算法**（同 LOD/同抽稀/同固件字库）渲一张样张
info    : 打印 bbox / 各等级条数 / 各 LOD 区间
```

⚠ **`out geom` 返回的是整条 way 的完整几何**，不是 bbox 内的部分 —— 一条跨区国道能把数据范围
拖出几十分之一度，撑爆要素 bbox（`i2` / 1e-5 度，上限 0.327°）。必须做 Liang-Barsky 裁剪。

⚠ 等高线的 `cls` 别用"整五十"分档：等高距 20 m 时 `20k%50==0` 与 `20k%100==0` 等价
（都要求 `k%5==0`），**中间那一档会整档空掉**。

  点收藏项 → `app.dlg.confirm("开始导航到 XXX?")`（**复用系统弹窗**）→ 画连线 + 底部距离条，
  30 m 内自动判「已到达」。
- **收藏自动命名**：落点 400 m 内最近的一条**有名字**的路 ⇒ 存成"文献路"而不是"点1"。
  持久化 `app.nvs` 单键 `fav1`，行格式 `lat_e6,lon_e6,name`。

#### ★ 点要素：地标 / 收藏 / 导航目标（2026-10-05）
地图上现在有**三类"点"**，都带名字：

| 类型 | 数据来源 | 标记 | 名字 |
|---|---|---|---|
| **地标** | OSM `place/amenity/tourism/historic/railway=station` → `putian_poi.ltm` | 5×5 实心菱形 | **12px 小字** |
| **收藏** | 本机 NVS（`fav1`），不占地图文件 | 5×5 空心方块 | 16px |
| **导航目标** | 点收藏后确认导航 | 实心圆 + 外圈（最醒目） | 16px + 距离 |

**地标图层**（`tools/map_vec.py poi`）：莆田市区实测 **90 个地标 / 4.1 KB**。
只收"人话能当地标"的（行政区/政府/医院/车站/学校/宗教/场馆/古迹），
⛔ **不收 shop/restaurant/cafe** —— OSM 在国内本来就稀，收了也全是空白，反而把真地标挤没。
⛔ Overpass 查询**必须按具体值用正则筛**；写 `node["amenity"]`（不带值）会直接 **504 Gateway Timeout**。

**统一标注层**：路名 / 地标 / 收藏 / 目标**一起收集、一起避让**，否则会互相压。
优先级 `prio` 越小越先摆：目标(0) > 收藏(1) > 地标(2+cls) > 路名(10+cls)。
还要**让开左右两列浮动按键**（名字被按钮压住 = 等于没标）。

⛔ 点要素的坑：要素表布局是 `<BBHIhhhh`，`poff` 是 **i4** 但 bbox 四个字段都是 **i2**。
写成 `"<BBHII"` 会把 `bx0`(2B)+`by0`(2B) 当成一个 i4 读 → 坐标全乱（地标一个都画不出来）。

#### 从参考项目抄了什么（已落地）
| 参考位置 | 拿到的东西 |
|---|---|
| `lib/compass/compass.cpp` | **六轴只用来给磁力计做倾斜补偿**（pitch/roll → hx/hy 旋转），朝向本身只能来自磁力计 —— 决定了"要不要上六轴"的结论 |
| `lib/utils/climbAnalyzer.cpp` | 爬升必须先**平滑/迟滞**再累计，否则 GPS 高度噪声会把爬升虚高一大截（我们用了 ±3 m 迟滞） |
| `lib/gpx/` | 轨迹用**标准 GPX 1.1** 落盘，别的软件能直接导入 |
| `lib/utils/navigation.hpp` | 到达判定（`isFinished`）；偏航 50 m、重算路由等重逻辑暂不做（我们是直线导航） |
| `lib/settings/` | 设置页的字段取舍：只留对本地图有用的（单位/图层/数据/GPX） |
| `lib/maps/src/maps.cpp` | 矢量格式的 `RenderBatch` 批量同色段 ≈ 我们的"同主轴行程合并" |

#### ⛔ 本轮踩到的坑
1. **`app.dlg.list` 返回值是 0 基下标**，`confirm` 的右"取消"是 **1**（不是 -1！-1 只出现在超时/BACK/列表返回行）。模拟器一开始也写错了，会掩盖真机 bug。
2. **`app.textsb/texts/textm` 是纯 ASCII 字体** —— 值里带汉字（"11 颗"/"设置"）会画成 `?`，必须换 `app.mix` / `app.zhsm`。
3. **弹窗由内核层消费触摸**，页面 `poll()` 提前 return 时就没人处理；模拟器要在 `call("poll")` 前替它消费一次，否则弹窗永远关不掉。
4. **被引用的 local 必须放在使用点之前** —— `gpx_save` / `TRACK_MAX` / `render` 都因为顺序错过一次（`attempt to call a nil value (global '...')`）。
5. **LUA_32BITS 下不能用 CRC32 做下载校验**：值常 > 2^31，既拿不到精确整数，也过不了 `%08x`。改用 **Fletcher-16 + 字节数**双检。
6. **模拟器假 GPS 的 `mps100` 换算错了 10 倍**（`kmh10` 是 0.1km/h ⇒ mps100 = kmh10/36*100），配速显示成 0'13" 而不是 2'51"。**假数据算错比没有假数据更危险**。
7. **按键可点性要和绘制一致**：只在某页画的按键，就不要在别的页判命中，否则"画出来却点不动"。

### 9. 省级地图（2026-10-05）

#### 9.1 为什么必须是"1 个 bin + 索引"，而不是"一瓦片一个 .ltm"

| 方案 | 问题 |
|---|---|
| 一个 `.ltm` 装整省 | 18 MB，而 `app.fs.read` 上限 512 KB ⇒ **根本读不进来**；要素 bbox 也放不下 |
| 一瓦片一个 `.ltm` | 福建 = 607 路块 + 564 标块 = **1171 个 HTTP 请求**，设备端一个个下 20 分钟打不住，每个还要重来一遍 TLS 握手 |
| ✅ 块平铺进一个 `.bin` + 索引 | 一次请求下完整个省；设备端 `app.fs.read_at(bin, off, size)` 只读当前视口那几块 |

产物（`tools/map_prov.py`）：

```
fj.json   索引: 顶层标量 + tiles:[{x,y,o,s,po,ps}]  (一行一块, 道路与地标共用网格键)
fj.bin    [省级概览][地标块...][道路块...]  —— 顺序平铺, 偏移写在 json 里
```

设备端策略：`z <= ztile-1(10) 用概览` / `z >= ztile(11) 按视口读块（±1 块边距）`。

#### 9.2 实测数据（福建省，`--tile 0.15 --ovcls 1 --ovtol 6e-3 --tol 1e-5 --maxcls 6`）

| 项 | 值 |
|---|---|
| 源 | `download.openstreetmap.fr/extracts/asia/china/fujian-latest.osm.pbf`，**46.5 MB** |
| 规模 | 671 万 node / 45 万 way |
| 解析 | `osmium.apply_file(locations=True)`，**13 秒** |
| 产出 | **18.0 MB**：概览 605 KB + 610 块（路中位 13.8 KB / 最大 364 KB）+ 564 地标块（中位 0.5 KB） |
| 索引 | `fj.json` 46.7 KB |
| 下载 | **1 次请求**（流式落盘），非 1171 次 |

#### 9.3 三个把体积压下来的关键优化（都是**必须有**，不是可选）

1. **同名 way 溶解 `dissolve_ways()`** —— 体积大头是**要素表 24 B/条**，而 OSM 把一条国道
   打成几百段。福建 cls≤1 有 **46,065 条 way**，光要素表就 1.1 MB。
   两级策略：同名同级直接串；**无名路走 strict（只在"共享端点恰好连 2 条"时接）**——
   第一版只做同名，46065 只降到 24172（**多数干道压根没名字**），加了 strict 才降到 13110。
2. **概览层降级**：`--ovcls 0`（只高速/国道）→ 384 KB；`--ovcls 1`（含省道）→ 605 KB。
   最终选 1 —— 384 KB 那版在福州一带只看得见 3 条高速，太稀疏。
3. **块缩到 0.15°**：最大块 555 KB → **364 KB**（全部落进单次读上限），中位 26 → 13.8 KB。

#### 9.4 地标为什么按块分（不是全省一个文件）

全省 10,064 个中文名 ⇒ 字符串表 120 KB，而 `nameoff` 只有 **u16（0xFFFF）** ⇒ 打包直接抛
`字符串表超 64KB`。分到块里每文件只有十几~几十个名字，顺带把设备端每帧的遍历量也降下来了
（10064 个要素每帧 unpack 一次 ≈ 20 ms，不可接受）。

#### 9.5 为它新增的固件 API

| API | 为什么 |
|---|---|
| `app.fs.read_at(path, off, len)` | 按偏移读一段（≤1 MB）。整文件读上限 512 KB，而 bin 有 18 MB |
| `app.fs.size(path)` | 读之前先问大小 |
| `app.fs.mkdir(path)` | 逐级建目录（幂等） |
| `app.net.fetch_start(url, ms, path)` | **给了 path 就边收边写文件**（内存只留 8 KB 搬运缓冲），并**核对 Content-Length**（短包必拒） |
| `app.net.fetch_got()` | 已收字节数（画进度条）；18 MB 单文件要 90 秒，界面必须让用户看到"在动" |
| `app.json.pick` 上限 512 → **2048** | 索引有 610 行，512 会**静默截断**成"地图下了一半" |

#### 9.6 ⛔ 本轮踩到的坑（都已在代码里标注）

- **要素 bbox 单位是 1e-5 度，不是微度**。`pack_tile` 少除 10 ⇒ 块能解析、要素数也对，
  但每个要素被放大 10 倍，裁剪全判"在视口外" ⇒ **地图一片空白**。靠出样张才发现
  （症状是"0/3133 条"）。
- **先插点再压点 = 顶穿 255**。`npts` 是 u8；`pack_ready()` 必须把"插点开销"算进预算
  （插点开销 ≈ 折线总长/3.3 km，与保留点数无关），否则 `struct.pack` 抛
  `'B' format requires 0 <= number <= 255`。
- **要素表步长与格式串必须同步**：v2 把 bbox 从 i2 改成 i4，表从 16 B 变 24 B，
  `map.lua` 里三处 `i * 16` 没跟着改 ⇒ 遍历整体错位。现在统一走常量 `FEAT_LEN`。
- **`dl_after_index` 调 `dl_next_file`，而后者定义在之后**（`local` 只对声明之后可见）
  ⇒ 拿到 nil，一点"联网下载"就崩。**这条下载分支以前从没被走到过**，所以一直没暴露。
  同时 `D.mirrors` 也从来没被赋值过（老代码只存进 `M.mirrors`）。
- **`local PAGES` 在删掉顶部页签时就没了**，而 `action()` 还在引用 `#PAGES` ⇒ 一按左右键就崩。
- **`map_reload` 成功后没清 `err_kind`** ⇒ 包已经就绪了界面还卡在"未找到地图数据"。
- 模拟器两个坑：`fetch_poll` 必须返回 **bytes**（返回 `str` 会被 UTF-8 编回去，二进制全坏）；
  计数器属性别和方法同名。

#### 9.7 复现命令

```bash
bash tools/dl_chunks.sh <pbf_url> cache_map/fujian-latest.osm.pbf 16   # 16 路 Range 并行
python3 tools/map_prov.py --pbf cache_map/fujian-latest.osm.pbf \
        --prefix fj --name 福建省 --outdir dist/map/fj
python3 tools/map_prov_check.py --dir dist/map/fj --center 25.4335,119.0110 \
        --zoom 14 --out docs/screenshots/福建样张.png     # 端到端反解自检 + 样张
python3 tools/map_pack.py            # → dist/tf/Map/ + store/maps/ + store/maps.json
python3 tools/sync_apps.py map       # → build/apps_l.bin (含地图应用)
```

`dl_chunks.sh` 存在的理由：`download.openstreetmap.fr` 单连接被限速 5~18 KB/s，
46 MB 单线程要 45 分钟；16 路并行 187 秒。
⚠ **必须按真实 Content-Length 分块** —— 估错总长会少下 20 MB，而拼接错误只有 osmium 解析
blob 时才报 `failed to uncompress data`，不早报。

### 10. 别人是怎么存地图的（2026-10-05 调研）

#### 10.1 六种主流格式的结构对照

| 方案 | 容器 | 空间定位 | 几何编码 | 分档（LOD） | 压缩 |
|---|---|---|---|---|---|
| **MBTiles** | SQLite 单库 | `tiles(z, x, y)` 主键索引 | 栅格 PNG / MVT | **瓦片金字塔**（每档独立存） | 每瓦片 gzip |
| **PMTiles** | **单文件 + 偏移**（127 B 头） | 根目录 + 可选叶子目录；**TileID 按 Hilbert 曲线编号** | MVT | 瓦片金字塔 | 目录/元数据 gzip·brotli·zstd；瓦片单独压 |
| **MVT (Mapbox)** | 不定义容器 | 由外层瓦片容器给 | **protobuf**：keys[]/values[] 字典 + tags 索引对 + **zigzag varint 几何命令**，格网 4096 | 由瓦片 z 决定 | 外层压 |
| **Mapsforge `.map`** | 单文件 | **每个 zoom 区间一个子文件**，子文件内 **5 字节索引项**（1 bit 水域 + 39 bit 偏移）→ **O(1) 定位瓦片** | 微度整数 + **VBE 变长** + **单 delta / 双 delta**（逐条选更省的） | 每瓦片带**zoom 表**（各档要素计数）+ 要素**按优先级存**（路在前、楼在后）⇒ 低档画到第 N 条就停 | 无 |
| **Organic Maps `.mwm`** | 单文件（一区域一文件） | 按 zoom 的 **bucket 网格** | delta varint | 几何带 **scale range**；要素带 **rank**（重要性）决定标注取舍 | 无 |
| **OsmAnd `.obf`** | 单文件 | 自有索引块 | delta varint + tag 字典 | 多档 | 自有 |
| **Garmin IMG** | 文件系统式 | 按分幅（TRE 分割表） | 自有 | 多档 | 无 |

#### 10.2 五条共性（也正是我们缺的）

1. **单区域一个文件 + 内部偏移表**（PMTiles/Mapsforge/MWM/OsmAnd 全是）。我们 v3 的
   `.bin + 索引` 就是这个形状 —— 独立收敛到同一个答案。
2. **空间索引，绝不线性扫**（瓦片金字塔 / 5 字节索引项 / bucket 网格）。
   **这是本轮补上的**（见 §11）。
3. **变长整数 + delta（有时双 delta）**。我们目前是"定长 i2 增量"：4.37 B/点。
   Mapsforge 允许逐条在单/双 delta 之间挑，实测能压到 ~1~2 B/点。
4. **tag/名字字典**：把重复的键值映射成小整数 ID（Mapsforge 在文件头存 POI/way 两张 tag 表；
   MVT 每层带 keys/values 数组）。我们有"每块独立字符串表"，够用但没跨块共享。
5. **重要性排序**（zoom 表计数 / MWM 的 rank）：低档只画前 N 条。
   我们的 LOD 前缀 + `cls` 就是同一件事，效果等价。

#### 10.3 术语对照：他们 ↔ 我们

| 他们 | 我们 |
|---|---|
| MBTiles 瓦片金字塔 / Mapsforge 子文件 / PMTiles 的 z | `.ltm` 的 **LOD 前缀**（要素按 `cls` 排序 ⇒ 每档是连续前缀，**零冗余**，比"每档单独存"省） |
| Mapsforge 每瓦片 5 字节索引项 | `fj.json` 里每块的 `(o,s)` + v3 块内 **64×64 网格索引** |
| Mapsforge 每瓦片 zoom 表（要素计数） | LOD 目录里的 `f0/f1`（要素区间）+ `p0/p1`（点区间） |
| PMTiles 的 `Clustered` / Hilbert 编号 | 块按 `(tx,ty)` 行主序平铺 —— 平移时局部性已经够好，Hilbert 收益很小，**不做** |
| MVT 的 4096 格网 + zigzag varint | 微度整数 + i2 delta（**精度更高**：格网 4096 在 0.15° 块上只有 4 m/格，我们 0.11 m） |
| PMTiles 的 gzip/brotli 目录 | 我们**整块不压**（见下：实测只有 1.43x，不值） |

#### 10.4 测过但我**没做**的两件事（附数据，别重复踩）

- **整块 gzip**：实测 17.61 MB → 12.31 MB，只有 **1.43x**。因为点表是 delta 后的低位随机数，
  **压不动（1.11x）**；能压的是要素表 1.74x、字符串表 2.35x。省 5 MB 但每块要 inflate，
  还要在固件里引 zlib/miniz。**判：不值**（TF 卡不缺这 5 MB）。
- **把块内 bbox 从 i4 收成 i2**：块只有 0.15° = 15000 单位(1e-5°)，i2 的 32767 装得下
  ⇒ 要素表 24 B → 16 B，全省省 **4.0 MB（-23%）**。
  但会让格式多一个变体（概览必须留 i4），而"格式变体不同步"正是这个项目最容易出错的地方
  （今天已经因为步长 16/24 踩过一次）。**判：先不做**，等真要省下载时间再加。

### 11. 本轮优化：空间索引（v3）

#### 11.1 为什么（先量再改）

插桩实测每帧**扫描的要素数** vs 实际画出来的：

| 缩放 | 帧时间 | 扫要素 | 命中 | 命中点 |
|---|---|---|---|---|
| z16 | 8.5 ms | **9307** | **31** | 179 |
| z11 | 21.8 ms | 3011 | 961 | 5352 |
| z10 | 16.5 ms | 13110 | 594 | 3212 |

**z16 每帧解 9307 个要素表项，只为了画 31 条（300:1）**。Lua 里一次 `string.unpack`
≈ 0.5~1 µs ⇒ 白烧 5~9 ms。根因：`draw_layer` 必须逐个 unpack 当前 LOD 的**全部**要素表项
再判 bbox —— 缺一层空间索引。

#### 11.2 结构（v3 = v2 + 尾部追加索引段；头部 56..59 是原来的填充位）

```
u8  iver | u8 pad | u16 nx | u16 ny      6 B
i4  ox, oy, cw, ch                      16 B   网格原点(微度, = 文件 min) 与格尺寸
u32 nsid | u32 gcount                    8 B
u32 cell_start[nx*ny+1]                        前缀和 → 第 c 格的条目区间
u16 fid[nsid]                                  要素下标
u16 gid[gcount]                                "跨格太多"的长要素，每帧都扫
```

**关键设计：要素只登记在 bbox 的「最小格」里，查询时把格区间向外扩 2 格。**
数学上等价于"每格都登记"，但天然不会取到重复要素 —— 否则要在 Lua 里维护一张
`nfeat` 大小的去重表（几千要素就是几百 KB）。索引也因此更小（每要素只占 1 条 u16）。
跨格 > 3 格的（溶解后的整条国道）进 `gid`，每帧扫一遍 —— 它们本来就几乎总在视口里。

格数 `nx=ny=⌈√(nfeat/3)⌉`（上限 64，目标每格 ~3 条）。
⚠ 格数别小：16×16 时 z16 只能过滤 81%，50×50 能过滤 93%（"外扩 2 格"的开销在小格数下被放大）。

#### 11.3 效果

| 缩放 | 线性扫解表 | 索引解表 | 降幅 |
|---|---|---|---|
| z16 | 9307 | **662** | **14.1x** |
| z15 | 9307 | 800 | 11.6x |
| z14 | 3208 | 700 | 4.6x |
| z12 | 2130 | 766 | 2.8x |
| z11 | 3011 | 1360 | 2.2x |
| z10 | 13110 | **1035** | **12.7x** |

设备端每次解表 ≈ 0.5~1 µs ⇒ **z16 省 ~6 ms/帧、z10 省 ~8.5 ms/帧**。
（z11 只有 2.2x 是因为视口几乎覆盖了整块，"过滤"本来就没多少可过滤的。）
代价：文件 +5%（19.1 MB），索引约占 6%。
z11 顺带说明：1360 解表 vs 961 命中，已经非常接近理论下限（≈ 视口内要素数）。

#### 11.4 ⛔ 两个坑

- **索引段偏移**：`<BBHH` 是 **6 字节**不是 4 ⇒ `ox` 在 off 6、`nsid` 在 off 22、
  `cell_start` 在 off 30。算错 2 字节 ⇒ `string.unpack` 报 `data string too short`。
- **`table.sort` 不是稳定排序**：加了索引之后**要素遍历顺序变了**，于是"同优先级"的标注
  并列名次换人，画面像素跟着变 —— 看起来像索引画错了，其实只是排序没定序。
  修法：`place_labels` 的排序键补成 `(p, y, x, s)` **全序**；
  `collect_road_labels` 也先 `table.sort(names)`。
  **这个坑对任何"改变遍历顺序"的优化都成立**，值得记一条。
- **等价性必须逐像素验**：加了 `LTM_NOIDX` 开关（强制退回线性扫），
  同数据同视口跑两遍比对帧缓冲，**z16/z15/z14/z12/z11/z10 六个档全部逐像素一致** ✓。

#### 11.5 还没做的（下一位接手时按价值排序）

1. **几何变长编码**（单/双 delta + zigzag varint）：点表 4.37 B/点 → 估 1.5~2 B/点，
   全省再省 **~6 MB（-30%）**。解码要放在 **C 侧**（`app.poly` 加一个"变长点串"入参变体），
   否则 Lua 解码成本会吃掉收益。
2. **块内 bbox 用 i2**：省 4.0 MB（见 §10.4），但要接受格式多一个变体。
3. **跨块共享名字字典**（Mapsforge 那样在文件头放一张 tag 表）：现在每块各存一份，
   全省字符串表 0.19 MB —— **收益太小，不做**。
4. **搜索索引**（OsmAnd/MWM/Mapsforge 都有独立的 POI/地址索引，Mapsforge 用 SQLite）：
   现在没有"找最近的加油站"这类功能，需要的话得单独做一层。

### 2. 数据链

```
espsdr_capture(2048, 80MSa/s)          ← 64KB 突发缓冲里的前 2048 个样本
   ↓ 取 I/Q (bit19-10=I, bit9-0=Q, 有符号10bit, /512 归一化)
   ↓ 去 DC (减均值) + Hann 窗
dsps_fft2r_fc32 + dsps_bit_rev_fc32     ← esp-dsp, 走 S3 向量指令
   ↓ dB = 10log10(|X|²)   (fftshift: bin k ↔ f = (k-N/2)·80M/N)
   ↓ 2048 bin → 400 列 (每列取区间**最大值**, 窄带信号不会被抽掉)
   ↓ 中心 ±1 列做 DC 修补
   ↓ 指数平均 (AVG 1/4/16)
上半屏: 每列从底部填到该列 dB     下半屏: 130 行瀑布位图整块 blit (1bpp)
```

**性能预算**（S3 @240MHz）：采集 2048 点 ≈ 26 µs · FFT 2048 点 ≈ 1~2 ms · 绘制 ≈ 1~2 ms
→ 刷新节拍设 **100 ms（10 Hz）**，CPU 占用个位数百分比。

### 4. 关键实现点（都是踩过的坑）

1. **64KB SRAM 必须是保留区**：`SOC_RESERVE_MEMORY_REGION(0x3fcd0000,0x3fce0000,s3_rf_dump)`
   （宏在 IDF 的 **`heap_memory_layout.h`** 里 —— 官方那行 include 很容易漏，漏了编译就报
   "expected declaration specifiers before numeric constant") + `sram_guard.ld` 三条 ASSERT。
2. **采集序列顺序不能改**：填哨兵 → 配 pack 寄存器(0x60033d90) → 把 0x600c101c 的
   MAC_DUMP_USAGE 置 4（**这块 SRAM 交给 modem**）→ 写控制字(0x60033d5c) → 再写 `ctrl|(1<<19)` 触发
   → 轮询 bit18 完成（超时 20 ms）→ 关控制字 → **把 SRAM 还给 CPU**（异常路径也要还，否则下次抓不到）。
3. **增益符号在 IDF 版本间改过名**：官方用 `librftest.a` 的 `force_rx_gain(manual,code,0)`，
   但 IDF **默认不把 librftest.a 挂进链接** → 链不过；`libphy.a` 里有等价的
   **`phy_force_rx_gain(manual, code)`**（官方 S31 路径用的就是它）→ 本项目用后者。
4. **射频独占**：进入时 `wifi_manager_disable()` → `os_hw_request(OS_HW_WIFI)` → espsdr_enter()
   （起 WiFi NULL 模式 + 混杂模式 + PHY 上电序列）；退出反向归还，并按进入前的状态
   `wifi_manager_enable()` 恢复用户联网。**期间 WiFi/BT 不能用**。
5. **采集窗口内不要写 flash**（NVS/日志落盘会禁 cache）→ 本页热路径刻意不打日志。
6. **零中频的固有毛病**：正中一根 DC 尖刺 + 镜像 → 去均值 + 中心 ±1 列修补；
   增益跳变会毁幅度 → 想稳定就切**手动固定增益**。

| # | 看什么 | 期望 |
|---|---|---|

### 6. 已知限制（别指望它做不到的事）

- **量化 10 bit** → 动态范围有限，强邻道 + 弱信号会吃力
- **模拟带宽 ~13–54 MHz**，两端有滚降 → 显示跨度默认 ±16 MHz（避开边缘）
- **单芯片单天线 → 做不了测向**（那要 ESPARGOS 那种多天线相位相干）；配定向天线可手动扫方向
- **与 WiFi/BT 互斥**（射频独占）
- **幅度是相对的**：没做绝对 dBm 校准，用于"比较大小/找干扰"足够
- 寄存器属**未文档化**功能，Espressif 未承诺 → 换 IDF/芯片版本要重验

#### 0. 一句话

Espressif 的 ESP32 里**藏了一条没写进文档的通路**：固件可以**绕开** WiFi/蓝牙的固定硬件调制解调器，
把**射频原始 I/Q 采样**直接抓进内存。于是**几块钱的 ESP32 就成了一台软件无线电（SDR）接收机**，
**不用加任何硬件**。

---

#### 1. 它抓的到底是什么：**原始 I/Q 基带样本**

##### 1.1 射频链在哪一步被"截"
```
天线 → LNA/混频 → 低通滤波 → 【ADC 采样】 → ⛔硬件调制解调器(WiFi/BT) → 协议栈
                                    │
                                    └─★ ESP-SDR 从这里的"调试出口"把数据旁路进 SRAM
```

##### 1.2 I/Q 是什么，为什么"原始"这么关键
- ADC 采出来的是 **I（同相）+ Q（正交）两路**数字基带 → 合起来是一个**复数**
- 复数同时带 **幅度和相位** —— **相位**才是能做"相干处理/测向/雷达"的东西
- 正常路径下，ADC 数据**直接喂给硬件调制解调器**（去解 OFDM / 蓝牙跳频），软件只能看**解出来的结果**
- ESP-SDR 让软件拿到**调制解调器之前**的数据 → 空口上的**一切**都在里面（信号、干扰、噪声、脉冲）

##### 1.3 每个样本 32 bit 的构成（他们的实测格式）
| 位 | 含义 |
|---|---|
| bit 19–10 | **I**（有符号 10 bit，−512…+511）|
| bit 9–0 | **Q**（有符号 10 bit）|
| bit 27–20 | 当前接收增益（增益表索引）|
| bit 31–28 | 大概是 AGC 状态机内部状态 |

##### 1.4 怎么搬进内存（ESP32-C61 为例）
SRAM 分 bank → 固件占**两块 bank 做成环形缓冲**：一块归调制解调器写、一块归 CPU 拷贝搬走，
固件盯硬件写指针，写满一块就换角色 → 连续采集不丢。

#### 2. 硬指标（他们页面给的）

| 项 | 数值 |
|---|---|
| 调谐范围 | **2.2–2.7 GHz**；ESP32-C5 另有 **4.8–6.0 GHz** |
| 采样率 | **最高 80 MSa/s** |
| 模拟接收带宽 | **~13–54 MHz**（随芯片/滤波器设置）|
| 增益 | 内置 **AGC** 或手动固定增益 |
| 数据率 | 80 MSa/s × 32 bit = **2.56 Gbit/s** 写进 SRAM |
| 支持芯片 | **原始 ESP32 / C3 / C5 / C6 / C61 / S2 / S3 / S31** |
| 出口 | 大多数型号走 **UART**（低占空比）；**S31 走千兆以太网** |
| 持续能力 | S31 上 **8 / 16 MSa/s 持续**；社区玩家 h0m3us3r 用 **FPGA 搬运**，在 **S3 上做到 80 MSa/s 持续** |
| 超规格 | C61 的 PLL 实际能到 **2.7 GHz**，覆盖 **LTE band 7 / 5G NR n7（约 2.6 GHz）** |

#### 3. 拿到这些数据，能干什么（重点）

##### 3.1 当**频谱分析仪**用（最直接、马上能用）
浏览器（Web Serial）里出**实时频谱 + 瀑布图**：
- 看 2.4G 上**谁在说话**、占多宽、多强 → 判断哪个 WiFi 信道最挤
- 找**干扰源**：微波炉、劣质电源、无线摄像头、坏掉的 AP
- 看 BLE 信标/邻居 AP 的密度（做"无线环境体检"）
- **对你做硬件的意义**：看自己板子发 BLE/WiFi 时的**功率、频偏、占空比、有没有跑飞/杂散**；
  配一个定向天线还能粗测"信号从哪个方向来"（找干扰）

##### 3.2 抓**任意 2.4G 协议**（这是 CSI 做不到的）
原始 IQ 里包含空口一切：**BLE 广播/连接包、Zigbee、802.11b/g/n（含多空间流）、
私有 2.4G（无线鼠标键盘、遥控、航模、无线麦、部分胎压/门磁）**。
有了 IQ，你可以在电脑上**自己写解调器**（GNU Radio / Python / Universal Radio Hacker / inspectrum），
甚至**逆向一个私有协议的编码**（比如自家的无线遥控、遥控车）。

##### 3.3 **相位相干** → 测向 / 定位（他们最核心的放大器）
- 单台接收机只能测"有没有、多强"；**多台相位同步**才有**相位差** → 才能算**到达角（AoA）** → 才能**定位**
- 以前 CSI 方案只能定位"**能发 WiFi 的**"设备；现在能定位**任意 2.4G 信号源**
  （BLE 标签、遥控器、无人机图传、甚至**干扰源**）
- 硬件：**ESPARGOS One** = 8 颗相位同步 ESP32 + **8 个双极化贴片天线** + λ/2 间距（60 mm）+ PoE 以太网；
  还能多阵列拼成 **6×4 = 24 天线** / **8×4 = 32 天线** 的大口径 → 角分辨率更高
- 用途：室内定位、资产追踪、遥控/无人机测向、**频谱监测执法找干扰源**、手势感知

##### 3.4 **无线感知**（ESPARGOS 的本行）
从无线信道的微小扰动反推**环境与人体**：动作识别、**呼吸/心跳检测**、人数统计、跌倒检测、穿墙感知。
原来用 WiFi CSI（20/40 MHz）已能做；加上 IQ 后可以用**非 WiFi 专用波形**做感知（例如脉冲波形对微动更敏感）。

##### 3.5 **（脉冲压缩）雷达**
自己发一个**已知波形** + **相干接收** → 做匹配滤波 → **测距/测速**（这就是雷达）。
ESPARGOS 支持**相干发射**；IQ 相干处理能出距离像/多普勒像。
用途：手势雷达、距离/液位测量、微动检测。

##### 3.6 **安全研究 / 频谱监测**
- 看**谁在发、发了多少、什么节奏**（不涉及破解加密 WiFi 内容，是"看得到空口行为"）
- 检测**攻击**：deauth 洪水、假 AP/邪恶双子、BLE 欺骗、干扰器
- 设备指纹/存在检测（靠信号特征识别机型）
- 反过来也是**安全提醒**：2.4G 上如果传明文，附近一颗 ESP32 就能抓 → 问题在"不该明文传"
  （他们 FAQ 专门解释了"这不是后门，是未文档化功能"）

##### 3.7 **超规格监听蜂窝频段**
C61 可到 2.7 GHz → 覆盖 **LTE band 7 / 5G NR n7（≈2.6 GHz）** → 看蜂窝信号强度与干扰、做被动信号分析。

##### 3.8 **教学 / 科研 / 算法验证**
- 最便宜的 SDR 教学硬件：几十元 vs 动辄上千的多通道 USRP 方案
- 能拿**真数据**验证：解调、同步、滤波、MIMO、波束成形、定位算法
- 他们的 `pyespargos`（Python 库）可以直接把 **CSI 实时流**拉进你的应用做实验

##### 3.9 **接进成熟生态**
- **SoapyESPSDR**（S31 + 千兆网）→ 直接进 **GNU Radio / gqrx / CubicSDR / SDR#**
  → 录 IQ 文件、接力现成的解调/解码模块 → 说明它**能当正经仪器链路的一环**，不只是玩具演示

#### 4. 和"以前的 CSI 方案"的本质区别

| | **CSI**（他们以前的做法）| **Raw IQ**（这次新开的）|
|---|---|---|
| 数据是什么 | 每个 OFDM 子载波的**幅度/相位**（已经信道估计过）| **时域复数样本流** |
| 只对什么有效 | **WiFi 的特定前导符号**（L-LTF / HT-LTF）| **任何信号**（ADC 原始输出）|
| 能看哪些协议 | 仅 802.11g/n/ax（**802.11b 和多空间流不支持**）| **BLE / Zigbee / 私有 2.4G / 干扰** 全都能看 |
| 带宽 | 20 MHz（信道绑定 40 MHz）| **~13–54 MHz** 模拟带宽 |
| 在哪加工 | 芯片里已经加工完了 | **你在电脑上想怎么算就怎么算** |
| 能力上限 | 只能定位"能发 WiFi 的" | 定位 / 解调 **任意信号源** |

#### 5. 怎么上手（4 步）

1. **拿一块支持的板子**（你的 **ESP32-S3 就在列表里**）→ 用他们的**浏览器 flasher** 刷 ESP-SDR 固件
   ⚠ **别刷到正在跑 LinTOS 的那块板**（会覆盖固件）；找块空闲板，玩完再刷回
2. 拔掉、等 5 秒、插回 → 打开 **ESP-WebSDR** 网页 → 选设备 → 看**实时频谱/瀑布图**
3. 想认真玩 → **S31 + 千兆以太网 + SoapyESPSDR** → GNU Radio / gqrx 里当接收机用、**录 IQ 文件**，
   再用 Python（numpy/scipy）、inspectrum、Universal Radio Hacker 离线解协议
4. 想做定位/感知 → **ESPARGOS One**（Core Kit 单阵列 8 天线；Aperture Kit 拼 24/32 天线）+ `pyespargos`

#### 6. 局限（必须知道，别被"牛逼"冲昏）

1. **瓶颈在搬运**：2.56 Gbit/s 写进 SRAM，但出口慢得多 → 浏览器演示是**极低占空比**
   （抓一小段、歇很久）→ **会漏包**，**不能当连续接收机/连续解码**
2. 只有 **S31 + 千兆网** 能 8/16 MSa/s 持续；其他型号（含 S3）走 UART → 够看频谱，不够连续听
3. 量化只有 **10 bit**（不是 12/16 bit）→ 动态范围有限，强邻道+弱信号场景吃力
4. 频段固定在 **2.4G / 5G**；要别的频段得**外接混频器**
5. **只放接收实现**（发射能力确实有，但怕被滥用为干扰，故意不提供）
6. 每颗芯片的寄存器/触发方式都不同 → 支持列表靠**一颗颗逆向**，文档还没补齐
   （他们是从 Espressif `librftest` 的 `adctrig` 函数反推的，还用了 LLM 帮忙）
7. 这是**未文档化功能**，不是官方特性 → 将来新型号可能没有，也可能被固件/量产配置关掉

| 场景 | 能做什么 |

| **手上就有 S3** | 立刻能当 **2.4G 频谱仪/瀑布图** 用（浏览器就行，零硬件）|

| **产品验证** | 给设备做"**无线环境体检**"：信道占用、周围 AP/BLE 密度、有没有干扰源 |

> lininit 需求原文：「我需要**中转**，不然后期更新很麻烦；需要单纯访问一个链接获取应用列表和相关信息，
> 然后点击下载，**下载失败就切换另外一个**；我有一个域名但想要几个下载源，需要稳定。
> 你先搞一个方案，**首先我不要腾讯了**。」

#### 0. 一句话结论

**一个稳定入口（你要的"中转"）= `https://bbk.linit.cn/bbk/`**，
它背后挂 **N 个下载源**；**后端换源设备完全无感**；设备侧再自带一份"直连备源清单"兜底。

分两层切换，覆盖两种故障：

| 层 | 谁在切 | 故障场景 | 设备感知 |
|---|---|---|---|
| **① 中转层（服务器 nginx）** | 服务器自动切后端 | 某个对象存储/Gitee 挂了、慢了 | **完全无感**（设备永远只访问一个域名） |
| **② 设备层（`mirrors[]`）** | 设备依次尝试 | **整个域名都不可用**（服务器宕机/DNS 挂了） | 自动切到直连备源，用户只看到"重试中" |

> 为什么两层都要：只用 ①，服务器挂了就全灭；只用 ②，你就得维护多个源地址、每次换源都要改固件。
> **① 解决"换源麻烦"，② 解决"入口单点"。**

#### 3. `index.json` 设计（**换源不用改固件**）

关键两点：**① 只存相对路径；② 内嵌 mirrors 列表。**

```json
{
  "ver": 4,
  "mirrors": [
    "https://bbk.linit.cn/bbk",
    "https://<bucket>.<region>.aliyuncs.com/bbk",
    "https://gitee.com/<账号>/ESP32-S3-RLCD-BBK/raw/master/store"
  ],
  "pkgs": [
    { "name": "qqtang", "label": "QQ堂冒险", "cat": "app", "ver": 6,
      "size": 45056, "crc32": "1a2b3c4d",
      "path": "pkgs/qqtang.lua" },
    { "name": "wuxia", "label": "英雄坛说", "cat": "app", "ver": 3,
      "size": 64512, "crc32": "9f3e0a71",
      "path": "pkgs/wuxia.lua" }
  ]
}
```

设备侧拼 URL：`mirrors[i] + "/" + pkg.path`。
⇒ **加源/换源 = 改这个 json 里的 `mirrors[]`，固件一行都不用动。**

`index.json` 本身也要多源：设备按 `mirrors[i] + "/index.json"` 依次试。

#### 4. 中转层：nginx 配置（核心是"后端挂了自动换"）

```nginx
upstream bbk_backend {
    server 127.0.0.1:8080;                                  # A. 本机静态(最优先, 0 成本)
    server <bucket>.<region>.aliyuncs.com:443 backup;       # B. 阿里云 OSS
    server gitee.com:443 backup;                            # C. Gitee raw
    keepalive 8;
}

server {
    listen 443 ssl http2;
    server_name bbk.linit.cn;
    # ssl_certificate ...;  ⚠ 必须开自动续期, 证书过期=设备下载直接失败

    location /bbk/ {
        proxy_pass         https://bbk_backend/bbk/;
        proxy_http_version 1.1;
        proxy_set_header   Host $proxy_host;
        proxy_set_header   Connection "";

        # ★ 关键: 后端超时/5xx 自动换下一个, 设备完全无感
        proxy_next_upstream        error timeout http_502 http_503 http_504 invalid_header;
        proxy_next_upstream_tries  3;
        proxy_next_upstream_timeout 10s;
        proxy_connect_timeout      3s;
        proxy_read_timeout         30s;

        proxy_buffering on;                     # 让 nginx 缓冲, 设备侧慢也不拖后端
        add_header Cache-Control "no-store";    # 商店索引要即时
    }

    # 可选: 走本机静态目录直出(比反代快, 适合主后端就是本机的情况)
    # location /bbk-local/ { alias /srv/bbk/; }
}
```

> **这就是你要的"中转"**：设备永远只认 `bbk.linit.cn`，后端在服务器上换，**设备不用改、不用重新配**。

#### 5. 自动化：你只 `git push`

`.github/workflows/store-sync.yml`（示例骨架）

```yaml
name: store-sync
on:
  push:
    paths: ["store/**"]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 计算每个包的 size/crc32 → 生成 index.json
        run: python tools/store_index.py --src store --out store/index.json
      - name: 上传到本机(linit.cn)
        run: rsync -az --delete store/ ${{ secrets.LINIT_SSH }}:/srv/bbk/
      - name: 上传到阿里云 OSS
        run: ossutil cp -rf store/ oss://<bucket>/bbk/ -e <endpoint> -i ${{ secrets.OSS_AK }} -k ${{ secrets.OSS_SK }}
      # Gitee 走它自己的「GitHub 导入 + 定时同步」, 不用在这里做
```

**这样"后期更新"就只有一步：改包 → `git push` → 所有源自动同步。**

#### 6. 设备侧要补的（这是工程，不是改地址）

| 缺口 | 做法 | 优先级 |
|---|---|---|
| **下载→落盘** 链路 | 现在 `app.net.http_get` 只把内容放 PSRAM 不落地。新增"下载到文件"：**优先落 TF** `/sdcard/store_pkg/`（商店已有的第二源，扫描逻辑零改动） | ★★★ |
| **多源依次尝试** | 按 `mirrors[]` 顺序：`index.json` 失败换下一个；某个包的 URL 失败换下一个 mirror 拼同一 `path` | ★★★ |
| **校验** | 下完对 `size` + `crc32`；不符就删掉重试下一个源（**必须**，半包会让应用一打开就崩） | ★★★ |
| **进度与重试** | "下载中 x% / 第 2 个源重试" —— 否则用户以为死机 | ★★ |
| **HTTPS 的 RAM** | TLS 握手+缓冲 ~30–50KB 内部 RAM；把 httpd 缓冲调小、**同一时刻只跑一个 TLS**；验收 `remcon audit` 的 `largest ≥ 8KB` | ★★ |
| **写 SPIFFS 的坑** | `/store/apps/` 写入会**禁 Flash cache** → 必须跑**专用内部 RAM 栈任务**，否则崩；所以**优先 TF** | ★★ |
| **大素材** | `wuxia` 素材 1.8MB 是大头。**先让素材随固件烧录，只有 `.lua` 走网络**（最省事） | ★ |

**单包很小**：`qqtang 44KB + wuxia 63KB + biossim 212KB + planeradar 29KB ≈ 350KB`，1M 带宽够用。

#### 7. 落地顺序（我建议）

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 | 在 `bbk.linit.cn` 上开 `/srv/bbk/`，nginx 加一个 `location /bbk/`（先只指向本机静态） | 你（5 分钟） |
| 2 | 传一份 `index.json` + 4 个 `.lua` 上去，**手机浏览器点一下确认能下** | 你 |
| 3 | 我把固件侧"下载→落盘→多源切换→crc32 校验→进度"做出来 | 我 |
| 4 | 接第 2 个后端（阿里云 OSS）并打开 `proxy_next_upstream` | 我（用 WorkBuddy 的连接器） |
| 5 | 加 GitHub Action 自动扇出，之后你只 `git push` | 我 |
| 6 | （可选）Gitee 镜像 + `mirrors[]` 里补直连备源 | 你/我 |

> ⚠ **第 1 步里最容易忘的一条**：**HTTPS 证书的自动续期必须开着**。
> 证书过期 = 设备下载**直接失败**，而且现象和"网络不好"一模一样，极难排查。

#### 1. 选型硬标准（先定标尺，再看候选）

| # | 标准 | 为什么 |
|---|---|---|
| ① | **能给"文件直链"** | 设备是 `esp_http_client` 直接 GET 文件本体。⛔ **网盘"分享链接"不行** —— 它返回的是 HTML 页面（要 JS/跳转），设备拿不到字节 |

| ④ | 支持 **HTTPS** | 公网明文 HTTP 容易被中间劫持/篡改固件包；HTTPS 在 S3 上可行（见 §4） |
| ⑤ | 免费额度够用 | 总量很小：`qqtang 44KB + wuxia 63KB + biossim 212KB + planeradar 29KB ≈ 350KB` 代码；**素材另算**（wuxia 的 `/store/wuxia` 就 1.8MB） |

##### 2.5 为什么"免备案"这条很关键

- **国内服务器 + 绑域名** → 必须 ICP 备案（个人也能备，但要走流程、等审核、域名还得实名）。
- **对象存储的默认域名**（`xxx.cos.ap-guangzhou.myqcloud.com` 这类）**可以直接对外提供直链，无需备案**。
- 所以：**只是"给设备下几个静态包"这个需求，选对象存储就够了，别去买服务器**。
- 将来真要自定义域名（`dl.你的域名.com`）再补备案即可，届时只需改 `index.json` 里的 URL 前缀。

##### 3.1 `index.json` 建议格式（越简单越好，设备侧解析便宜）

```json
{
  "ver": 3,
  "pkgs": [
    { "name": "qqtang", "label": "QQ堂冒险", "cat": "app", "ver": 6,
      "size": 45056, "crc32": "1a2b3c4d",
      "url": "https://xxx.cos.ap-guangzhou.myqcloud.com/pkgs/qqtang.lua" }
  ]
}
```

> 设备侧不引 cJSON 也能解析：用现有的 `app.json_*` 那套极简解析（`tools/lua_sim.py` 里已有同构实现），
> 或者干脆换成**行文本格式**（`name|label|cat|ver|size|crc32|url` 一行一个），解析成本更低、更抗错。

#### 4. ⛔ 固件侧的缺口（这是"要做工程"，不是"改个地址"）

| 缺口 | 说明 |
|---|---|
| **没有"下载→落盘"链路** | 现在 `app.net.http_get` 只把响应体放进 **Lua 字符串（PSRAM）**，不落地。要新增：Lua 侧 `app.fs.write`，或 C 侧一个"下载到指定目录"的接口 |
| **优先落 TF 卡** | `/sdcard/store_pkg` 已经是商店的第二个源（`AM_STORE_SRC2`）→ **下载到卡上，商店扫描逻辑零改动**。写 SPIFFS（`/store/apps/`）会**禁 Flash cache**，必须放**专用内部 RAM 栈任务**里（否则崩），且 SPIFFS 写入慢 —— **无 TF 卡时再考虑** |
| **HTTPS 的 RAM 代价** | TLS 握手 + 收发缓冲要 ~30–50KB **内部 RAM**。验收底线 `remcon audit` 的 `largest ≥ 8KB`。S3 上可行，但要把 httpd 缓冲调小、并串行化（同一时刻只跑一个 TLS） |
| **必须校验** | 下载完对 `size` + `crc32`，否则半包会让应用"打开就崩"。现有 `tools/pack_app.py` 的 LAPP 头里已有版本/名称，可复用 |
| **大素材（wuxia 1.8MB）** | 代码只有几十 KB，素材是大头。方案：① 素材也走网络，首次安装等 20s+；② 按世界分片按需下载；③ **素材继续随固件烧录**，只有 `.lua` 走网络（最省事，推荐先这样） |
| **进度与断点** | 至少要有"下载中 x% / 失败重试"，否则用户以为死机 |

#### 5. ★ 最终推荐：**自有站为主 + 对象存储为备（双源）**

linit 2026-10-03 补充：**自有站是 `linit.cn`**，担心它不稳定。

##### 5.1 先给结论

> **主源 = `linit.cn`（你自己的站），备源 = 腾讯云 COS/OSS（或 CloudBase 静态托管），
> 设备侧按"URL 列表依次尝试"。索引文件本身也给两个源。**

理由只有一句：**设备侧本来只是"GET 一个 index.json"，多给几个 URL 的成本是零，
却把"网站不稳定"这个担心直接化解掉**。这不是"二选一"，而是"两个都要、分主备"。

##### 5.2 为什么 `linit.cn` 可以当主源（实测证据）

| 项 | 实测 | 含义 |
|---|---|---|
| DNS | `linit.cn` → **47.122.46.5** | — |
| 归属 | **阿里云（Aliyun Computing / ALISOFT，CN）** | ★ **国内节点**，设备（也在国内）延迟会很低 |
| 备案 | 既然它在阿里云国内节点对外提供站点 | ★ **ICP 备案这道坎你早就过了** ← 这是选自有站最大的隐性好处（见 §2.5） |
| 可达性 | ⚠️ **我这边测不了**（工具环境默认拦出网，`CONNECT tunnel failed 502` 是沙箱代理返回的，不是站点问题） | 需要你自己在手机浏览器上点一下确认 |

##### 5.3 分工建议

| | 角色 | 放什么 | 为什么 |
|---|---|---|---|
| `linit.cn` | **主源** | `bbk/index.json` + `bbk/pkgs/*.lua` | 你可控、随时改、国内节点、已备案；改一个包不用求人 |
| 对象存储（COS/OSS） | **备源 / 镜像** | 同样的 `index.json` + `pkgs/` | 云厂商 SLA 兜底；**抗突发流量**（自有 VPS 被打/限速时它顶上）；按量计费几乎免费 |
| 固件内置 | **兜底** | 一份"出厂索引"（只有版本号） | 网络全挂时商店仍列出**本地已有包** + 提示"暂时无法更新"，**绝不砖** |

设备侧取包顺序：`主源 → 备源 → 内置兜底`。任一成功即用。

##### 5.4 ⛔ 放包的形式要求（这几条最容易踩）

1. **必须是纯静态直链**：`https://linit.cn/bbk/index.json`、`https://linit.cn/bbk/pkgs/qqiang.lua`
   —— ⛔ 不能经过"登录 / 跳转 / JS 渲染 / 防盗链"任何中间层（设备不是浏览器）。
2. **别让应用包走动态框架**：如果 linit.cn 是 WordPress/PHP 类站点，把包放到**独立静态目录**，
   或干脆用一个子域（`dl.linit.cn`）直出静态文件。避免"站点被攻击 → 商店一起废"。
3. **证书自动续期必须开着**（Let's Encrypt 之类）—— 证书过期 = 设备下载**直接失败**，而且很难查。
4. 目录结构建议（一眼能改、不牵连站点其它内容）：
   ```
   /www/linit.cn/bbk/index.json
   /www/linit.cn/bbk/pkgs/*.lua
   ```
   发布就是用 `rsync` 把本地 `build/store_pkgs/` 同步上去。
5. **单包很小**（`.lua` 几十 KB），1M 带宽都够；但**以后若要下 wuxia 的 1.8MB 素材**，
   就吃带宽了 —— 那时用对象存储+CDN 更合适（这也是"备源"提前建好的理由）。
6. 允许 `Range` 请求、开 gzip（可选，省流量、断点续传用）。

##### 5.5 怎么判断"自有站够不够稳"（你自己 30 秒能答完）

| 问题 | 若是"否/不知道" |
|---|---|
| 最近 3 个月它挂过吗？ | 挂过 → 老老实实做双源，别赌 |
| HTTPS 证书有自动续期吗？ | 没有 → **先去开**，这是设备下载最常见的猝死原因 |
| 被 DDoS 时云厂商有基础防护吗？ | 阿里云 ECS **裸机默认没有**；OSS 有 → 这也是备源的价值 |
| 你有服务器运维精力吗？ | 没有 → 主源也别做复杂，纯静态目录即可 |

> 结论：**先只上 `linit.cn` 完全可行**（尤其你已经有备案+国内节点），
> 把"对象存储备源"当成**第二周再补**的事 —— 设备侧代码一次写好"多源列表"，以后加源只是改 `index.json`。

#### 7. 「把包放进 GitHub 仓库 + 国内能下载」怎么做

linit 2026-10-03：想放到 `https://github.com/LinIT-L/ESP32-S3-RLCD-BBK` 仓库里，
问"有没有国内可以下载的"。

##### 7.1 结论：有，但**最稳的不是找第三方镜像，而是用你自己的域名做 GitHub 的出口**

```
GitHub  LinIT-L/ESP32-S3-RLCD-BBK
   store/index.json
   store/pkgs/*.lua            ← 你的维护习惯不变：push 到 GitHub 就是发布
        │  push
        ▼
linit.cn 服务器:  cron 每 5 分钟 git pull   (或 GitHub Webhook 触发即时拉)
        │  nginx:  location /bbk/ { alias /srv/bbk/store/; }   ← 只读静态直出
        ▼
设备:  GET https://linit.cn/bbk/index.json
```

**为什么这是最优**：
- 你只管 push GitHub（**唯一真相源**），不用维护第二套发布流程；
- 设备只访问 `linit.cn` —— 国内阿里云节点、已备案、你自己的域名、**完全可控**；
- **不依赖任何第三方镜像**（第三方哪天挂了，你无从修复）；
- 一劳永逸：以后所有"发布"动作都只是 `git push`。

服务器侧只要求：能 `git pull` + nginx 直出静态目录。连"发布脚本"都不用写。

##### 7.2 备源（设备侧依次尝试，多给几个 URL 成本为零）

| 顺序 | 源 | 国内可用性 | 备注 |
|---|---|---|---|
| 1 | `https://linit.cn/bbk/…` | ✅ 最稳 | 主源，见 §7.1 |
| 2 | `https://cdn.jsdelivr.net/gh/LinIT-L/ESP32-S3-RLCD-BBK@main/store/…` | ⚠️ **~85%** | 官方 2026 数据：中国区可用率约 85%、比 raw 快约 6 倍；单文件 ≤50MB。**只做备源**（15% 随机失败） |
| 3 | `https://gitee.com/<你的账号>/ESP32-S3-RLCD-BBK/raw/master/store/…` | ✅ 稳 | Gitee「导入 GitHub 仓库」+ 定期同步。⚠️ 同步是**手动/定时**，不是实时；raw 有限流风险 |

##### 7.3 ⛔ 明确不能当设备分发源的

| 途径 | 为什么不行 |
|---|---|
| `raw.githubusercontent.com` | 国内长期不稳（平均延迟 3s+、常断） |
| `ghproxy.cn` / `gh.api.99988866.xyz` 等代理 | 第三方、无 SLA、会挂/限流/改行为。**可以人工临时下载，绝不能进固件默认源** |

| ⚠️ **GitHub Releases 附件**（`LinTOS_v1.3_16MB.bin`） | 国内下载成功率低（有资料称 <60%）；同样建议 `linit.cn` 放一份 |
